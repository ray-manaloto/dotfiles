# Receipt — #440: Who owns `dot_config/mise/config.toml.tmpl`, and how does that kill the mise lock resurrection?

**Verdict:** **dotfiles owns it as ONE OS-branched source file** (per #439's idiom — darwin branch =
the host config, linux branch = the existing devcontainer overlay, `.chezmoiignore`'s darwin gate
retired), because retiring mde removes the *only* non-dotfiles writer and assert-only would orphan
the target. **But ownership does not "permanently kill" the hook, and the ticket's premise that it
could is wrong**: killing the emitter is the only *structural* part; everything else is detection.
The honest kill is **(a)** the emitter dying with mde — enforceable, because the active chezmoi
`sourceDir` is machine-checkable and is *still mde today*; **(b)** a **hard CI gate on the
unscoped command, not on the `[hooks]` key** — measured this session, the destructive act is
`mise lock` **with no `--platform`** (802 Linux conda rows → 0), while `--platform macos-arm64`
leaves all 802 intact, so a `[hooks]`-token check both misses a task that shells out to bare
`mise lock` and over-bans legitimate hooks; and **(c)** host-side **detection only** — there is no
hard stop available for `~/.config/mise/config.toml`, and saying otherwise would overclaim.
⚠️ Scope note: the `update:all` task body is an **adjacent unmeasured risk**, not a proven second
vector — today's accident rewrote the lockfile *benignly* and did not reproduce #370.

## Notes

### The measurement that changed the answer

The received framing — #370's title, its body, and the guard comment at
`~/.config/mise/config.toml:285` — all say the re-lock drops **platform entries**, "548 linux-x64
entries lost". Re-derived in an isolated scratch copy (dotfiles' real `mise.toml` + `mise.lock`),
mise **2026.7.18**, every run rc=0:

| run | `[tools.*.platforms.*]` | `[conda-packages.linux*]` | `[conda-packages.macos*]` | `[conda-packages.windows*]` |
|---|---|---|---|---|
| committed baseline | 72/36/18/34 | **802** | 0 | 160 |
| bare `mise lock` | **unchanged** | **0** | 267 | 160 |
| `--platform linux-x64` (arm A) | unchanged | **665** (exactly the 137 `linux-x64` rows gone; other 5 linux variants intact) | 0 | 160 |
| `--platform macos-arm64` (arm B) | unchanged | **802 — untouched** | 89 | 160 |

**The defect is live; the noun is wrong.** The `platforms` table — the thing every existing
write-up names — is exactly the part that survives. The victim is **`[conda-packages.*]`**.

This nearly produced a false clear: my first pass counted only `platforms.*`, saw 72→72, and
concluded "nothing lost" — the correct count of the wrong table. **An inherited claim can be true
in substance and wrong in the noun, and the wrong noun aims your probe at the wrong table.**

**Arms A and B give the mechanism, and they exist because the review demanded them.** `mise lock`
re-solves conda **per targeted platform**; on macOS it can only solve macOS, so every *targeted*
foreign platform loses its conda rows and every *untargeted* one is left alone. Bare `mise lock`
targets all → all 802 die. Arm B is the control that proves targeting works, which is also what
refutes finding #9.

**Correcting a carried-forward warning.** The 2026-08-01 handoff says *"⚠️ Do NOT run the suggested
`mise lock --platform macos-arm64` — that is the destructive whole-file re-lock."* **Measured
false** (arm B): it leaves all 802 Linux conda rows intact. The destructive form is the **bare**
one; the warning conflated the two. `--platform` naming a *foreign* platform is the other unsafe
shape, and that one is real (arm A).

**Conceded (finding #10):** "isolated" here means *no parent `mise.toml`*. I did not exclude the
global/system config, cache or registry. Arm B holding Linux at 802 under identical conditions is
what keeps the comparison sound, not the isolation claim.

**Softened (finding #12):** mise's help says bare `mise lock` updates *"all platforms already in
lockfile"*. Whether that is a preservation guarantee for backend package tables, or only a
statement about platform selection, is not settled by the help text — so this is reported as
observed behaviour, not as a documented-contract violation.

### Today's accident: a real control arm, for a smaller claim than I first made

Ray accidentally ran `mise self-update && mise upgrade --bump && update-all && mise doctor` in the
dotfiles clone at the start of this session. Both lockfiles were rewritten **with the hook already
absent**. My first draft read that as disproving the single-vector framing. **Finding #13 is right
that it does not**: the run was *benign* (its `mise.lock` diff was 385 changed lines; dropping the
conda set costs ~2680), so it demonstrates a lockfile **mutation**, not a #370 **destruction**.

What survives: `update-all` → `mise run update:all`, whose body runs `mise upgrade --bump` and
`mise install`, and #370 alleges the latter is destructive. That allegation is **inherited and
unmeasured here** (re-deriving it means installing ~193 tools). So the task body is an **adjacent
risk to measure**, not a proven second vector — and it is already covered by (b), because the gate
bans the unscoped command wherever it appears.

Parked, not acted on: that run wrote full `linux-x64` lock entries for hk 1.54.0 **from macOS**,
which makes **#421's stated blocker ("a linux-x64 lock regen that cannot run on macOS") look
stale**. Out of scope of map #431 by the map's own text.

### Why write, not assert-only, given #435 went the other way

#435 decided dotfiles owns `~/.config/fnox/config.toml` **by assertion, never by writing**, under
the rule *assert iff drift is SILENT*. Finding #4 is right that the drift here is silent and the
rule therefore points at assertion. The discriminator the rule omits — and the reason this file
goes the other way:

**Assert-only presumes an existing non-dotfiles writer.** fnox's config has several (`fnox set`,
the keychain sync, mde's generator); dotfiles asserting over it leaves a maintained file. This file
has exactly **one** writer, mde's template, and this map **retires it**. Assert-only would leave
`~/.config/mise/config.toml` with no writer at all — an unmanaged-but-load-bearing host file, which
the map already lists as a known hazard.

The content axis points the same way but is weaker than I first wrote (finding #5): fnox's config
holds 49 declarations and per-secret opt-ins derived from Doppler and keychain state — genuinely
not template content. This file holds tool pins, settings, env and tasks, which are *reconstructible*
— **but not yet reconstructed**. `chezmoi diff` shows the next apply deletes Ray's four hand-added
`[tasks."update:*"]` sections, `[shell_alias]` and the guard comment. Moving those into the template
is a **hard precondition on the takeover transition**, not cleanup — the same shape #434 found for
the config-template handover. Until it is done, taking ownership reproduces the wipe class on day one.

### The self-erasing fix (hygiene, not a kill — finding #18)

`chezmoi diff` also removes `# [hooks] postinstall = "mise lock"  -- REMOVED 2026-07-30.` and its
three explanatory lines. The record of *why* lives only in the artifact the render overwrites, so
after one apply a reader cannot tell the removal was deliberate. I claimed this was "the mechanism
by which it comes back a third time"; finding #17 is right that this is unproven. The defensible
statement is narrower: **an apply destroys the evidence a reviewer would need**, so the rationale
belongs in the reviewed source. It is hygiene, not part of the technical guarantee.

### What the two tiers actually are, after the review

- **(a) Emitter retirement — the only structural part.** mde's template is the sole emitter. The
  enforceable condition is not "mde is gone" but the machine-checkable **active chezmoi
  `sourceDir`**, which is *still mde today*. A `doctor.toml` axis on that covers the whole class
  (any target mde restores), not just this token — finding #3's improvement over my draft.
- **(b) Source-side, CI-visible, HARD.** A `suites.toml` contract over the owned template banning
  the **unscoped re-lock command** — bare `mise lock`, or `--platform` naming a non-host platform —
  anywhere in the rendered config, in a hook body *or* a task body. Not a `[hooks]` ban: findings
  #6/#7 are right that the key is the wrong target, and arms A/B show the command is the right one.
  This is the tier that can actually block a change, because CI fails a PR.
- **(c) Host-side, DETECTION ONLY.** A `doctor.toml` axis over the live
  `~/.config/mise/config.toml`, since a runner has no `~/.config/mise`. Warn-only, exit 0, per
  #435's posture — and finding #1 is right that this **prevents nothing**. #435 could pair
  warn-only with a hard stop in the secrets CLI; there is no equivalent chokepoint here, and
  claiming one would be false.

Neither is built here. Map #431 is **planning-only**.

**Version-bound (finding #20):** every measurement above is mise **2026.7.18**, chezmoi 2.71.1,
on macOS arm64. "Permanently" is dropped from the verdict; the gate in (b) is what makes the
property re-checkable when mise changes.

### Does this survive #448?

**Partly — narrower than I first claimed.** The **ownership** answer survives: mise's dotfiles
templating is Tera with `os()`/`os_family()`, so the OS-branch idiom exists under both tools, and
#448 changes the source filename rather than who owns the target. The **assertion mechanism does
not** — finding #16 is right, and the prior art I was quoting says so directly:
`chezmoi managed` has **no mise-dotfiles analogue**, so tier (a) is cheap under chezmoi and unbuilt
under mise. Handed to #448 rather than answered here, along with the circularity: under
`mise bootstrap dotfiles` the renderer would be rendering **mise's own global config**.
