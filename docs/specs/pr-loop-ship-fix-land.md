# Spec draft — `pr-loop`: one ship → fix → land loop (input to `/to-spec`)

Status: DRAFT (Ray, 2026-09-23, via `/skill-creator:skill-creator`). Not implemented. Sequenced as a Phase 11
ticket **after #1329 (datamodel-codegen) and #1330 (universal logger + subprocess runner)**. `/to-spec` turns this
into the ticket spec; `/to-tickets` files it; `/implement` builds it.

## Objective

Today an agent runs `mise run ship`, reads a streamed log to learn what failed, fixes, re-ships, waits for the
merge, then runs `mise run land -- <PR#>`. Every step costs context: `ship_main` and `land_main` return a bare
`0`/`1` (`python/src/dotfiles_setup/pr.py:552-618`, `:880-912`), so the only way to learn *which* gate or check
failed is to read logs. `pr-loop` makes the whole cycle one loop whose every stop is a **small typed outcome**
(generated enum + the one log path that matters), so the agent spends tokens only on the fix itself.

## Ray's rulings (2026-09-23)

1. Build after #1329/#1330; the loop is their first real consumer (generated models/enums, universal logger).
2. Fix scope: **local gate failures AND PR/CI check failures**, bounded (see Loop).
3. Testing: a `--dry-run` mode + pytest fixtures per typed outcome; skill-creator evals run in dry-run only; the
   **first live run is the next set of changes committed to be shipped/landed**.
4. Layering protocol (standing): reusable skill(s) → mise task(s) → python library module(s)/function(s); wrappers
   call the lower layers, never re-implement them.

## Typed outcomes (generated per #1329, never hand-written)

Schema source: a JSON Schema (or the #1329-chosen source format) under the repo's schema tree; models and enums are
generated by datamodel-code-generator into the model system #1329 settles (`msgspec` via `codec` is the project
standard, `python/AGENTS.md` § Serialization). Exit codes are a generated enum too (the pattern
`gate_result.STATUS_EXIT_CODES` already hand-writes: `GateStatus` at `gate_result.py:32`, the map at `:66`).

`LoopStatus` (one per stop; each maps to a distinct exit code):

| Value | Meaning | Agent action |
|---|---|---|
| `LANDED` | merged, main CI green, Mac synced | done |
| `GATE_FAILED` | a local ship gate failed | fix the named gate, commit, re-run loop |
| `CHECKS_FAILED` | a required PR check failed | fix per the named check + its run-log path, commit, re-run loop |
| `PREFLIGHT_REFUSED` | dirty tree / on main / no diff | commit or branch, re-run |
| `MERGE_PENDING` | checks still running at the wait bound | re-run later (no fix) |
| `CONFLICT` | branch conflicts with main | stop, ask (rebase is a judgment call) |
| `BRANCH_CLOSED` | a change is needed while auto-merge is armed and checks are green/pending | stop; new branch + cherry-pick (#544 race) |
| `LAND_FAILED` | post-merge validation failed | stop; route to `persistence-gate-retry.md` signatures |
| `ROUND_LIMIT` | fix rounds exhausted | stop, surface residuals to Ray |
| `INFRA_ERROR` | `gh`/network/API failure | retry once, then stop |

`LoopOutcome` fields: `status`, `pr_number`, `head_sha`, `round`, `failed_name` (gate or check), `log_path`
(file the universal logger wrote, #1330), `log_excerpt` (bounded tail, ≤40 lines), `next_command` (the exact
command to run next). The CLI prints ONLY the encoded outcome on stdout; full logs go to `log_path`.

## Loop

1. `ship` (reused). Gate fail → `GATE_FAILED`. Success arms auto-merge pinned to the head (`--match-head-commit`,
   `pr.py:435-478`).
2. Read the PR state ONCE per invocation — no client-side watch (`pr.py`'s design is native auto-merge, and the
   guard denies `gh pr checks --watch`): `pr_checks_green` + `gh pr view --json state`. Failed check →
   `CHECKS_FAILED`; its `log_path` is written by `gh run view <run-id> --log-failed` into the universal logger's
   directory. Still pending → `MERGE_PENDING` (the caller re-invokes later, e.g. as a harness background run).
3. MERGED → `land` (reused) → `LANDED` or `LAND_FAILED`.
4. Re-entry is decided from the state file (keyed by branch: last step, head SHA, round): if HEAD is unchanged since
   the last ship, re-enter at step 2 (never re-ship without a new commit — e.g. after `MERGE_PENDING`); if HEAD moved
   (a fix was committed), re-enter at step 1 (ship re-gates, pushes, re-arms on the new head). The round counter
   increments only on a push from a red state and resets when the PR lands or is closed. Max **2** fix rounds per loop (orchestration two-round bound), counted in a small state
   file keyed by branch; round 3 → `ROUND_LIMIT`.

**Auto-merge race rule (memory `feedback_amend_after_ship_races_automerge`, #544):** a push after arming is safe
ONLY when the PR cannot merge at the current head — i.e. a required check has FAILED. The loop therefore pushes a
fix only from `CHECKS_FAILED` (ci-gate red, GitHub also auto-disables auto-merge on a new push) or `GATE_FAILED`
(never pushed). It never pushes while checks are green or pending; a change needed in that state stops with `BRANCH_CLOSED`
("new branch + cherry-pick"), a status distinct from `CONFLICT`.

## Dry-run

`pr-loop --dry-run` resolves branch, diff, gate matrix and PR state, prints the outcome it WOULD produce and the
commands it would run, and performs no push, arm, merge, checkout or sync. Every `LoopStatus` has a pytest fixture
driving `run_loop` with stubbed `gh`/git (both arms: the stub that yields the status, and a control that does not).

## Skill draft (installed only when the code lands — a SKILL.md naming a nonexistent task would fail `doc_refs`)

```markdown
---
name: pr-loop
description: Ship, fix and land a branch in one bounded loop via `mise run pr-loop` — gates, push, PR,
  auto-merge, CI wait, post-merge land — stopping only on a typed outcome. Use whenever committed work should
  become a merged, landed PR, when asked to "ship and land", "get this merged", or after a fix to a failed ship,
  instead of running `ship`, waiting, and `land` by hand. For bot PRs use pr-workflow's `automerge`.
---

Run `mise run pr-loop`. Read ONLY the printed outcome; open `log_path` only when fixing.

- `LANDED` → done; report the PR and merge SHA.
- `GATE_FAILED` / `CHECKS_FAILED` → fix `failed_name` using `log_excerpt` (open `log_path` if the excerpt is not
  enough), commit, run `next_command`. Do not push by hand.
- `PREFLIGHT_REFUSED` → commit or branch as the outcome says, re-run.
- `MERGE_PENDING` → re-run later; nothing to fix.
- `CONFLICT`, `BRANCH_CLOSED`, `LAND_FAILED`, `ROUND_LIMIT` → stop and ask Ray with the outcome (AskUserQuestion).
- `INFRA_ERROR` → re-run once; then ask.

Why the outcome and not the log: the log is for the fix, the outcome is for the decision — reading full logs on
every stop is what this loop exists to avoid.
```
