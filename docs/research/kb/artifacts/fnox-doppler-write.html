Teaching fnox to write to Doppler

It does not exist yet, anywhere I can see. It is also small — the provider already shells out to the Doppler CLI, so the write is one more subcommand. Here is exactly what changes, and the separate defect found while looking.

Found while looking

A separate defect, and it is the more urgent one

The Provider trait's default put_secret already handles read-only providers correctly — it returns Err("This provider does not support storing secrets"). So fnox knows the right answer.

set.rs never asks it. The dispatch checks for the two writer capabilities, and a read-only provider falls into an else that yields (None, None) — put_secret is not called, so the trait's error never fires. Further down, (None, None) plus a named provider lands in a branch that writes the raw value into the config file.

// crates/.../commands/set.rs — the dispatch
} else {
    // Not an encryption or remote storage provider
    (None, None)          // <- put_secret never called
}

// ...and further down, where that (None, None) lands:
} else if provider_name_to_use.is_some() {
    // Provider specified or default provider available
    // (but not an encryption/remote provider)
    secret_config.set_value(Some(value.clone()));   // <- CLEARTEXT into fnox.toml
}
Why this matters more than the feature

The feature's absence is a limitation you can route around. This is a silent failure that plaintexts a credential to disk while appearing to succeed — and it applies to all six read-only providers, not just Doppler. The fix is small and independent: make that else call put_secret (or return its error) instead of yielding (None, None). Read from source, not executed — confirm in a throwaway FNOX_CONFIG_DIR before filing

The whole difference is step 2. Once capabilities() returns RemoteStorage, set.rs's existing dispatch routes to put_secret on its own — no change needed there for the feature.

The change

Four edits, one of them the real work

All in crates/fnox-core/src/providers/doppler.rs unless noted. The provider is 464 lines today and already shells out to the Doppler CLI, so nothing new has to be invented.

1 · Let the command helper carry stdin

The real work

doppler.rs — execute_doppler_command

The helper hardcodes cmd.stdin(std::process::Stdio::null()), because every existing call is a read. A write has to pass the value somehow, and it must not be argv — fnox set's own help warns that argv leaks to shell history and ps, and that applies just as much to the doppler child process it spawns.

// today
cmd.stdin(std::process::Stdio::null());

// needed: an optional payload, piped and written to the child
cmd.stdin(match stdin_payload {
    Some(_) => Stdio::piped(),
    None    => Stdio::null(),
});

This is the only edit that touches shared code and the only one that can regress existing reads, so it wants its own test.

2 · Declare the capability

3 lines

doppler.rs — impl Provider for DopplerProvider

fn capabilities(&self) -> Vec<ProviderCapability> {
    vec![ProviderCapability::RemoteStorage]
}

This single addition is what flips set.rs's dispatch from the cleartext branch to the put_secret branch.

3 · Implement the write

~15 lines

doppler.rs — same impl block

async fn put_secret(&self, key: &str, value: &str) -> Result<String> {
    // project/config flags are added by build_common_args()
    self.execute_doppler_command_with_stdin(
        &["secrets", "set", key],
        value,           // on stdin, never argv
        Some(key),
    ).await?;
    Ok(key.to_string())  // config stores the REFERENCE, not the value
}

Returning the key name rather than the value is what makes the config hold a reference. That contract is already documented on the trait: "Remote storage providers: store remotely and return the key name."

4 · Docs and the schema

small

docs/providers/doppler.md · docs/public/schema.json

#376 shipped 250 lines of provider docs and 23 of schema. A write path needs the fnox set --provider doppler example that bitwarden-sm.md:140 already has and doppler.md conspicuously lacks — that absence is currently the clearest signal to a reader that writes are unsupported.

Also worth doing, separately

Fix the set.rs fall-through so the other five read-only providers error instead of plaintexting. It is a different change with a different risk profile, and bundling it with a feature makes both harder to review. Two PRs, not one.

What it costs you

The part that is not code

You cannot ask first. jdx/fnox has GitHub Issues disabled. There is no way to propose the change, check whether writes were deliberately withheld, or find out if a maintainer already has an opinion. Every contribution there is speculative by construction.

Your CLI cannot depend on it until it ships. Merge, then release, then your pin moves — on someone else's timeline. If the CLI is blocking on this, you have coupled your schedule to an upstream you cannot even file against.

There is a hedge. Doppler writes are one subcommand of the Doppler CLI. The CLI can shell out to doppler secrets set directly today, ship now, and drop that path later if the PR lands. That keeps the contribution valuable without making it load-bearing.
