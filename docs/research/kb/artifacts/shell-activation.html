Blocking decision · retiring 50-mde-secrets.zsh

What replaces the shell activation

Retiring mde deletes the one file that loads your credentials. Five candidates, measured — and the two most obvious ones both turn out to be traps.

Both tools can do it — that was the question, and the answer is yes

fnox can, two different ways, and mise can via a real global env source: ~/.config/mise/config.toml's [env] applies in every directory, not just from that directory down. Measured: 26 keys survive at /tmp under a sanitised env -i, with a 3/3 control arm.

But mise cannot replace fnox — only re-house the call. Its two native secret paths are both experimental and file-or-inline only, so using them means re-homing all 50 secrets out of fnox and Doppler. Every viable mise route still ends in fnox export.

Five candidates

The options

B · fnox export once per shell

Recommended
# ~/.zshrc.d/50-dotfiles-secrets.zsh, owned by this repo
eval "$(fnox export -f shell -P shell --no-defaults)"
ProScoping actually works here. Verified in an isolated fixture: the scoped arm yields only that profile's secrets, and -P bogus --no-defaults yields nothing — fail-closed, unlike every other path. Values round-trip byte-identical through eval, including spaces, quotes and $. Respects per-secret env = false/"exec".
ProResolves once per shell. No prompt hook at all, so it sidesteps the fnox/mise hook-ordering hazard entirely and cannot wedge a prompt.
ConNo auto-reload. Rotate a secret and existing shells keep the old value until you re-source or open a new one — activate would have picked it up on the next cd.
ConRequires declaring a shell profile you do not have today; your config has zero [profiles.*] blocks. Deriving that subset is real work.

A · Relocate fnox activate as-is

Safest, unscoped
eval "$(fnox activate zsh)"
ProA one-line relocation of a mechanism that already works. Zero behaviour change, so it cannot break your morning, and it decouples retiring mde from settling the exposure model.
ProAuto-reloads on cd and on config change, which B does not.
ConCannot be scoped, at all. -P and --no-defaults are accepted and silently discarded — ActivateCommand has only two fields and the hook is hardcoded. Writing activate -P agent --no-defaults reads as scoped in review and hands over all 50.
ConKeeps a per-prompt hook, and its early exit fails on every cd, every config mtime change, and every new shell.

C · mise _.source in the global config

Works, adds moving parts
[env]
_.source = "/abs/path/to/load-secrets.sh"   # NEVER a bare `fnox` inside
Pro_.source is the only command escape hatch in mise's [env], it is not experimental, and mise's hook is already installed — so this removes a per-prompt hook rather than adding one. mise's hook also has a dedup fast-path fnox's lacks.
ConReproduced fork bomb. A bare fnox inside _.source with mise shims on PATH re-enters through the shim: 3,011 processes, load 17.9 → 28.4. Absolute path returns instantly. Same root cause as mde#75.
Conenv_cache = true with a 1h TTL means decrypted secrets are cached to disk — a new exposure surface, and only visible via mise settings --all.
ConDelivery through _.source is unverified end-to-end — the probing agent's shell lacked AGE_PRIVATE_KEY, so its test arm could never have passed. Needs a re-run in your real shell.

D · mise-native sops or inline age

Not now
ProRemoves fnox from the shell path entirely and gives per-project scoping structurally, by directory.
ConMeans re-homing all 50 secrets out of fnox and Doppler into files — the migration you have twice declined, to reach the same place.
ConBoth paths are flagged experimental by mise, and direct age returns the ciphertext as-is when decryption fails rather than erroring — a silent wrong-value failure.

E · the mise-env-fnox plugin

No
ConLast code change 2026-02-21, 0 releases, 7 open issues, 16 stars. Registered on this host but inert.
ConIts own README says: "I am not sure this plugin is a good idea… I would probably advise avoiding this." fnox's docs warn it off too, as an "incomplete experiment". When both authors say no, that is the finding.
What actually happens

Shell startup, the two leading options

The difference is not cosmetic — it is where the resolution happens and how often.

A · fnox activate — a hook that re-resolves

eval "$(fnox activate zsh)"
yourc fragmentfnoxprovidersshell env
1
emit hook code — no secrets yet
2
_fnox_hook into precmd_functions AND chpwd_functions
3
new shell → early exit FAILS → resolve all 50
4
steady prompt: should_exit_early → 0 bytes, ~2ms
5
every cd → resolve again

Measured warm at 11.78 ms against a 9.57 ms bare fnox --version spawn floor — so the steady-state hook costs about 2 ms and is genuinely cheap. The cost lives in steps 3 and 5, which is why a hung provider CLI felt like it wedged "every prompt": it was every new shell and every cd.

B · fnox export — resolve once, then nothing

eval "$(fnox export -f shell -P shell --no-defaults)"
yourc fragmentfnoxprovidersshell env
1
export -f shell, scoped profile
2
resolve ONLY the profile's secrets — once
3
shell-quoted export lines
4
eval → the scoped set is in the shell
5
no hook registered — every later prompt costs zero

Step 5 is the whole argument. No prompt hook means no per-cd re-resolution, no interaction with mise's hooks, and no path by which a hung provider can touch an already-running shell. The price is step 2 never repeating: a rotated secret needs a new shell.

Found while measuring

Six hazards, four of them undocumented

HazardWhat happensStatus
_.source fork bomb A bare fnox inside _.source re-enters via mise's shim. 3,011 processes, load 17.9 → 28.4. Absolute path returns instantly. Reproduced
activate discards its flags -P and --no-defaults are accepted and ignored. diff of activate output with and without them is identical; control against --no-hook-env shows a 16-line diff, so the probe discriminates. Verified
Hook ordering fnox prepends to precmd_functions, so whichever tool is eval'd last runs first. fnox consults an existing env var before resolving, so mise-set names can win. And mise capturing fnox's exports is where __MISE_DIFF's payload comes from. Undocumented control-armed: 0 hits for ordering terms against a working control
mise's unset preamble mise activate installs a preamble that will unset all 50 credentials — so ordering is not merely cosmetic. Source-read
mise caches decrypted secrets to disk env_cache = true, TTL 1h, visible only via mise settings --all. Any mise-mediated route writes plaintext-equivalent material to disk. Verified setting
age fails open on decrypt mise's direct-age path returns the ciphertext as-is when decryption fails, rather than erroring — a consumer gets a wrong value instead of a failure. Docs-stated
A near-miss worth recording

The first measurement of mise's global env reported 75 keys including DOPPLER_TOKEN and AGE_PRIVATE_KEY — which would have "proved" mise was already serving your secrets. It was wrong: mise env echoes the ambient environment, and those values were inherited from fnox. Sanitised under env -i: 0 of 4. The first control arm was itself broken, because command -v mise resolves to the shell function rather than the binary. Two layers of probe error, caught before it became a finding.

And who manages the fragment itself

mise manages dotfiles — natively, and well

mise bootstrap dotfiles is a full dotfile manager driven by a [dotfiles] config section, and it is step 3 of mise bootstrap. So the replacement fragment needs no chezmoi, which matches your earlier ruling that the CLI shouldn't.

CapabilityWhat it gives you here
mode = "symlink-each" Walks a source directory and symlinks each file individually, with exclude globs. Exactly right for ~/.zshrc.d/ — repo-managed fragments and any unmanaged ones coexist, rather than the repo owning the whole directory.
status --json --missing Exits 1 when anything is missing, differs, or its source is gone. That is a drift detector with a machine-readable output, for free — one of the seams I listed as unowned is natively covered for dotfiles.
block / line edits Manages a marker-delimited block, or ensures a single exact line, inside a file mise does not own. So the eval "$(…)" line can be managed inside ~/.zshrc without the repo taking over that file.
apply --dry-run · unapply Reversible with a preview. unapply deliberately refuses to remove modified or ambiguous files without --force, so it will not silently discard a hand-edit.
add <target> Seeds the source from the live target, so adopting the existing file is one command rather than a copy-and-hope.
How I nearly told you this didn't exist

My first probe grepped mise --help and the local docs cache, found bootstrap/link/sync and two irrelevant "dotfile" mentions, and concluded there was no such feature. Both control arms passed — install → 20 hits, tasks → 187 — so the probes were working. They were simply aimed at the wrong surface: top-level help does not list subcommands, and the docs cache is stale. A control arm proves your probe can see; it says nothing about whether you pointed it at the right thing.

What I would do

Recommendation

Take A first, then B — and manage the file with [dotfiles]. Relocate fnox activate zsh into a repo-owned ~/.zshrc.d/ fragment today, declared in [dotfiles] with mode = "symlink-each", and gate it with mise bootstrap dotfiles status --missing. It retires mde, which is the goal you actually stated, changes nothing about how your machine behaves, and needs no chezmoi.

Then move to B once a shell profile has been derived rather than guessed. B is the only option where scoping genuinely works and fails closed, and the only one with no prompt hook at all — but it needs a subset list you do not have yet, and the last time a credential's consumer was assumed instead of measured, the assumption was wrong.

Before B ships, one thing must be measured

Which secrets the shell actually needs. reconcile's code-scan is exactly that measurement, which is an argument for building it before the scoping decision rather than after.
