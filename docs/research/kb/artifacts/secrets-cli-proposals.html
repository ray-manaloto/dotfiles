Re-derived, and it holds

The fnox fail-open figure arrived through a handoff and was the one cell nobody had measured. It has now been run here on 1.32.0 with both arms: the control (no profile) puts 50 secrets in the child at rc=0, and a nonexistent profile puts the same 50 in at rc=0 with zero stderr. The claim stands. The count was 49 in the handoff and is 50 today.

The correction that matters more: this defect is neutralised by your own ruling. Fail-open on a profile can only bite something that uses profiles, and you decided agents hold all 50 regardless. The strongest charge against fnox is one whose blast radius you have already accepted.

What I got wrong about fnox

fnox supports 23 providers — including infisical, bitwarden-sm, doppler, 1password, vault, keychain, age and the three cloud KMS/SM families. It is, already, the multi-backend CRUD proxy this project set out to build. Version 1.32.0 shipped 2026-08-01, and the changelog shows active profile work.

Two things I attributed to it are not its: the churn of all sync ciphertexts on every add/remove is mde's _run_fnox_sync_age(), which leaves when mde does; and the config-regeneration wipe class was closed upstream in mde#82, which exonerated fnox. Swapping its Doppler provider for Infisical is a config change, not a migration.

New constraint · changes the answer

Every consumer is a mise project

That is not just a distribution detail. mise 2026.8.1 already does most of this natively, which means the tool-builtins gate applies before any of the proposals below.

mise reads sops natively [env] _.file = ".env.json" — age is the only supported backend; formats are .env.json, .env.yaml, .env.toml. Key resolution order is documented: MISE_SOPS_AGE_KEY → ..._FILE → SOPS_AGE_KEY_FILE → SOPS_AGE_KEY → ~/.config/mise/age.txt.
mise has built-in age mise set --age-encrypt --prompt DB_PASSWORD stores ciphertext inline in mise.toml. No age CLI required. Defaults to your existing SSH key.
--age-recipient is repeatable Plus --age-ssh-recipient and --age-key-file. This is precisely the multi-recipient recovery primitive that has to exist before the first secret is encrypted — available natively, today.
Redaction is native _.file = { path = ".env.json", redact = true }, mise env --redacted. Direct-age values are always redacted. Partially answers the transcript-leak concern in #474.
fnox is NOT a mise feature Same author, but mise's docs are explicit: "There is no direct integration between fnox and mise — you configure fnox independently, and it sets environment variables that mise picks up like any other variables in your shell." It is recommended for team environments. You are one person.
Both paths are experimental mise's docs carry an explicit warning on each: "Behavior may change in future releases." That is a real cost, not a footnote.
What this does to the build

Per-project injection, encryption, multi-recipient recovery and redaction are all already native. And because mise config is per-directory, scoping is structural rather than a flag a call site can forget — which is the open question in #492, answered for free. What mise does not give you is cloud durability beyond a git remote, cross-project CRUD, rotation across many projects, or the agent-scoping surface.

Five options

The proposals

Not a sequence and not ranked by effort — each is a different bet about which component is the weak one. The verdict chips are judgments, and the reasoning behind each is stated so you can reject it.

Lean on mise, build only the gap

Smallest real build
Components out
fnox, the mde shell fragment, most of the planned CLI.
Components in
mise's native sops/age env loading in each consuming project, plus a thin CRUD tool for origination and a cloud store for durability.
Why
Injection, encryption, multi-recipient recovery, redaction and directory-scoping are already native and free. Writing any of that ourselves is exactly what the tool-builtins rule forbids, and this repo's standing preference is mise wherever mise has the feature.
What breaks
Both mise features are experimental. Shell-wide availability becomes per-project, so anything relying on all 50 everywhere changes shape. Cloud durability still has to come from somewhere.

Cost: lowest build, highest dependence on an experimental feature.

Move to Infisical

Strongest fit
Components out
fnox, Doppler, the mde shell fragment, the age cache.
Components in
infisical CLI + Infisical cloud. The CLI you build wraps it; the plugin wraps agent-proxy.
Why
It already ships the end state you described — agent credential scoping and a Claude Code plugin marketplace — so most of the build becomes adoption. Refuses on unknown scope. Has an offline cache.
What breaks
No documented shell-activate, so today's every-shell behaviour has no direct equivalent. Rotation, versioning and audit are paid. The 5-identity cap may bind sooner than it looks.

Cost: full migration of 50 secrets + the durable copy.

Drop fnox, keep Doppler

Lowest risk
Components out
fnox, the age cache, the mde shell fragment.
Components in
Your CLI wrapping doppler directly. Keychain keeps the bootstrap token.
Why
Every defect measured this session belongs to fnox, not Doppler. Doppler already satisfies free + cloud + durable, and doppler run -- is the same injection shape everything else uses.
What breaks
Loses fnox activate; the shell-wide equivalent is a download piped into eval, which is exactly the shape that puts values on stdout. Loses the offline cache.

Cost: no data migration. Rewrites the shell integration.

SOPS + age

Viable, narrow
Components out
fnox, Doppler, the keychain token.
Components in
sops + age + a private git repo as the cloud.
Why
The only option with runtime-proven refusal on all six arms. Zero vendor. Rotation is O(recipients) not O(secrets) — much cheaper than churning 49 ciphertexts per change.
What breaks
No interactive-shell injection exists at all, so it cannot reproduce current behaviour. A second recipient must be created before the first secret is encrypted, or the durability requirement is not met.

Cost: full migration + a key-custody decision first.

Keep fnox, swap its provider

Least work, most reuse
Components out
The Doppler provider, if you want off it. The mde shell fragment either way.
Components in
[providers] infisical = { type = "infisical", project_id = "…", environment = "dev" } — a config change, not a migration.
Why
fnox already is the multi-backend CRUD proxy, across 23 providers, current as of two days ago, by mise's author. Its one confirmed defect only bites profiles, which your ruling means nobody uses. Two other charges against it were mde's, not its.
What breaks
Nothing structural. You still own origination and the plugin, and you still need a shell-activate story once the mde fragment goes. Writes through the Infisical provider go via infisical secrets set, not fnox.

Cost: a config edit plus the origination layer.

Four lanes, four answers

How a credential gets resolved

The lanes are where the proposals actually differ. Note that today's second and fourth lanes are served by two unrelated mechanisms that nothing keeps in sync.

Lane Today Infisical Doppler-direct mise + age / sops
Interactive shell chpwd/precmd hooks export all 50. No documented equivalent — open question. doppler secrets download → eval. Needs verifying; leaks to stdout. Native, per-project mise activate already loads [env] per directory. Not shell-wide — scoped, which is arguably the better property.
Per-command fnox exec --, fails open on a bad profile. infisical run --, refuses. doppler run --. sops exec-env, refuses.
Devcontainer Separate lane: doppler download to an env file. Never touches fnox. Same CLI as the host — the two lanes collapse into one. Unchanged, and now the same tool as the host. Repo is already mounted; needs the key inside the container — one env var, MISE_SOPS_AGE_KEY.
AI agent Inherits all 50 from the parent shell. Accepted by decision. agent-proxy run -- claude scrubs and brokers. Knows ~/.claude by name. Inherits, or you build the scrubbing yourself. Inherits whatever the project scopes — which is a subset, not 50.
The tension this surfaces

You ruled an hour ago that agents keep all 50 and confinement is dead. Infisical's agent-proxy, Bitwarden's agent-access, and a live July incident where an AI tool hoovered whole repos including SSH keys are three independent signals pointing the other way — all from the last month. That does not make the ruling wrong; it does mean the market is building the thing we decided not to need, and it is worth deciding again on purpose rather than by omission.

Unresolved

What still has to be decided

Each carries a recommended default, so silence resolves to something stated rather than something accidental.

What justifies the CLI at all now?
The spec calls converting fnox's fail-open into a refusal "the CLI's whole job" (secrets-takeover.md:528-530). With no profile in play nobody passes -P, so that never fires — and every candidate backend refuses natively anyway. Recommended default: the CLI's justification becomes CRUD ownership plus the plugin surface, and the refusal clause is struck from the spec rather than quietly inherited.
Does the agent-proxy finding reopen the all-50 ruling?
Confinement was ruled dead when the only available mechanism was fnox profiles, which cannot un-inject what the shell already exported. A wire-level broker is a different mechanism with a different cost. Recommended default: the ruling stands for the shell, but agent-proxy is evaluated on its own merits rather than being ruled out by inheritance.
#496 — wrap or reimplement?
The ticket asks about resolution, and resolution was never the problem — fnox activate works. What mde owns is origination: the config writer, the CRUD verbs, the shell fragment. Recommended default: rewrite #496 to ask "which tool do we wrap, and who owns origination", then answer it with whichever backend wins.
#497 — which repo?
Own repo, python/ under dotfiles, or the shared uv git-dep shape kb_setup.currency already proves in this org. Recommended default: defer — it is a cheap later refactor, and the ticket itself says it may be a follow-on.
Re-derive the fnox fail-open number before it decides anything
It is inherited, not measured here, and it is load-bearing for the whole spec. Recommended default: run it with both arms — a known-good profile that succeeds, and the nonexistent one — and record the exit codes, before any proposal is chosen on its strength.
#470's arithmetic is stale
It argues the hole is 4 secrets "because env = "exec" keeps the other 45 out of the shell". That clause is retired; the number is 50, and the rest of the ticket's framing rests on the 4. Recommended default: correct the body before anyone builds against it.
