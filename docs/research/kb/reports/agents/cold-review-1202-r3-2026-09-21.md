## Q3 — can an array-shaped payload now get through?

**No.** Three independent arms:

1. **Matrix:** 21 array-shaped cells (`[]`, `[1,"ok"]`, and an array carrying own
   `verdict`/`findings` properties), **0 differ** between the SHAs. All PASS with
   "the check could not run".
2. **Mechanism:** the payload crosses a `JSON.stringify` → `JSON.parse` boundary
   (`register.ts:139`, and in production python's stdout). JSON array syntax has
   no slot for a named member, so `record.verdict` is `undefined` and C2 rejects.
   The array's own `verdict` property in my fixture was dropped by
   `JSON.stringify` exactly as the commit body claims.
3. **Prototype route closed:** `JSON.parse('{"__proto__":{"verdict":"ok",…}}')`
   creates an own `"__proto__"` data property; it does not mutate
   `Object.prototype`. That payload is in the matrix and PASSes on both SHAs.

The one behavioural difference the removal leaves is a rejection *reason*, not a
*result*: an array is now rejected by C2 rather than C1.

## Q4 — what can still escape `load_baseline`

`python/src/dotfiles_setup/claude_doctor.py:577-579`:

```python
    parsed = tomllib.loads(baseline_path.read_text())
except OSError, UnicodeDecodeError, tomllib.TOMLDecodeError:
```

Measured against the real function (`module: …/python/src/dotfiles_setup/claude_doctor.py`):

| Input | Result |
|---|---|
| missing file | HANDLED → `(True,'native',…)` |
| bad TOML | HANDLED |
| non-UTF-8 (`b"\xff"`) | HANDLED (new) |
| `doctor.toml` is a DIRECTORY | HANDLED (`IsADirectoryError` ⊂ `OSError`) |
| `a = [[[…2000 deep…]]]` | **ESCAPES `RecursionError`** |
| `project_root` containing `\0` | **ESCAPES `ValueError: embedded null byte`** |

Both escapes are *narrow*: `project_root` comes from `_project_root()`
(`python/src/dotfiles_setup/__init__.py:7-13`, a `Path(__file__)` walk), so the
NUL case is unreachable from the shipped CLI; the recursion case needs a
pathological tracked `doctor.toml`. Note `UnicodeDecodeError` and
`TOMLDecodeError` are **both** `ValueError` subclasses (verified
`issubclass(...) == True` for both), so `except (OSError, ValueError)` would
close the decode family with one name instead of enumerating two members of it.

**The locale question, armed and negative.** `Path.read_text()` with no
`encoding=` binds `locale.getpreferredencoding(False)`, not UTF-8 — so I checked
whether a non-UTF-8 locale could make a perfectly valid `doctor.toml` undecodable.
The repo's own `doctor.toml` is not ASCII (em dashes and `⚠️` on lines 1, 9, 17,
20, 31 of 14,142 bytes). Under a bare interpreter with `LC_ALL=C PYTHONUTF8=0`
the preferred encoding is `US-ASCII` and `read_text()` raises. **But through the
production entrypoint it does not:** across six arms (`LC_ALL=C`, `LC_ALL=POSIX`,
`LC_ALL=C PYTHONUTF8=0`, two ISO8859-1 arms, `LC_ALL=C.UTF-8`) `uv run --project
python` reported `utf8_mode=1`, `preferred=utf-8`, `read_text=OK`, and
`load_baseline` correctly returned `(False, 'npm-global')` every time — matching
the default control arm. So this is a latent shape issue, **not a live bug**.
`read_text(encoding="utf-8")`, or `tomllib.load(path.open("rb"))` which is
tomllib's documented interface precisely because TOML is defined as UTF-8, would
remove the dependence on an invariant `uv` happens to supply.

### F1 — the consequence that does bite, measured end to end

`claude_doctor_main(force_refresh=False, project_root=<tmp>)`, real module,
three arms:

| `doctor.toml` | rc | verdict | eligible | disabled | findings |
|---|---|---|---|---|---|
| `b"\xff"` (undecodable) | 0 | **ok** | False | **False** | **`[]`** |
| valid, `enabled = false` | 0 | unknown | False | True | the disabled advice |
| valid, `expected_install_method="npm-global"` | 1 | invalid | True | False | method mismatch |

Rows 2 and 3 are the control arms and they discriminate. Row 1 is the finding:
an undecodable baseline produces **a clean bill of health with no finding at
all**. Nothing in the emitted JSON says the file was not read; `baseline_path`
still points at it.

That is the exact failure direction this module's own `_DISABLED_ADVICE`
docstring says the design routes around — `claude_doctor.py:541-546`: *"a
disabled check reports nothing, which reads exactly like a healthy host"*.

Two concrete costs:

- **Off-switch discarded.** `enabled = false` in an undecodable file is ignored,
  silently. At base the same file raised out of `load_baseline`, the CLI died
  with no JSON, `JSON.parse` threw, and SessionStart said *"the check could not
  run. This is not a clean bill of health - it is an unanswered question."* Head
  removes that warning entirely (the `verdict === "ok"` early return).
- **Lockout with a repair that cannot work.** On an `npm-global` host whose
  `doctor.toml` sets `expected_install_method = "npm-global"`, an undecodable
  file reverts the expectation to `native` → `verdict: invalid` →
  `enforcement_eligible: true` → **DENY**, with a finding that blames the install
  method. The permitted in-session repair is editing `doctor.toml`
  (`register.ts:293-297`) — which cannot help, because the file will still fail
  to decode, and nothing tells the operator that is the real cause.

A one-line mitigation that keeps the chosen fail-safe default would be to return
a "baseline unreadable" signal and emit it as a finding, so the fallback stops
being silent.

### F5 — the new test cannot name its own arm

`tests/test_claude_doctor.py:767-777` asserts only the returned tuple. On this
host the sharp mutation (delete **only** `UnicodeDecodeError` from the tuple,
leaving `OSError` and `TOMLDecodeError`) turns the suite red — `1 failed, 74
passed`, `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff` — so the new
clause is load-bearing here. On a host whose preferred encoding is latin-1,
`b"\xff"` decodes to `"ÿ"` and the same assertion passes through the
`TOMLDecodeError` arm, silently.

**Control arm for the whole pytest rig:** the scratch copy under
`<scratch>/py/python/src/…` IS the module pytest imports — proven because
mutating it changed the result (75 passed → 1 failed, 74 passed).
