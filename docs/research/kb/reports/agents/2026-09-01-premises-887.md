## MISSING premises — facts the spec assumes without a row

Ordered by severity. M-1 through M-3 are, in my reading, ship-blockers: the

### M-1 — BLOCKER. INV-1/INV-2's drift check is the wrong SCOPE, and it defeats the spec's own target PR

`tests/test_lock_coverage.py` holds **13 tests across four different locks** —
root `mise.lock`, `.config/mise/mise.lock`, `mise-system.lock`,
`mise-runtime.lock`, plus `devcontainer-lock.json`:

```
test_system_lock_covers_merged_config          test_deep_currency_tools_have_one_declared_owner
test_runtime_lock_covers_runtime_config        test_shared_conf_d_lock_covers_shared_fragment
test_image_locks_carry_no_provenance           test_devcontainer_lock_covers_features
test_root_lock_covers_host_config              test_root_lock_versions_match_pins
test_shared_lock_versions_match_pins           test_system_lock_versions_match_pins
test_runtime_lock_versions_match_pins          test_version_drift_gate_discriminates
test_version_drift_gate_skips_non_exact_pins
```

INV-1 runs the **whole file**. Only five of those are in the image-lock domain
this job fixes. On PR **#821** — open right now, `author=app/dotfiles-refresh-bot-org`,
`head=chore/lock-refresh`, `isCrossRepository=false`, exactly the target class —
the whole-file run fails on a ROOT-lock test:

```
FAILED tests/test_lock_coverage.py::test_root_lock_covers_host_config
  - AssertionError: stale mise.lock entries for removed tools: ['node']
1 failed, 2640 passed, 7 skipped, 11 deselected in 41.35s
```
(run 33493592619, job 99811112214)

Trace the spec through that PR: INV-1's check fails → job proceeds → regenerates
the image locks → INV-2 re-runs the same whole-file check → **it still fails**,
because the root-lock defect is precisely what INV-3 refuses to touch → INV-2
says "FAILS LOUDLY and pushes nothing". A correct regeneration is thrown away
and #821 stays deadlocked.

The spec is internally inconsistent here: §1 and INV-3 both name the specific
tests, and INV-1 then widens the gate to the file that contains their opposite.

Fix: pin INV-1/INV-2 to node IDs, not the file —
`::test_system_lock_versions_match_pins`, `::test_runtime_lock_versions_match_pins`,
`::test_system_lock_covers_merged_config`, `::test_runtime_lock_covers_runtime_config`,
`::test_image_locks_carry_no_provenance`. (Prefer explicit node IDs over `-k`:
`-k` is a substring matcher and would silently pick up a future test whose name
happens to contain the pattern.)

### M-2 — BLOCKER. `GITHUB_TOKEN` / `MISE_GITHUB_TOKEN` must be exported to the regen step; nothing else supplies them

The existing composite sets BOTH on every `mise lock` step
(`.github/actions/lock-refresh/action.yml:28-30` and `:34-36`) with an explicit
rationale at `:17-20`:

> "…so `mise lock`'s GitHub-backed resolutions are not rate-limited (the
> convergence loop exists because anonymous quota exhausts mid-run)."

`mise run lock-image` does **not** replace that. `image_lock.run_lock_passes`
builds its child env as `{**os.environ, "MISE_ENV": ..., "MISE_TRUSTED_CONFIG_PATHS": ...}`
— it inherits, it never injects a token. Control-armed:
`grep -rn 'GITHUB_TOKEN\|MISE_GITHUB_TOKEN' python/src/dotfiles_setup/` returns
hits in `renovate_dryrun.py`, `process_env.py` and `skillopt_provenance.py` and
**zero** in `image_lock.py` or `lock_refresh.py`.

Anonymous, the five-pass loop is expected to exhaust quota and raise
`ImageLockError("mise lock did not converge in 5 pass(es)")` — a loud failure,
but a failure. The new job MUST carry
`GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` and
`MISE_GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` on the regen step.

Corollary, answering the lead's question directly: **`MISE_TRUSTED_CONFIG_PATHS`
is NOT a job precondition** — `image_lock.py` sets it internally on the stage
dir. The spec was right to not worry about it; it was wrong to not worry about
the token.

### M-3 — BLOCKER. There are TWO ungated jobs in this file, not one

INV-7 names only `lock-refresh`. `refresh.yml:155` also defines
**`tool-currency`**, equally ungated, and it is not read-only: it runs

Two further details INV-7 does not carry:

  edits (an `if:` on each existing job), so §2's file list under-describes the

### M-4 — MAJOR. Commit attribution vs the repo ruleset; and the `GIT_CONFIG_*` block does NOT cover identity

`gh api repos/ray-manaloto/dotfiles/rulesets/19868073` → the `pull_request` rule

INV-8 says the `GIT_CONFIG_COUNT`/`KEY_0`/`VALUE_0` block is "per-workflow and

Graded MAJOR rather than BLOCKER because I did not observe the ruleset

### M-5 — MAJOR. Fork PRs and Dependabot PRs both break the token mint

Two distinct platform facts, neither in the spec:

1. **Forks.** `secrets.*` are unavailable to `pull_request` runs whose head is a
   fork, so `actions/create-github-app-token` would fail outright. Verified the
   feature is nonetheless viable today: both live bot PRs are same-repo —
   `gh pr view 899/821 --json isCrossRepository` → `false` for both. But the job
   needs a guard, or it red-Xs every fork PR.
2. **Dependabot.** `.github/dependabot.yml` exists (`package-ecosystem: "pip"`,
   `directory: "/python"`). Dependabot-triggered `pull_request` runs read the
   **Dependabot secrets store**, not Actions secrets, so `secrets.REFRESH_APP_ID`
   and `secrets.REFRESH_APP_PRIVATE_KEY` resolve empty there as well. INV-5's
   "bot-authored head branches" is written as if all bots are equivalent; the
   predicate must exclude `dependabot[bot]` explicitly.

### M-6 — MAJOR. INV-5 and INV-6 contradict each other, and the wrong reading kills the feature

INV-5 wants an **inclusion** predicate ("restrict to bot-authored head
branches"). The PR class #887 exists for is Renovate: `author=app/renovate`,
`actor=renovate[bot]`, branch `renovate/all`. INV-6 then says "the correct
spelling is `dotfiles-refresh-bot-org[bot]`". If a lane reads INV-6 as naming
the inclusion predicate, the job **never runs on a Renovate PR** — a silent
no-op on the primary target.

A1's measurement is of the actor on the run *our own push* triggers; that is a
**loop-guard EXCLUSION** value, the same shape as `autofix.yml:41`'s three-way
exclusion list, not an inclusion filter. The only coherent reading is exclusion,
and the spec must say so in words — the two invariants currently name predicates
over different values without saying they are different predicates.

### M-8 — MODERATE. `autofix` already commits back to refresh-bot PR branches — this would be a second writer

### M-9 — MODERATE. Renovate will NOT clobber the commit — verified from source — but it WILL freeze the PR

Read `renovatebot/renovate@main`:

- `lib/config/options/index.ts:2121-2132` — `rebaseWhen` default is `'auto'`.
  `renovate.json` sets no override (`grep -n 'rebase' renovate.json` → no
  `rebaseWhen` key), and neither does the inherited preset: fetched
  `jdx/renovate-config@main/default.json` (HTTP 200) and it carries
  `"automerge": true` at top level with **no** `rebaseWhen` key. So the
  default applies, and `automerge` is true from two independent directions.
- `lib/workers/repository/update/branch/reuse.ts`, `determineRebaseWhenValue` —
  `'auto'` is converted to `'behind-base-branch'` when `automerge === true`,
  which this repo sets for `matchUpdateTypes: [minor, patch, digest]`
  (`renovate.json:32-41`, with `platformAutomerge: true`).
- Same file, `shouldReuseExistingBranch` — under `behind-base-branch`, a branch
  that is behind base AND `isBranchModified` returns
  `{ reuseExistingBranch: true, isModified: true }` and **returns without
  rebasing**: `logger.debug('Cannot rebase branch as it has been modified')`.

So our commit survives; Renovate does not force-push over it. The cost the spec
should state: once the branch is `isModified`, Renovate stops updating that PR
at all. This repo runs `extends: ["github>jdx/renovate-config", "group:all"]` —
ONE grouped "Update all dependencies" PR — so if auto-merge is blocked for any
other reason, that PR is frozen with no further bumps until a human intervenes.
Acceptable, but it should be a stated consequence, not an unexamined one.

## Q3 — with `gitIgnoredAuthors`, your reading is CORRECT, and the cadence is measured

Trace, given `gitIgnoredAuthors` contains our push address:

1. `isBranchModified` → `includedAuthors` empty → **false** (`git/index.js:712-714`).
2. `determineRebaseWhenValue`: `automerge === true` → `rebaseWhen = "behind-base-branch"`
   (`reuse.js:76-79`).
3. `shouldReuseExistingBranch`: `rebaseWhen === "behind-base-branch"` (`:24`) →
   `isBranchBehindBase` (`:25`). If behind → `isBranchModified` now false → falls
   past L14 to `logger.debug("Branch is unmodified, so can be rebased"); return result;`
   (`:33-34`) with `reuseExistingBranch` still `false` from `:15`.
4. Renovate regenerates the branch from base and force-pushes. **Our lock commit
   is gone. The drift returns.**
5. The `synchronize` fires our job again → regenerate → push → goto 3.

So yes: adding `gitIgnoredAuthors` hands Renovate the permission to erase the
very commit the feature exists to make.

**Termination:** not guaranteed by construction. The rebase is gated on
`isBranchBehindBase`, so the loop is driven by main moving, and it ends only if
our CI wins the race to merge before the next rebase. The measured cadence is
bad for us: **30 force-pushes on `renovate/all` over ~3 days** (2026-08-29T21:02
→ 2026-09-01T17:38), i.e. roughly one every 30-90 minutes during active periods.
Meanwhile `.config/mise/conf.d/shared.toml` is on ci.yml's build path filter, so
a #899-shaped PR runs the FULL build chain (~10 min warm, up to ~2.5h on a cold
base). During a cold-base window we lose that race deterministically, and each
lost iteration burns a full image build.

Formally a livelock, not an infinite loop. Practically: do not do this.

## Q4 — exactly what would have to go in `gitIgnoredAuthors`

- **Both fields are compared.** `git/index.js:695-701` adds `author_email` (`%ae`)
  AND `committer_email` (`%ce`) to the same `committedAuthors` set, and every
  member must be excluded for the branch to read unmodified. Your reading of
  `3f5752c` is right: author `sortakool` / committer `github-actions[bot]` means
  a single entry would not have sufficed there.
- **A plain `git commit` in the job sets both to the same address.** Git takes
  author and committer from `user.email` unless `--author` or
  `GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_EMAIL` diverge them. So one pinned
  `git config user.email` → one entry suffices — *provided* the job uses plain
  `git commit` and nothing (an action like `peter-evans/create-pull-request`, or
  `autofix-ci/action`) rewrites either field. `3f5752c`'s split is what a
  third-party action does; that is the shape to avoid.
- **Matching is literal OR pattern** (`:712`: `ignoredAuthors.includes(...)` ||
  `matchRegexOrGlobList(...)`; the option is declared `patternMatch: true` at
  `config/options/index.js:1243-1249`). A convenience glob such as
  `*@users.noreply.github.com` would also un-protect **Ray's own** commits from
  being force-pushed away. Use the exact address if you use it at all.
- **Placement:** `stage: "repository"` (`:1248`) — top level of `renovate.json`,
  not inside a `packageRules` entry.

structural, not a gap in my search: the only regeneration hook is
`postUpgradeTasks`, and it is admin-gated by design.

## What this means for the spec

**I disagree with the lead's framing on one of the two points.**

- The spec's §2 "do not modify `renovate.json`" is, on this evidence,
  **CORRECT and should stay**. Adding `gitIgnoredAuthors` does not fix a problem
  that exists; it *creates* the clobber-loop of Q3 by removing the L14 protection

  never states the commit-identity requirement (round-1 M-4) — which, given Q2's
  refutation, is now the **only** remaining mechanism by which the outcome the
  lead feared could actually occur. Both belong in the spec as stated
  consequences.

1. `isBranchModified` false → `rebaseWhen` = `behind-base-branch` (L30) →
   branch behind base → past L14's guard to "Branch is unmodified, so can be
   rebased" (`reuse.js:33-34`) → force-push. Lock commit gone, drift back.
2. `synchronize` → our job → INV-1 fails → regen → push.
3. Our push touches `.devcontainer/mise-*.lock`, and **`.devcontainer/**` is on
   ci.yml's build path filter** (`ci.yml` `changes` job, `filters: build:
   - '.devcontainer/**'`) — so our own push triggers the FULL build chain, not
   just lint. ~10 min warm; up to ~2.5h on a cold base.
4. Meanwhile main moves → branch behind again → goto 1. Every rebase resets the
   checks, and `ci.yml`'s `cancel-in-progress` kills the in-flight run.

The merge requires "checks green AND no rebase since". That is unreachable
whenever the inter-rebase interval is shorter than a full green pipeline. Given a
measured 30-90 min rebase cadence against a build that can take hours cold,
**non-convergence is not an exotic corner — it is any period in which main is
active and the base cache is cold**, and each lost cycle burns a full image
build. Formally a livelock with unbounded expected time, not a convergent loop.

**Verdict on INV-10: delete it. Restore v1's "do not modify `renovate.json`".**

## Attack 2 — the identity question, and the answer inverts

The lead's worry ("adding `github-actions[bot]` to `gitIgnoredAuthors` would also

and the truth is worse than the worry.

  So there is no collision to avoid.
- **The address is ALREADY in `gitIgnoredAuthors`** via the preset (L27). So
  INV-8 and INV-10 are mutually defeating in a way neither invariant states: if
  the lane follows INV-8 and commits as
  `41898282+github-actions[bot]@users.noreply.github.com`, then
  `isBranchModified` is **already false today**, with no renovate.json change —
  Renovate is already free to rebase our commit away, and attack 1's clobber loop
  happens whether or not INV-10 lands. **INV-8, as written, is the invariant that
  breaks the feature.**

**Concrete recommendation — commit as the App's own bot identity:**

```
git config --global user.name  "dotfiles-refresh-bot-org[bot]"
git config --global user.email "298071151+dotfiles-refresh-bot-org[bot]@users.noreply.github.com"
```

The numeric id is measured, not guessed:
`gh api 'users/dotfiles-refresh-bot-org[bot]'` → `{"id":298071151,
"login":"dotfiles-refresh-bot-org[bot]","type":"Bot"}`. This identity is:

- **attributable** — a real GitHub `Bot` account in the `<id>+<login>@users.noreply.github.com`
  form, so A4's `require_extra_approval_for_unattributed_changes` is satisfied;
- **NOT in the preset's ignore list**, so the branch reads modified, the freeze
  holds, and #822's proven merge shape applies;
- **distinct from autofix's** and from `github-actions[bot]`;
- **consistent with the push actor** — the push uses this App's installation
  token, so the commit identity and A1's measured `github.actor`

Amend INV-8 to name this address, and drop INV-10.

## Attack 3 — INV-5's predicate, with the exact fields

The predicate matches #899 today. Measured from the API, with #821 as the control
arm that must NOT match:

```
$ gh api repos/ray-manaloto/dotfiles/pulls/899
head.ref              = "renovate/all"
head.repo.full_name   = "ray-manaloto/dotfiles"
head.repo.fork        = false
user.login            = "renovate[bot]"
base.repo.full_name   = "ray-manaloto/dotfiles"

$ gh api repos/ray-manaloto/dotfiles/pulls/821     # control arm
head.ref              = "chore/lock-refresh"       # fails the prefix
user.login            = "dotfiles-refresh-bot-org[bot]"
```

The probe discriminates: #899 satisfies every clause, #821 fails two of them.

**The exact expression** — and the field distinction between INV-5 and INV-6 is
the part worth stating explicitly, because they read over *different* values:

```yaml
if: >-
  github.event_name != 'pull_request' && false ||
  (startsWith(github.event.pull_request.head.ref, 'renovate/') &&
   github.event.pull_request.head.repo.full_name == github.repository &&
   github.event.pull_request.user.login == 'renovate[bot]' &&
   github.actor != 'dotfiles-refresh-bot-org[bot]')
```
(written plainly rather than as the one-liner above, this is four clauses:)

| Clause | Field | Why this field |
|---|---|---|
| INV-5 branch | `github.event.pull_request.head.ref` | the head branch name without `refs/heads/`. `github.head_ref` is the same value on `pull_request` events; prefer the payload path so the expression reads identically if the trigger set ever widens. |
| INV-5 fork | `github.event.pull_request.head.repo.full_name == github.repository` | the ONLY clause that excludes forks. `head.repo.fork` also exists (`false` on #899) but compares against upstream-ness, not against *this* repo; `full_name` is the direct question. |
| INV-5 author | `github.event.pull_request.user.login == 'renovate[bot]'` | the PR's **author**, which is stable across every event on the PR. |
| INV-6 loop guard | `github.actor != 'dotfiles-refresh-bot-org[bot]'` | the actor of **this event**. On the `synchronize` our own push triggers, `github.actor` becomes the App bot while `user.login` stays `renovate[bot]` — which is exactly why these must be two different fields and why INV-6's value is not INV-5's. |

Do NOT use `github.actor` for the INV-5 author clause: on the very
`synchronize` this job cares about, `github.actor` is not `renovate[bot]`.
