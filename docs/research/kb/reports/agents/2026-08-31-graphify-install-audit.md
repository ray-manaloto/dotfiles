# Graphify Install Audit (read-only)

Started 2026-08-31.

## Step 0: locate graphify package

## Findings (verbatim, in order derived)

### 1. `_copy_skill_file` (install.py:172-239) writes `.graphify_version` for EVERY platform that goes through it
Read directly from installed package source
`python/.venv/lib/python3.14/site-packages/graphify/install.py:239`:
`(skill_dst.parent / ".graphify_version").write_text(__version__, encoding="utf-8")`
runs unconditionally at the end of `_copy_skill_file`, which every monolith/progressive platform funnels through. So a REAL install always writes the stamp — its absence is not automatically "some platforms don't get one."

### 2. `.claude/skills/graphify/.graphify_version` is DELIBERATELY gitignored, and genuinely absent from disk
`.gitignore:68` — `.claude/skills/graphify/.graphify_version` — comment at `.gitignore:67`: "graphify per-install state (generated by `graphify install`/runs; not source)".
Control arm: `find .claude/skills/graphify -maxdepth 1 -name ".graphify_version"` → empty; `git status --ignored` on that path shows nothing (file doesn't exist even untracked). So this is NOT evidence of an incomplete install — it's evidence the file was intentionally excluded from source control and never regenerated locally (consistent with `do-not.md` #8: this repo does not run `graphify install` against itself; the SKILL.md content was placed here through a controlled/manual process, not by executing the installer in-repo).

### 3. `.claude/skills/graphify/SKILL.md` (41,300 B) is essentially RAW installer output, not truncated/custom
`diff .claude/skills/graphify/SKILL.md python/.venv/.../graphify/skill.md` → exactly ONE line different (`raise SystemExit(1)` inserted), which matches commit 9502422's own message: "graphify SKILL.md: raise SystemExit(1) when to_json refuses the shrink...". So this file = packaged `skill.md` + one deliberate, documented patch. `references/` dir is BYTE-IDENTICAL to the packaged `graphify/skills/claude/references/` bundle (`diff -rq` → no output). CORRECT SHAPE for the "claude" platform's install output.

### 4. `.agents/skills/graphify/SKILL.md` (1,043 B) is NOT graphify output at all — it is 100% hand-authored
Read `git show 9502422 -- .agents/skills/graphify/SKILL.md`: the file was added FROM SCRATCH (new file 100644) in the same PR #748 that upgraded graphify to 0.9.42, alongside a hand-written `.graphify_version` containing "0.9.42" (later bumped, currently on-disk 0.9.53). Its content is dotfiles-specific prose ("Use the repository's reviewed tasks. Do not invoke a global Graphify binary...") that directly matches the doctrine in `.claude/rules/graphify-first.md` and points at `.claude/skills/graphify/references/`. `git log --follow` shows exactly ONE commit ever touched this file — it was never produced by a real `graphify agents install` run.

The REAL "agents" platform installer output would be ~41,000 B: `python/.venv/.../graphify/skill-agents.md` is 41,000 B, and `_PLATFORM_CONFIG["agents"]` (install.py:456-464) declares `skill_refs: "agents"`, meaning a genuine install ALSO writes a `references/` sidecar — `python/.venv/.../graphify/skills/agents/references/` exists on disk (10 entries). None of that landed here. So the 40x size gap is NOT a truncation of a real install — it is two unrelated things: a deliberate 1KB redirect stub vs. what an actual `graphify agents install` would produce (41KB + references/).

Note also: `.agents/skills/graphify/SKILL.md` is the shared destination for MULTIPLE platforms per `_platform_skill_destination`/`_PLATFORM_CONFIG` — "agents" (project+global), "amp" (project scope), "antigravity"/"antigravity-windows" (project scope only). This repo has Antigravity adopted (`.claude/CLAUDE.md` "antigravity@antigravity-for-claude-code"). A real `graphify antigravity install --project` would ALSO target this same path and would write claude's full skill.md bundle (41KB), not the 1KB stub — so the stub is not even platform-disambiguated; it's a single manually-placed placeholder serving as a catch-all for whichever of these three platforms reads `.agents/skills/graphify/`.

### 5. `.codex/` is GITIGNORED — brief's claim it is untracked-and-not-ignored is WRONG
`.gitignore:54` — `.codex/*` — comment `.gitignore:53`: "Codex CLI temporary state".
Control arm: `git check-ignore -v .codex/config.toml` → matches `.gitignore:54`; `git check-ignore -v AGENTS.md` (known-tracked file) → rc=1, no match. Probe discriminates correctly. `git status --short --ignored .codex` → `!! .codex/`.
So `.codex/` is NOT in the "neither tracked nor ignored" limbo state the brief described — it IS correctly ignored.

### 6. `.codex/` content is NOT graphify's output — it is the Codex CLI's own project-local runtime config
Content inspected: `.codex/config.toml` (shell_environment_policy + CLAUDE_*/OTEL_* env passthrough), `.codex/hooks.json` (mirrors `.claude/settings.json`'s PreToolUse hooks — pretooluse-guard.sh, graphify-hook-guard.sh), `.codex/agents/{adversarial-critic,claude-code-expert,dockerfile-reviewer,staleness-auditor}.toml` (mirrors `.claude/agents/*.md` subagent defs). This is the Codex CLI mirroring Claude Code's own project config for its own use, unrelated to graphify.
Per `_PLATFORM_CONFIG["codex"]` (install.py:344-349), a REAL `graphify codex install` writes to `.codex/skills/graphify/SKILL.md` + a `references/` sidecar (`skill_refs: "codex"`, packaged bundle at `graphify/skills/codex/references/`). `find .codex -maxdepth 2 -type d` shows only `.codex/agents` — **no `.codex/skills/` directory exists at all.** So no graphify codex install has EVER happened in this repo, tracked or otherwise. This is a real gap if a codex-platform graphify skill was ever wanted, but it is not "graphify wrote something wrong" — graphify wrote nothing here.

### 7. Neither on-disk `.graphify_version` stamp is read by this repo's own tooling
`grep -rn "graphify_version" python/src/dotfiles_setup/*.py python/.venv/.../kb_setup/graphify_health.py` → zero hits in both. The "version drift" check `graphify-first.md` describes is implemented in `python/src/dotfiles_setup/graphify.py:81-83` via `importlib.metadata.version("graphifyy")` — i.e. it reads the INSTALLED PACKAGE version in the venv, not either on-disk stamp file. So the presence/absence of `.graphify_version` under `.claude/` or `.agents/` has ZERO effect on this repo's own graphify-health/version-drift gate. It is purely a per-platform installer bookkeeping file with no consumer in this repo.

## Ranked fix list

1. **[Documentation gap, not a defect]** `.agents/skills/graphify/SKILL.md` and its `.graphify_version` are a deliberate hand-authored stub but nothing says so — no comment in the file, no note in `.claude/CLAUDE.md`'s graphify section (which only documents the `.claude/` placement and the "why not run install" rationale). A one-line comment/frontmatter note ("hand-authored redirect stub; NOT graphify installer output — see #748") would prevent this exact audit from recurring. Low effort, real value: closes the confusion that triggered this whole audit.
2. **[Untidy, not broken]** The `.agents/skills/graphify/.graphify_version` value (0.9.53) is unread by anything in this repo (confirmed by grep — zero consumers) and has no source of truth keeping it in sync with the venv-pinned version (0.9.42 per graphify-first.md's stated pin, vs 0.9.53 currently on disk in the venv — these two numbers already disagree, which is a live inconsistency, though inert since nothing reads the stamp). Either wire it to something or delete it to stop it looking like signal.
3. **[Optional, no evidence it's wanted]** No `.codex/skills/graphify/` exists — if a Codex-CLI-native graphify skill is desired (parallel to the deliberate `.claude/` and `.agents/` placements), it does not exist yet. This audit found no requirement anywhere that it should; flagging only because the brief's framing implied `.codex/` was graphify-related. It is not, so there is nothing to "fix" for `.codex/` beyond correcting the belief that it's an incomplete graphify install.
4. **[Correction, not a repo action]** The architect's brief asserted `.codex/` is "UNTRACKED and NOT gitignored" — this is factually wrong (`.gitignore:54` covers it, `git check-ignore` confirms, control-armed against a known-tracked file). No repo change needed; just don't act on that premise.

## What I could not determine
- Whether `.claude/skills/graphify/SKILL.md`'s content was placed by manually copying installer output into the repo, vs. some other mechanism (e.g. `graphify install` run once outside the repo then files copied in). The 1-line diff from the packaged `skill.md` and the exact `references/` match are consistent with either; I found no commit message stating the mechanism explicitly beyond "Upgrade Graphify to 0.9.42" / "feat/graphify full native setup (#344)".
- Why `.agents/skills/graphify/.graphify_version` was set to a version number at all if nothing reads it — no comment in commit 9502422 explains the intent behind stamping it.
- Whether Ray/the operator INTENDED `.agents/skills/graphify/` to one day receive the real installer output (41KB + references) for amp/antigravity/agents-spec consumers, or intended it to stay a redirect stub permanently. This is a product decision, not something derivable from the code.
