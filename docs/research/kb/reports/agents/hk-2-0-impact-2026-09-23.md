# hk 2.0 impact on dotfiles + knowledge-base hk configs (#1306)

Research ticket #1306, wayfinder map #1293. Read-only lane: no hk 2.x binary was
installed or run, no pin was changed, `mise run fmt` was not run. Every behavioural
claim below is sourced from hk's CHANGELOG, release notes, merged PRs, or source at
the release tags `v1.57.0` (pinned) and `v2.0.1` (latest). Raw fetches are under
`.agent/kb/raw/` (machine-local); the load-bearing excerpts are quoted here.

## Question

What does hk 2.0 break or change for `hk.pkl`, `hk-common.pkl`, `hk-image.pkl`,
the knowledge-base `hk.pkl`, the `mise run lint` / `mise run fmt` wrappers
(`python/src/dotfiles_setup/lint.py`), and the "git add BEFORE `mise run fmt`"
doctrine (`AGENTS.md:152-155`)? Which features we rely on were removed or renamed,
and what is newly native that could retire custom code?

## Answer in one paragraph

Five things must change before hk 2.x can land. (1) The user-global
`~/.config/mise/config.toml:48` still exports `HK_PKL_BACKEND = "pkl"`, and hk 2
refuses to load any config when that variable is anything but `pklr`, so every
host-side lint breaks while CI stays green. (2) The knowledge-base uses the removed
`Builtins.gitleaks_staged` (`knowledge-base/hk.pkl:346`). (3) An undocumented
change: the v2 `editorconfig_checker` builtin now runs `editorconfig-checker`
instead of `ec`, so it hits ENOENT against our pinned editorconfig-checker 3.11.3.
This is already visible in #1090's CI log, and #1089 (editorconfig-checker v4) fails
the same way in reverse, so the two PRs must land together or the builtin must be
told `version = "3"`. (4) Renovate cannot deliver #1090 green, because the pkl URL
sites are not grouped with `shared.toml` (`renovate.json` `packageRules[0]`). (5) The
fmt doctrine's stated rationale becomes false. hk 2 stages fixes **only** in
`pre-commit`, so `mise run fmt` (`hk fix`) no longer touches the index at all. Our
configs use no other removed interface (`.hkrc`, `hk.toml`, `UserConfig`, `Regex`,
`hk generate`, the other variant builtins), and each of those greps is control-armed.
The top-level `steps` feature is opt-in and not materialised for our hook-only
configs. `depends`, `exclusive`, `fail_fast`, `stash`, `min_hk_version` and every
`HK_*` variable we set keep their v1 schema. `lint.py` must stay, because hk 2 still
has no native timeout. The one real retire candidate predates 2.0: upstream fixed
the `depends` + `fail_fast = false` deadlock in 1.53.0 (jdx/hk#1099), which meets the
retire condition written into `hk.pkl:596-597` for `no_hk_depends`. The KB records
Ray's decision to keep the ban anyway.

## A. REQUIRED changes (blocking)

### R1. Remove `HK_PKL_BACKEND = "pkl"` from the user-global mise config (operator; outside the repo)

- **Where:** `~/.config/mise/config.toml:48`:
  `HK_PKL_BACKEND = "pkl"  # "pkl" (not pklr) required for import/spread in hk-common.pkl`.
  Re-derived 2026-09-23. Earlier reports cite `:82`, so the line has moved; the
  inherited line number is superseded.
- **Why it breaks:** hk v2.0.1 `src/config.rs:26-32`, the first statement of
  `Config::load`:
  ```rust
  if let Some(backend) = std::env::var_os("HK_PKL_BACKEND") && backend != "pklr" {
      bail!("HK_PKL_BACKEND no longer selects an evaluator in hk v2; remove it or set it to `pklr`. ...");
  }
  ```
  Release notes and migration guide agree: "`HK_PKL_BACKEND=pkl` -> remove it; `pklr`
  remains an accepted no-op" (jdx/hk#1257; `docs/migration-v2.md`).
- **Blast radius:** every host `mise run lint` / `fmt` / `pre-commit` / git hook,
  because mise re-injects user-global env into every task. The repo side is already
  clean: `mise.toml:202` and `.devcontainer/mise-system.toml:377` record the drop,
  and no CI workflow sets it. CI therefore stays green while the host breaks, which
  is a silent host/CI split.
- **Fix:** delete the line, or set it to `"pklr"`. The inline comment's premise has
  been retired since hk 1.49 (#160 T12). This is a user-level file, so it is an
  operator action.

### R2. KB: replace the removed `Builtins.gitleaks_staged`

- **Where:** `knowledge-base/hk.pkl:346` `local gitleaksStaged: Step = Builtins.gitleaks_staged`,
  used at `:598-600` in the `pre-commit` hook.
- **Evidence:** the builtin file set diff v1.57.0 -> v2.0.1 removes exactly
  `check_byte_order_marker`, `fix_byte_order_marker`, `gitleaks_staged`,
  `knip_strict`, `pinact_update_v3`, `pinact_v3`. That matches the jdx/hk#1253 table.
  `pkl/builtins/gitleaks_staged.pkl` returns HTTP 404 at `v2.0.1` and 200 at `v1.57.0`.
- **Replacement:** `local gitleaksStaged: Step = (Builtins.gitleaks) { scan = "staged" }`
  (`docs/migration-v2.md` "Builtins"). **The argv is byte-identical.** v2.0.1
  `pkl/builtins/gitleaks.pkl` with `scan == "staged"` emits
  `gitleaks git --pre-commit --redact --staged --verbose --no-banner`, the same list
  as v1.57.0 `pkl/builtins/gitleaks_staged.pkl:13-22`. v2 also carries the four
  staged-scope tests the KB comment (`:319-329`) says it adopted, so the KB's
  `hk test` count claim (`:332-335`, "46 -> 51") must be re-measured, not assumed.
- **Also update:** the KB comment block at `:308-345` that names the builtin, and
  the "FOURTH VERSION TOKEN" note at `:337-340` (still true: move all four tokens on
  lines 1 and 6, plus `mise.toml:46`).

### R3. `editorconfig_checker` now invokes `editorconfig-checker`, not `ec` (undocumented in the release notes)

- **Evidence (package):** v1.57.0 `pkl/builtins/editorconfig-checker.pkl` has
  `argv = List("ec", "{{files}}")`. v2.0.1 has
  `hidden version: "3" | "4" = "4"` and
  `argv = List(if (version == "3") "ec" else "editorconfig-checker", "{{files}}")`.
  The change came in jdx/hk#1253 (its file list includes
  `pkl/builtins/editorconfig-checker.pkl`), but the v2.0.0 release-note migration
  table does not mention it. The release notes are incomplete here.
- **Evidence (live):** #1090 lint job 107041184992:
  `✗ editorconfig-checker – ERROR ... Caused by: No such file or directory (os error 2)`.
  The mirror image is Renovate #1089 (editorconfig-checker v4, `mise.toml` +
  `mise.lock` only), whose lint job 107041147544 fails the same step with the same
  ENOENT: hk 1.57's builtin calls `ec`, and editorconfig-checker v4.0.0 "rename[d]
  ec to editorconfig-checker" (its v4.0.0 release notes).
- **Our pin:** `mise.toml:15` `editorconfig-checker = "3.11.3" # provides ec`.
  The reference is at `hk.pkl:42` `["editorconfig-checker"] = Builtins.editorconfig_checker`.
- **Fix, one of:** (a) land hk 2 and editorconfig-checker 4.x **in the same change**.
  This needs a Renovate grouping or a manual combined PR, and it must first review
  v4's other breaks: `.ecrc` no longer discovered (no `.ecrc` is tracked, so this is
  moot), and latin1 no longer accepted as utf-8. Or (b) keep ec 3.x and write
  `["editorconfig-checker"] = (Builtins.editorconfig_checker) { version = "3" }`.
  Option (a) keeps us native; option (b) decouples the two bumps.
- Side observation, not v2-specific: no `.editorconfig` is tracked at the repo root
  (`ls` -> absent; control `git ls-files | grep -c '^hk.pkl$'` -> 1), so it is worth
  confirming what this step actually enforces.

### R5. Rewrite the fmt doctrine: its rationale is false under hk 2

- **Doctrine:** `AGENTS.md:152-155`: "Always `git add` BEFORE `mise run fmt` —
  `fix=true` can strand unstaged edits when new files are present."
- **Origin:** commit `0e218d78` (2026-04-07). It was written when the lint command was
  `hk run pre-commit --all --stash none` and the fix path was a pre-commit run with
  `fix=true` (original text: "`fix=true` + `--stash none` can strand unstaged edits
  when new files are present"). Today lint is the read-only `hk run check --all`
  (`lint.py:64-66`) and fmt is `hk fix` (`mise.toml:1287-1289`). hk.pkl gained a
  dedicated `fix` hook in #160 T12 (`hk.pkl:813-827`).
- **What changes in v2:** staging after fixes is resolved at
  v2.0.1 `src/hook.rs:1153-1157`:
  ```rust
  let should_stage = opts.should_stage().or(settings.stage).or(self.stage)
      .unwrap_or_else(|| self.name == "pre-commit");
  ```
  v1.57.0 `src/hook.rs:1118-1122` ends in `.unwrap_or(true)`. Our `fix` hook sets
  `fix = true` and no `stage` (`hk.pkl:822-827`; KB `hk.pkl:591-594`). So under
  1.57 `mise run fmt` **stages** the files its fixers touched, and under 2.x it
  **stages nothing**. This is jdx/hk#1256, "stage fixes by default only for
  `pre-commit` ... leave manual `hk fix` and other hooks unstaged unless staging is
  explicitly enabled". Release notes: "Scripts that relied on `hk fix` staging its
  changes should pass `--stage`."
- **Stash is unchanged for fmt:** the `fix` hook has no `stash`, so it resolves to
  `None` in both versions (v2.0.1 `hook.rs:655-670`; v1.57.0 `hook.rs:620-634`).
  File selection for bare `hk fix` is "Modified files: staged, unstaged, and
  untracked" (v2 `docs/hooks.md` "File selection"). New files are therefore already
  seen without `git add`.
- **Required edit (tool-currency rule 5: same change as the bump):** replace the
  rationale. Suggested text: "`mise run fmt` applies fixes and leaves them
  **unstaged** (hk 2 stages only in `pre-commit`); review with `git diff`, then
  `git add` explicit paths." "`git add` your own edits first" survives only as
  optional review hygiene (it separates your diff from the fixers' diff), not as a
  safety rule.
- **Nothing else in-repo relies on `hk fix` staging.** `git grep` for
  `hk fix|hk run fix|mise run fmt|HK_STAGE|hk.stage|--stage` across `.github`,
  `python/src`, `scripts`, `.devcontainer`, `mise.toml` and the pkl files finds only
  prose, `mise.toml:1289`, and the autofix workflow. The autofix workflow runs
  `hk run pre-commit --all --stash none` with `HK_FIX=1` (`autofix.yml:67-74`).
  `pre-commit` still stages by default in v2, and `autofix-ci/action` commits the
  worktree either way, so its behaviour is unchanged.

## C. Recommended (not strictly required)

1. **Raise `min_hk_version` to `"2.0.0"`** at `hk.pkl:19`, `hk-image.pkl:19` and KB
   `hk.pkl:9`. The package default is `"{{version | truncate(length=1)}}.0.0"`
   (`Config.pkl:13`), which renders to 2.0.0 in the v2 package. Our explicit
   `"1.49.0"` *weakens* that guard, and #1090's CI shows a 1.57 binary happily
   evaluating the v2 package. A stale 1.x binary on some machine would then misread
   v2 hook semantics (staging) without error.
2. **Prefer an hk release that bundles pklr >= 2.0.5**, or at minimum capture
   `hk check --plan --json` from 1.57 and from 2.x and require equal step and file
   sets. hk 2.0.1 bundles pklr 2.0.4 (`Cargo.toml:51`: `pklr = { version = "2.0.1", ...}`,
   lock bumped to 2.0.4 via jdx/hk#1381), but pklr 2.0.5 (2026-09-19) fixes "amend
   inherited entries of untyped mappings instead of replacing them" (jdx/pklr#189).
   Our configs use spreads (`...allSteps`, `...common.hygiene`) and typed mappings.
   KB `steps = (lintSteps) { ["gitleaks"] = ... }` amends a typed
   `Mapping<String, Step>`, so the untyped bug likely does not apply, but that is
   UNVERIFIED (see E).
3. **Sync stale prose in the same change:** the `autofix.yml:68-72` comment ("we
   have `pre-commit`, not `fix`") is false since #160 T12. The "hk 1.46 / v1.48"
   version claims in `lint.py:10-13` should cite 2.x. `.claude/rules/clean-git-state.md:24`
   ("New files must be `git add`-ed before hk runs, or hk won't check them") is
   already inaccurate at 1.57 for `hk run check --all` (untracked files are included
   when stash is `none`). The real reason to `git add` is CI parity (CI's checkout has
   no untracked files), not hk visibility.

## D. Newly native: candidates to retire custom code

1. **`no_hk_depends` (`hk.pkl:578-605`) and the #268 prose at `hk.pkl:66-81`:
   upstream fixed the deadlock in 1.53.0.** jdx/hk#1099, "fix(step): unblock
   dependents after failed dependency", merged 2026-07-22 and listed under 1.53.0
   (CHANGELOG line 408; the 1.53.0 header is line 399): "signal step dependencies
   after terminal failures when `fail_fast = false`". It was reported in
   jdx/hk discussion #1098 by `astei`, not by us, so `hk.pkl:81` "Not yet reported
   upstream" is also moot. The step's own retire condition (`hk.pkl:596-597`:
   "Retire this step ONLY when upstream releases a dependent on a failed dependency
   and a control-armed probe confirms it") is met on the upstream side. **The
   control-armed probe has not been run** (out of scope for a read-only lane). The KB
   records a standing decision to keep the ban anyway (`knowledge-base/hk.pkl:574-578`:
   "The ban on `depends` is a standing decision (Ray, 2026-07-31), kept after upstream
   fixed the deadlock in v1.53.0"). So the dotfiles prose calling it a live upstream
   bug is stale regardless of that decision. Not a 2.0 change; surfaced here per
   `tool-currency-and-native-first.md` rule 2.
2. **Top-level `steps` can replace the `allSteps` spread.** dotfiles `hk.pkl`
   currently spreads `...allSteps` into `pre-commit`, `check` and `fix`
   (`hk.pkl:775-827`); the KB assigns `lintSteps` to three hooks
   (`knowledge-base/hk.pkl:587-601`). With v2, `steps { ...allSteps }` plus
   hook-level overrides (pre-commit adds `no_commit_to_branch`; KB pre-commit swaps
   `gitleaks`) expresses the same thing. An explicit hook "keeps its own hook-level
   settings and replaces same-named inherited steps; the remaining shared steps still
   apply". Optional simplification, and it changes the shape of the `hk.pkl`
   contracts in `suites.toml`, so it is its own ticket.
3. **KB `gitleaksStaged` local -> builtin option.** Forced by R2; it removes a
   custom local in favour of a typed option.
4. **`lint.py` must stay.** hk 2 still has no native timeout: 0 hits for `timeout`
   in v2.0.1 `settings.toml`, `docs/environment_variables.md` and `Config.pkl`, while
   the control `fail_fast` returns 3 / 2 / 1 hits in the same files. The mise
   `timeout = "700s"` backstop (`mise.toml:[tasks.lint]`) likewise stays.
5. **`autofix.yml` could call the native fix hook** (`hk fix --all`) instead of
   `HK_FIX=1 hk run pre-commit --all --stash none`. In v2 it would leave changes
   unstaged, which `autofix-ci/action` reads from the worktree anyway, and it would
   avoid running the `pre-commit`-only `no_commit_to_branch` step in CI. Optional;
   independent of 2.0.
6. **Not retire-worthy but new:** v2 release archives ship `hk-configure` and
   `hk-debug` agent skills plus native shell completions (jdx/hk#1337, #1336).
