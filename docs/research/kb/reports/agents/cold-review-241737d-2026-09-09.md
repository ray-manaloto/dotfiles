### MAJOR

**M1 — A missing implementer commit dispatches a cold review of nothing and
still returns `status: 'complete'`.**
`.claude/workflows/gated-implementation.js:106-118`

`commit` is `''` when the implementer's report carries no `COMMIT:` line, and
`ref = A.reviewRef || commit` is then `''`. The script logs `<missing-ref>` but
dispatches the reviewer anyway, with a prompt whose first line is empty. The
final `status` ternary has tokens for `implementer-null`, `gates-null`,
`review-null` and `critic-null` but none for a missing ref.

Verified by running the real script under the repo's own dry-run harness with
both arms:

```
[CONTROL-has-commit] status='complete' commit='abcdef1234567' review_dispatched=True
[ARM-no-commit]      status='complete' commit=''             review_dispatched=True
```

`status` cannot discriminate "cold-reviewed the real commit" from "cold-reviewed
nothing", which is the workflow's entire contract. The repo's own test cannot
see this: `tests/test_workflows_js.py:145` hardcodes a stub that always returns
`COMMIT: abcdef1234567`.

**M2 — A malformed `corrections.json` entry turns a loud crash into a silent
drop at rc=0.** `python/src/dotfiles_setup/modernization_audit.py:109-114`

`_correction_value` guards `if not isinstance(correction, dict): return ""`.
The oracle has no such guard. Armed with a `corrections.json` whose `alpha-1`
value is a string:

| | rc | behaviour |
|---|---|---|
| oracle `aggregate.py` | 1 | `Traceback`, `AttributeError` |
| port `audit-aggregate` | 0 | correction silently dropped |

Nothing is written to stderr, no counter records it, and `corrections_applied`
under-counts with no explanation. This inverts the module's own stated
philosophy, preserved verbatim from the oracle at `aggregate.py:23-25`: "A
silent `continue` here drops a whole lens without changing any visible count
except verdict_files — a fail-open. Record it and surface it on stderr AND in
stdout so a dropped lens can never read as 'not run'." Corrections are the
citation-repair mechanism, so a dropped one means the TOML ships the defective
pointer the `.md` report says was corrected. Contrast the sibling path
`_load_verdicts:80-96`, which does record and surface its malformed files.

**M3 — A non-string finding id changes the survival verdict relative to the
oracle.** `python/src/dotfiles_setup/modernization_audit.py:90` vs `:141`/`:190`

`_build_rows` coerces with `finding_id = str(finding["id"])`, while
`_load_verdicts` keys the verdict index on the raw `entry["id"]` — `cast("str", …)`
is a no-op at runtime. So `"101"` never matches `101`, every verdict for that
finding is lost, and `verify_votes` drops to 0. Armed with an integer id on a
finding that has two lens verdicts:

| | `survived` | `refuted` |
|---|---|---|
| oracle | `{'refactor': 1}` | 1 |
| port | `{}` | 2 |

A contested finding that survived in the oracle is recorded as refuted, silently,
at rc=0 — in the exact computation the module exists to perform and that the
saved TOML and the tests assume. Latent today (all 743 real ids are strings,
which is why the byte-identical comparison did not surface it), but it is a
port-introduced divergence, and the fix is one line on either side.
