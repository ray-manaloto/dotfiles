### 1. [MEDIUM] The `fetch-depth: 0` rationale is wrong for the 5 `session_review` tests it names

`.github/workflows/ci.yml:191` adds `fetch-depth: 0`, justified (in both the
inline comment and the commit body) by "5 session_review, lint_delta,
skillopt_provenance [tests that] resolve a merge-base against origin/main."

The 5 `session_review` tests are exactly the 5 that call the
`_git_repo_with_goal_history()` fixture
(`tests/test_session_review.py:284-322`):
`test_session_review_refuses_a_rewrite_of_landed_history`,
`test_session_review_refuses_a_two_commit_history_rewrite`,
`test_session_review_refuses_rewrite_of_branch_appended_entry`,
`test_session_review_refuses_a_rewritten_goal_with_recomputed_digest`,
`test_session_review_refuses_a_missing_history_in_a_git_checkout`. That
fixture builds a **fully isolated throwaway repo inside `tmp_path`**
(`git init`, its own commits) and manufactures its own
`refs/remotes/origin/main` via `git update-ref` (`tests/test_session_review.py:306-311`,
repeated at ~439-445). None of these 5 tests ever read the outer checkout's
real git history or its real `origin/main` — the only touch on the real repo
is a plain byte read of `docs/agents/goal-history.md`
(`tests/test_session_review.py:289`), which works identically under any
`fetch-depth`. All 5 would pass unchanged under the previous shallow clone.

`fetch-depth: 0` may still be independently justified —
`tests/test_lint_delta.py:155-169`'s
`test_the_baseline_revision_is_the_previous_lockfile_change` genuinely calls
`lint_delta.previous_lock_revision(REPO_ROOT)` against the real repo and
needs real commit history (a shallow clone would starve it), and
`tests/test_skillopt_provenance.py:38-39` does a real `git show <commit>:<path>`
against a real commit too. But the commit's own accounting attributes the need
to the wrong 5 tests. Not a functional bug (the setting is harmless, just
costs more clone time) — it is a factually incorrect piece of the stated
evidence trail, in a repo whose own rules (`probes-need-a-control-arm.md`,
`verify-before-advancing.md`) hold evidence-trail accuracy as a first-class
concern.

### 3. [LOW] Inconsistent `$CI` truthiness check vs. the rest of the codebase

`tests/conftest.py`'s new `pytest_collection_modifyitems` hook does
`if not os.environ.get("CI"): return` — any non-empty value of `CI` is
treated as "running in CI" and skips `host_only` tests.
`python/src/dotfiles_setup/parity.py:223` checks the same env var with
`os.environ.get("CI") == "true"` — a strict equality. Both agree for GitHub
Actions' real default (`CI=true`), so this does not break the shipped
behavior, but the two checks disagree for `CI=false` / `CI=0` (values a
developer might plausibly export to mean "not CI"), so the two host-detection
mechanisms in this codebase are not the same predicate.

### 4. [LOW / unverified] No real CI run backs this commit yet; the timeout headroom is estimated, not measured

`gh run list --branch fix/808-pytest-in-ci` returns no runs, and

on an actual GitHub Actions `ubuntu-latest` runner. The commit's evidence

## Things checked and ruled out (no defect found)

- `pytest.ini`'s `addopts = -m "not image_exec and not codex_exec"` is
  untouched by the new CI step (`uv run --project python pytest tests/ -q`,
  no `-m` override), so `image_exec`/`codex_exec` stay deselected as intended
  — correctly avoids the "last `-m` wins" pytest gotcha the commit calls out.
- `host_only` skip is implemented as a `pytest_collection_modifyitems` hook
  (not via `-m`), so it applies regardless of any `-m` override elsewhere
  (`mise run smoke-exec`, `codex-lane-e2e`) — sound design.
- `pytest.mark.host_only` is registered in `pytest.ini`'s `markers =` list in
  the same diff, so no unknown-marker warning.
- `tests/conftest.py` is the only `conftest.py` in the repo (new file, no
  collision with any other fixture scope).
- `list[pytest.Item]` type hint is valid without `from __future__ import
  annotations` given `requires-python = ">=3.14"` (`python/pyproject.toml`).
- Checked whether the new `.parity/knowledge-base` checkout (present in the
  same job before pytest runs) could be swept up by an unscoped
  `REPO_ROOT.rglob`/`os.walk` in some test and inflate/break a file-count
  assertion — no test does an unscoped walk of `REPO_ROOT`; the three files
  using `rglob` scope it to `git_dir/refs`, `python/src/dotfiles_setup`, or a
  cache dir. `.parity/` is also gitignored, so `git ls-files`-based tests
  don't see it either way.
- `graphify`'s `os = ["macos"]` gate (mise.toml:60, cited in the
  `ci.yml:207` comment) is real — confirmed in `mise.toml`.
- `chezmoi`/`pixi` (`.config/mise/conf.d/shared.toml:27,35`) and `codex`
  (`mise.toml:87`) are not OS-gated — they will install on the
  `ubuntu-latest` runner, consistent with the commit's claim.
- `uv run --project python pytest tests/ -q` correctly uses `--project` (not
  `--directory`), matching this repo's own documented gotcha
  (`uv-project-vs-directory-expertise` skill / `AGENTS.md`).
- `contract-preflight` has no `MISE_LOCKED` env (unlike `lint`), but this is
  pre-existing (not touched by this diff) and is likely moot in practice: the
  job `needs: lint`, which runs first and populates the `jdx/mise-action`
  cache under the *same* cache key (`{platform}-{install_args_hash}-{file_hash}`)
  now that both jobs use identical (empty) `install_args` — so
  contract-preflight likely restores the exact same locked binaries lint just
  installed, via cache hit, rather than doing an independent unlocked resolve.
- `mise run parity` (`python/src/dotfiles_setup/parity.py`) has no git-mutating
  side effects that could race or interfere with the new pytest step running
  afterward in the same job.
