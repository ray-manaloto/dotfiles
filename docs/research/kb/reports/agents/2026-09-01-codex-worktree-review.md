## A. How Codex handles Git worktrees

### Purpose, creation, and normal Git workflow

- Codex presents worktrees as isolation for parallel chats: “Worktrees let Codex run multiple independent chats in the same project without interfering with each other,” and scheduled tasks can use dedicated background worktrees (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/codex-docs/docs/learn.chatgpt.com/docs/environments/git-worktrees/index.md:16-18`). The long-running-work guide separately says to “Use worktrees to give parallel coding chats separate checkouts” and warns against two chats changing the same files (`.../long-running-work/index.md:159-165`).
- The feature uses Git worktrees “under the hood”; each checkout has its own repository files while sharing Git metadata, enabling multiple branches in parallel (`.../environments/git-worktrees/index.md:25-33`). A worktree requires a Git repository (`.../environments/git-worktrees/index.md:43`).
- In the desktop flow, the user selects **Worktree**, optionally selects a local-environment setup script, selects a starting branch (including one with unstaged changes), and Codex creates the worktree in detached-HEAD state (`.../environments/git-worktrees/index.md:45-62`). The managed worktree starts at the selected branch's `HEAD`; if that branch has local changes, Codex applies those changes too (`.../environments/git-worktrees/index.md:117-119`).
- Running inside a worktree is intended to support a normal branch delivery workflow: after **Create branch here**, the docs explicitly say the user can commit, push, and open a GitHub pull request, and can open an IDE or integrated terminal in that directory (`.../environments/git-worktrees/index.md:77-87`). This is a product workflow statement, not a promise that those metadata-writing commands bypass the active sandbox.
- Handoff moves a chat and its code between Local and the associated worktree, with Codex handling the Git operations; a chat returns to the same worktree when handed back (`.../environments/git-worktrees/index.md:93-105`). Git's one-branch-per-worktree constraint still applies: the same branch cannot be checked out simultaneously in Local and another worktree (`.../environments/git-worktrees/index.md:68-70, 140-155`).

### Managed location, ignored-file provisioning, and cleanup

- Codex-managed worktrees default to `$CODEX_HOME/worktrees`; the desktop **Settings > Worktrees > Worktree root** setting can choose another root (`.../environments/git-worktrees/index.md:117-119, 180-183`).
- `.worktreeinclude` at the repository root lists ignored files or `.gitignore`-style patterns to copy into **local Codex-managed** worktrees. Only ignored matching files are copied; tracked files should not be listed. An ignored `AGENTS.override.md` is copied automatically (`.../environments/git-worktrees/index.md:121-136`). Source symlinks are skipped, existing destination files are not overwritten, and this behavior does not apply to remote worktrees or command-line-created worktrees (`.../environments/git-worktrees/index.md:136`).
- Managed worktrees are disposable and normally one-chat-per-worktree; permanent worktrees are long-lived projects, are not automatically deleted, and may host multiple chats (`.../environments/git-worktrees/index.md:111-115`). By default Codex retains the 15 most recent managed worktrees. It preserves worktrees tied to pinned or in-progress chats and permanent worktrees; it deletes managed worktrees when the chat is archived or retention requires it, taking a restorable snapshot first (`.../environments/git-worktrees/index.md:159-176`). Scheduled-task guidance correspondingly says to archive runs no longer needed and avoid pinning runs unless their worktrees should remain (`.../automations/index.md:259-263`).

### Sandbox and configuration

- Worktree organization does not replace sandbox enforcement: “Projects and worktrees organize work, but the sandbox enforces what local commands can read, change, or access over the network” (`.../projects/index.md:222-223`). The documented lower-risk CLI preset is `codex --sandbox workspace-write --ask-for-approval on-request`; the corresponding keys are `sandbox_mode = "workspace-write"`, `approval_policy = "on-request"`, and optional `sandbox_workspace_write.writable_roots` (`.../agent-approvals-security/index.md:214-225`; `.../config-file/config-reference/index.md:140-170`). Project trust can be assigned per project **or worktree** through `projects.<path>.trust_level`; an untrusted worktree skips project-local `.codex/` config, hooks, and rules (`.../config-file/config-reference/index.md:1606-1610`).
- No dedicated CLI worktree-creation/location flag or TOML `worktree_root` key was found in the Codex `config-file/`, `codex/`, or `environments/` documentation. Negative probe: `rg -n -i --glob '*.md' '(--[a-z-]*worktree|worktree[_-]root|worktree_root|worktrees_root)' config-file codex environments` returned rc 1. Same-shape positive control with `(--sandbox|writable_roots)` returned documented matches including `config-file/config-reference/index.md:149`, rc 0. The documented location control is the desktop UI setting **Settings > Worktrees > Worktree root** (`.../environments/git-worktrees/index.md:180-184`).

### Other documented limitations and surfaces

- An integrated terminal is scoped to the chat's current project or worktree and is intended for validation and Git operations (`.../integrated-terminal/index.md:16-26`). Remote Handoff creates or reuses a destination-host worktree and transfers chat plus Git state; it cannot hand off the chat making the request and does not support handoff to a Codex cloud environment (`.../remote-connections/index.md:244-269`).
- Worktrees do not run locally on a phone; Remote controls the connected computer or remote development environment where the worktree remains (`.../environments/git-worktrees/index.md:20-22`). Ignored-file copying skips symlinks and existing destinations and applies only to local desktop-managed worktrees, not remote or manually created Git worktrees (`.../environments/git-worktrees/index.md:121-136`).
- Multiple folders attached to one project do not become multiple worktree targets: pull-request and worktree actions target the primary repository, while secondary folders remain attached (`.../projects/index.md:210-223`).

## C. Does a worktree change Git write capability under `workspace-write`?

### Answer: no; the resolved worktree Git directory is explicitly protected

- The controlling documentation is explicit and settles the motivating question. Under “Protected paths in writable roots,” it says:

  > “`<writable_root>/.git` is protected as read-only whether it appears as a directory or file.”
  >
  > “If `<writable_root>/.git` is a pointer file (`gitdir: ...`), the resolved Git directory path is also protected as read-only.”
  >
  > “Protection is recursive, so everything under those paths is read-only.”

  Source: `/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/codex-docs/docs/learn.chatgpt.com/docs/agent-approvals-security/index.md:227-235`.
- Therefore, when the worktree root is a writable root, its visible `.git` pointer file is read-only **and the pointer's resolved target is read-only recursively**. For the motivating Git-worktree shape, this directly protects the resolved administrative directory under the parent repository (for example `.git/worktrees/<name>`); it is not made writable merely because its textual target lies outside the worktree directory. This conclusion is a direct application of the quoted pointer-file rule, not a filesystem-layout inference.
- Compared with a normal checkout under the same default `workspace-write` policy, the permission boundary is the same: a normal checkout's `.git` directory is recursively read-only, while a worktree's `.git` file and resolved Git directory are recursively read-only (`.../agent-approvals-security/index.md:227-235`). The worktree changes isolation and branch ownership, not sandbox permission to mutate Git metadata.
- Consequence stated by the docs: in `workspace-write`, “commands like `git commit` may still require approval to run outside the sandbox” because some environments keep `.git/` read-only (`.../config-file/config-advanced/index.md:364-368`). The product worktree page's commit/push workflow (`.../environments/git-worktrees/index.md:79-83`) therefore depends on the applicable approval/rule/full-access path; it does not contradict the protected-path rule.

### Branch integration and cleanup

- Isolated worktree branches are integrated explicitly. One recorded Codex lane could not check out the already-held target branch, committed on its own `worktree-agent-*` branch, and the supervisor cherry-picked that commit onto the intended branch before removing the settled worktree (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/.agent/plans/session-2026-08-30-a.md:63-71`). Another handoff prescribes a normal merge followed by `git worktree remove` **without** `--force` (`.../.agent/plans/session-2026-08-28-a.md:75-78`).
- Cleanup is deliberately not automated because ignored lane evidence can be the sole copy. A four-worktree audit found all four contained ignored `.agent/` trees; 11 review reports and nine research artifacts existed nowhere else. It records that plain `git worktree remove` refuses modified/untracked content, while `--force` deletes the directory wholesale, including ignored files (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/docs/session-review/runs/2026-08-23-1/refute-pending-work.md:19-45, 49-64`). The operational rule is therefore to inventory/retain or copy `.agent/` evidence first and prefer unforced removal; a handoff states this explicitly (`.../docs/session-review/runs/2026-08-23-2/handoff.md:65`).
- Worktree cleanup can invalidate the process's current directory, so the project warns not to `cd` into a worktree that is about to be removed (`.../.agent/plans/session-2026-08-25-d.md:84-88`). It also says receipts and gate artifacts disappear with `.agent/`, so the receipt used for landing must be written in the checkout that performs the landing (`.../.agent/plans/session-2026-08-25-d.md:78-88`).
- Live read-only state at investigation time: `git worktree list --porcelain` in the knowledge-base returned only `/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base` at `b47b60cbc271…` on `refs/heads/chore/s1-tool-currency-2026-09-01`; no linked worktrees were currently registered. ## Bottom line

- Codex uses worktrees as separate checkouts for parallel/background chats, creates managed ones detached under `$CODEX_HOME/worktrees` by default, can copy selected ignored files through `.worktreeinclude`, and automatically cleans disposable managed worktrees subject to retention and chat-state protections (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/codex-docs/docs/learn.chatgpt.com/docs/environments/git-worktrees/index.md:16-18, 111-136, 159-183`).
- The knowledge-base itself delegates checkout creation to the harness or operator; tracked config arrives through Git, while `.venv`, ignored clones, the derived graph, reports, and receipts do not automatically cross. It rebuilds reproducible ignored inputs from committed manifests, and cleanup is an evidence-preserving manual merge/cherry-pick plus unforced `git worktree remove` workflow (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/.agent/plans/session-2026-08-24-e.md:69-82`; `.../.agent/plans/session-2026-08-25-d.md:76-88`; `.../docs/session-review/runs/2026-08-23-1/refute-pending-work.md:30-64`).
- For the motivating permission question, a worktree does **not** create a writable Git-metadata loophole: default `workspace-write` protects both the `.git` pointer file and its resolved Git directory recursively, exactly as it protects a normal checkout's `.git` directory (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/codex-docs/docs/learn.chatgpt.com/docs/agent-approvals-security/index.md:227-235`).
