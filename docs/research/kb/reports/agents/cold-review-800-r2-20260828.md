## MED

**M1 — A two-arch host without the containerd image store is permanently wedged by `sync`, self-perpetuatingly.**
`sync.py:610-612` — `wanted = {resolve_platform()} | local_platforms(image_ref)`. Once both platforms are present locally, every stale refresh requests a 2-platform `--output type=docker`, which the docstring itself says needs containerd. If it fails, `_converge` returns FAIL (`sync.py:718-722`) — and because the export never ran, both platforms are *still* present, so the next sync makes the identical failing request. There is no fallback, no flag, and no hint in the (improved) error message that `docker rmi` of the other platform is the only exit. UNVERIFIED that the export actually fails on a non-containerd store (not reproducible read-only here); the code path and its self-perpetuation are cited.

**M2 — F10's legacy-record migration aid is destroyed by the first converge from the *other* architecture, re-introducing the spurious rebuild it exists to prevent.**
`sync.py:296-311` (`write_sync_record` writes only `registry_digest`/`local_image_id`/`containers` — never the flat key) vs `sync.py:196-198` (the read-side fallback).
Trace: legacy record `{registry_digest:D, local_image_id:L, container_image_id:C}` where `C` is the **amd64** container. User syncs **arm64** first → not stale, `containers` empty, legacy `C` ≠ arm64's id → rebuild → `write_sync_record` merges (D,L match) → `containers={"arm64":A}`, flat key **dropped**. Next amd64 sync: `containers.get("amd64")` None, legacy now None → `container_current` **False** → full `dev-rebuild` of a container that was current. F10 buys one arch one skipped rebuild, and only until the other arch converges.

**M3 — `--check` cannot predict the rebuild that `container_current` now drives.**
`sync.py:790-798`: check-only returns `1 if status.stale else 0` and never consults `container_current`. After F1 moved the currency test above the state test (`sync.py:643-648`), a non-stale tag with a mismatched **stopped or running** overlay makes `decide_action` return `"rebuild"` while `--check` prints `current` and exits 0. A script gating on `--check` (rc 0 = "nothing to do") is wrong in exactly the case F1 added. Cited: the two code sites; `test_stopped_container_with_stale_overlay_is_rebuilt_not_reused` confirms the decide side.

**M4 — Any converge that runs with an unreachable registry poisons the record into a guaranteed rebuild next time.**
`sync.py:726-727` and `sync.py:731-733`: `if rc == 0 and status.registry_digest:` — offline, `registry_digest` is None, so `write_sync_record` is skipped even though the converge succeeded and minted a **new overlay id**. The stored `containers[arch]` still names the superseded overlay, so the next online sync sees `container_current` False → rebuild. Reachable offline via `--force` (which short-circuits `decide_action` at `sync.py:643`) and via the `"up"` path. Pre-existing in shape, but round 2's per-arch `containers` is what turns it into a deterministic extra rebuild.

**M5 — F1 answers "recreate the container" with a `--build-no-cache` overlay rebuild.**
`sync.py:645-646` returns `"rebuild"`, and `_converge` runs `mise run dev-rebuild` (`mise.toml:344-353` → `--remove-existing-container --build-no-cache`). For the F1 case the base tag is *not* stale — only the container's overlay is behind — so `up --remove-existing-container` would suffice. The chosen action pays a no-cache overlay build every time. Deliberate? Nothing in the diff says so.

**M6 — `mise.toml [tasks.prune]:1009` hard-codes the `dotfiles.workspace` label in bash, duplicating `WORKSPACE_LABEL` and re-opening the decision `[tasks.stop]` deliberately moved into python.**
`devcontainer_names.py:145` defines the constant; `mise.toml:1065-1069` states outright that "which containers to remove is a DECISION, not a filter — [[zero-bash-logic]]" and routes `stop` through `dotfiles-setup devcontainer teardown`. A rename of `WORKSPACE_LABEL` silently makes prune stop matching post-#677 containers — the same failure class F3 is fixing. There is no whole-clone CLI verb; `teardown_container_ids` is arch-scoped by construction (`devcontainer_names.py:595-599`).

## LOW

**L1 — `refresh_local_tag` can emit `--platform ""` silently.**
`sync.py:610-613`: the union is filtered by membership in `published_targets()`. If `resolve_platform()` ever returns a spelling that is not a published triple (a hand-set `DOTFILES_PLATFORM=linux/amd64`, say — the level-less form the same module's docstring warns about) and the local tag is absent, `platforms` is `""`. Cited, adjacent: `docker image inspect --platform "" <ref>` returns the default image at **rc=0**, i.e. an empty platform is not rejected by docker's inspect path. UNVERIFIED what `buildx build --platform ""` does (no build allowed here). A membership filter that can yield empty should raise instead.

**L2 — `docker.py down()` is now arch-scoped but reports itself as project-scoped.**
`docker.py:284` logs "No active or exited devcontainers found for **this project**" while `teardown_container_ids(resolve_names(...))` matches only this project **+ this architecture** (`devcontainer_names.py:595-599`). On a two-arch host the message is false, and `down()` silently leaves the other architecture running. `[tasks.prune]` went whole-clone in the same commit; `down()` went arch-scoped. Neither is wrong alone; nothing states the split.

**L3 — `down()` gained an env dependency it did not have.**

Worth noting the F3 docker.py half fixes a nearly-dead path while the live teardown already used the right lookup.

**L4 — The `sort -u` justification in `[tasks.prune]:1002-1006` contradicts itself.**

**L5 — `SyncStatus.arch` defaults to `""`.**
`sync.py:128`. A status built without `arch` makes `record.containers.get("")` always miss and therefore always fall through to the F10 legacy id, for every architecture. Production always goes through `observe()` (`sync.py:660-671`), so this is test-surface only — but it means a future direct construction reads the legacy id silently rather than failing.
