# Proposals: code-search 1000-result cap vs `collect = "all"` (#1502)

Date: 2026-10-03. Lane: read-only review (Opus subagent), for Ray. Branch `feat/1502-saved-searches` @ `3e1ac1d8`.
No source edited; this report is the only file written. Note: `git check-ignore` on this path returned rc=1, so the
file is **not** gitignored in the worktree — it shows as untracked; the coordinator decides whether to commit it.

## TL;DR

- **13 of the 14 recorded code watches exceed the cap** (all in `orchestration-2026-10-02.toml`). Under today's
  default (`collect = "all"`) every one of them reruns as `uncollectable` and `rerun` exits rc 1 on every run, forever:
  the corpus grows (`"claude --bg"`: 6864 on 2026-10-02 → 7184 today), so even the one watch under the cap (922)
  will cross it.
- **Recommended: (a) runtime fallback to the top window, rc 0, explicitly labelled**, plus one symmetric diff guard
  that does not exist today (full run → windowed run would list ~all previous URLs as GONE). It needs no schema change.
- **Auto-sharding by `size:` (b) is not recommended:** ~1230 page calls (~2.2 h at the 6.5 s pace) for one rerun of
  this file, and live shards summed to 6817 vs `total_count` 7184 (5.1% short), so completeness cannot be verified.

## Code as it stands (cited)

- `collect_mode` — code `query` defaults to `all` (`python/src/dotfiles_setup/saved_searches.py:122-133`).
- `_collect_all` — pages `per_page=100` up to `_RESULT_CAP // _PAGE_SIZE` = 10 pages; on **any** page with
  `total_count > 1000` returns `RerunStatus.uncollectable` with reason "split the query (for example by size:
  ranges)" (`saved_searches.py:575-610`; constants `:72-74`; per-page recheck from the codex lens P2,
  `docs/research/kb/reports/agents/codex-lens-saved-searches-1502-13c34367-2026-10-03.md:15-16`).
- `rerun_main` rc: `int(failed or any(run.status not in {ok, empty_verified}))` (`saved_searches.py:1060-1066`) — so a
  single `uncollectable` row makes the whole file rc 1.
- `_row` already renders a windowed run as `(top N of M)` and a full one as `(all collected)`
  (`saved_searches.py:943-955`), and guards **top → full** with `n/a (first full collection)` (`:968-979`). There is
  **no guard for full → top**: a windowed run after a complete one diffs top-10 against the full set and lists every
  other previous URL as GONE. Today that path is reachable only by hand-editing `collect = "top"`; any automatic
  fallback makes it routine.
- Snapshot schema: `WatchRun.reason` is `["string","null"]` with no status-conditional constraint
  (`schemas/saved-search-snapshot.schema.json`, `WatchRun`), and `complete` is optional — so an `ok` row carrying a
  reason needs no schema/codegen change.
- Spec rev 2.3 codifies the current behaviour (`docs/specs/research-saved-searches-1502.md:222-235`, cap at `:231`).
- The prior research recommended **`top` as the default** with `uncollectable` above 1000
  (`docs/research/kb/reports/agents/saved-searches-newer-examples-research-2026-10-03.md:136`); Ray's 2026-10-03 ruling
  made `all` the default (spec `:222-223`). The census above is the evidence the ruling did not have: on the only file
  with recorded counts, the `all` default produces 13 permanent failures.

## Native research (GitHub docs, fetched 2026-10-03)

Fetched via `https://docs.github.com/api/article/body?pathname=<path>`; control: `/en/rest/search/zzqq-nope-<random>`
→ 404 while both real pages → 200, so the fetch discriminates.

- Cap: "the GitHub REST API provides **up to 1,000 results for each search**" —
  https://docs.github.com/en/rest/search/search (§ About search).
- Rate: "The Search code endpoint requires you to authenticate and limits you to 10 requests per minute" — same page
  (§ Rate limit). Measured header `x-ratelimit-resource: code_search`, limit 10.
- `incomplete_results`: set when a query exceeds the time limit; "Reaching a timeout does not necessarily mean that
  search results are incomplete" — same page (§ Timeouts and incomplete results). Already mapped to
  `RerunStatus.incomplete` (`saved_searches.py:541-544`).
- `size:` qualifier (with `>`/`<`), and "Only files smaller than 384 KB are searchable" —
  https://docs.github.com/en/search-github/searching-on-github/searching-code (legacy syntax, the one the REST
  endpoint takes).
- No endpoint lifts the cap: the new code-search engine has no public REST/GraphQL endpoint and GraphQL `SearchType`
  has no `CODE` member (introspected with a bogus-type control in the prior report, `…newer-examples…:56-63`). I did
  not re-probe GraphQL (call budget); that finding is inherited, labelled as such.
- Prior art: monitors that page code search (VKSRC/Github-Monitor, Macr0phag3/GithubMonitor) take
  `min(total_count, 1000)` and page to the cap — **none shards past it** (`…newer-examples…:122-130`, inherited).

| s_lt2k | `… size:<2000` | 645 | false | 100 | 7/10 | page=7 |

| neg_huge (negative arm) | `… size:>400000` | 0 | false | 0 | 4/10 | none |

Findings:

1. **The cap is visible in the protocol:** for 7184 hits the `Link` header's `rel="last"` is `page=10` — the API
   will not hand out page 11. A runtime check could key on this too, but `total_count > 1000` is simpler.
2. **`total_count` drifts between runs, not between calls:** 6864 recorded 2026-10-02 → 7184 today; base1 = base2
   and the top-100 key sets were identical. (The prior report saw 125 → 141 within seconds, so per-call drift also
   happens; neither direction is safe to treat as a hit count.)
3. **`size:` is applied** (negative arm 0; shard counts differ from the base) and **shard page-1 key sets are
   pairwise disjoint** (0/0/0 overlap), consistent with "every file has one size".
4. **But shards are not exhaustive against `total_count`:** 645 + 2044 + 4128 = **6817 vs 7184** (−367, −5.1%).
   Either `total_count` is an estimate (likely, given finding 2) or shards drop files; a sharder cannot tell which,
   so it can never assert "complete" against the total. And two of three shards are themselves still over 1000.
5. Repeat calls were fast (0.4–0.6 s vs 1.4–2.6 s first) — consistent with a server cache; the pace, not latency,
   dominates cost.

## Options, ranked

### 1. (a+) Runtime fallback to the top window, rc 0, labelled — **RECOMMENDED**

When the default-`all` collection sees `total_count > 1000` on any page, return the already-fetched page-1 items as
a **top window**: `status = ok`, `complete` unset, `count = total_count`, `reason = "over the 1000-result cap: top N
of M, not all collected — narrow the query to collect all"`. The row renders via the existing
`(top N of M)` path (`saved_searches.py:951-954`). Add the missing symmetric guard: previous run `complete` and this
run not → NEW/GONE `n/a (window after full collection)`.

- PRO: zero extra API calls (page 1 is already in hand; same 1-call cost as today's `uncollectable`).
- PRO: rc 0 — a query that is merely broad is no longer a failure; rc 1 again means something broke.
- PRO: still yields a signal (count trend + top-window diff, already labelled as ranking-churn-prone), versus no
  signal at all under `uncollectable`.
- PRO: self-healing over time: a query that shrinks under the cap (or is narrowed) silently becomes a full collection,
  and one that grows past it degrades instead of breaking — matters because counts drift upward (finding 2).
- PRO: no schema/codegen change (`reason` is a free nullable string; `complete` already optional).
- CON: "default all" no longer guarantees "all" — a reader must read the label. Mitigation: the reason string and
  the `(top N of M)` counts column both say so.
- CON: needs the full→top guard, or the first fallback after a complete run floods GONE (real today-latent bug).
- CON: an explicit `collect = "all"` (a user demand, not a default) arguably should stay strict. Suggested split:
  **default** all falls back; **explicit** `collect = "all"` keeps `uncollectable` (rc 1). `collect_mode` already
  distinguishes explicit from unset (`saved_searches.py:130-131`), so this is cheap. Ray should rule on the split.
- CON: `uncollectable` becomes reachable only via explicit `all` (keep it; do not delete the enum value).

### 2. (c) Keep `uncollectable`, but non-failing (rc 0) plus a "narrow this query" note

- PRO: smallest diff — remove `uncollectable` from the rc set in `rerun_main` (`:1060-1066`) and reword the reason.
- PRO: never pretends to be a full collection.
- CON: the watch produces **no** diff at all (non-comparable → `n/a`, `saved_searches.py:963-966`); 13/14 watches of
  the orchestration file would be count-only forever.
- CON: a status that is not ok/empty-verified yet exits 0 breaks the rc invariant everything else relies on ("rc 0
  ⇔ every row answered"). It would need its own exception, which is how gates go quiet.

### 3. (e) Narrow the queries by hand (`filename:`, `path:`, `extension:`, `language:`, `repo:`)

- PRO: the only route to a genuinely complete, meaningful set. `"subagent_type" "fork"` at 41664 hits is too broad to
  be a useful watch anyway; `… path:.claude` already cuts it to 1652, `isolation: worktree path:.claude/agents` to 1298.
- PRO: needs no code — it is what the existing `uncollectable` reason already asks for.
- CON: human work per query, and the result still drifts back over the cap as the corpus grows, so it is not a fix
  for the rc-1 failure mode on its own.
- Position: the **remedy the (a) label points at**, not an alternative to (a).

### 4. (d) `record` writes `collect = "top"` for code queries whose recorded count > 1000

At record time (`saved_searches.py:305-325`, where `count` is read from the manifest).

- PRO: explicit in the file — the reader sees `collect = "top"` and knows.
- CON: a point-in-time decision on a drifting number: a 922 query recorded as `all` fails once it crosses 1000
  (exactly the "claude --bg" 6864 → 7184 drift class). Still needs (a) or (c) at runtime.
- CON: a generated file is overwritten on the next record (`GENERATED_HEADER`, `:60-63`), so the choice is not durable
  for curated edits either way; and manifests with no code count (the llvm/model-registry files) cannot be decided.
- Position: optional nicety on top of (a), never instead of it.

### 5. (b) Auto-shard by `size:` ranges until every shard ≤ 1000 — **not recommended**

- PRO: the only automatic route past the cap; shards are disjoint (finding 3).
- CON — cost: ≥ ceil(M/1000) shards × up to 10 pages, plus bisection probes to find boundaries. For this file's 13
  over-cap watches, ≥ 122,778/100 ≈ **1,230 page calls ≈ 2.2 h per rerun** at the 6.5 s pace (`_CODE_PACE`,
  `saved_searches.py:66`); `"subagent_type" "fork"` alone ≈ 420+ calls (~45 min).
- CON — not verifiably complete: shards sum 5.1% short of `total_count` (finding 4); with no exact total there is no
  completeness check, so "complete" would be asserted on faith — the exact false-GONE risk the spec forbids.
- CON — unshardable floor: `size:N` cannot split > 1000 files of one exact byte size (vendored/duplicated files such
  as a copied CLAUDE.md are plausible in this corpus), and files ≥ 384 KB are unindexed anyway.
- CON — a shard plan is non-deterministic across runs (boundaries move as counts drift), making snapshots harder to
  audit; and the prior research rejected default sharding for these reasons (`…newer-examples…:136,160-163`).
- If ever wanted, prefer a **declared** `shards = ["size:<2000", …]` list per watch (opt-in, reviewed, each shard
  falling back per (a)) over automatic bisection.

### Other options considered

- **(a2) Page the best 1000 for over-cap queries** (top 1000 instead of top `limit`): 10 calls/watch for a window
  whose bottom edge is still ranking churn — costs 10× (a) for no completeness. Rejected.
- **Second source (Sourcegraph `count:all`)**: no cap, but a curated subset of repos (prior report: 167 matches in 25
  repos vs GitHub's 221 files) — supplementary at most; not authoritative for "new to the index". Inherited, not
  re-probed.
- **Revisit the default (`top`)**: the prior research's recommendation. (a) makes this mostly moot — a default-`all`
  that falls back is a strict superset for sub-cap queries — but if Ray rejects (a), the census is the argument for
  reverting the default.

## Recommendation

Adopt **(a+)**: default-`all` code queries fall back to the labelled top window above the cap, rc 0; explicit
`collect = "all"` stays strict (`uncollectable`, rc 1) pending Ray's ruling; add the full→window diff guard; make the
reason name (e) as the remedy. Update spec rev 2.3 (`docs/specs/research-saved-searches-1502.md:231`) and the
`_collect_all` docstring in the same change. Skip (b); treat (d) as optional.
