## Findings

### F1 — HIGH — `ci.image-lock-pr-wired` asserts none of the security gate its own description claims
`python/verification/suites.toml:809-826`

The contract's `description` says the job must "fire only on same-repo Renovate
`pull_request` events". Its `per_path_tokens` are:

```
"image-lock-pr:",
"lock-refresh:\n    # Never on pull_request",
"tool-currency:\n    # Never on pull_request",
"id: drift-check\n        continue-on-error: true\n ... test_system_lock_versions_match_pins",
"run: mise run lock-image -- --no-container",
"enforces it on any new job.\n      HK_SKIP_HOOKS: pre-commit,pre-push",
"git config --global user.name \"dotfiles-refresh-bot-org[bot]\"",
```

Nothing binds the job's `if:` block (`.github/workflows/refresh.yml:263-268`).
Delete `github.event.pull_request.head.repo.full_name == github.repository`,
`github.event.pull_request.user.login == 'renovate[bot]'`, and the
`github.actor != ...` loop guard, and **this contract still passes**. That is
the exact "assertion could still pass if the thing it guards were reverted"
shape `.claude/rules/probes-need-a-control-arm.md` rule 2 names — and the
reverted thing here is the fork/authorship gate on a job that mints a
`contents: write` App token and pushes.

Two further sub-claims in the same description are also unbound:
- "never run the composite's root `mise lock` step" — `require_tokens` only
  asserts presence; a *forbid* token would be needed. Nothing checks it.
- "scope its drift check to the five image-lock node IDs" — the token pins
  only the **first** of the five node IDs
  (`suites.toml:820`); the other four can be deleted silently.

### F2 — MEDIUM/HIGH — `ci.refresh-uses-app-token` was materially weakened: it no longer asserts an App token is minted
`python/verification/suites.toml:797-806`

Removed tokens: `uses: actions/create-github-app-token@`,
`app-id: ${{ secrets.REFRESH_APP_ID }}`, `REFRESH_APP_PRIVATE_KEY`.
Added: `uses: $/.github/actions/lock-refresh`,
`uses: $/.github/actions/open-refresh-pr`, `permission-pull-requests: write`.

The contract named *"refresh-uses-app-token"* now contains **no token naming
the App-token action or either App secret**. The only residual binding is the
incidental `permission-pull-requests: write` input line
(`refresh.yml:99`), which happens to sit inside the app-token step today.

The stated justification — "the generic tokens now match 2x each and no longer
bind this job alone" — describes the `contract_token_uniqueness` /
`token-audit` gate, not `require_tokens`. A **multi-line** token would have
kept the real assertion and stayed unique, e.g.
`"app-id: ${{ secrets.REFRESH_APP_ID }}\n          private-key: ${{ secrets.REFRESH_APP_PRIVATE_KEY }}\n          permission-contents: write\n          permission-pull-requests: write"`
(matches only `refresh.yml:96-99`; the new job at `:290-292` lacks the fourth
line). The weakening was avoidable.

### F3 — MEDIUM — write-scoped App token is minted **before** untrusted PR-branch code executes
`.github/workflows/refresh.yml:283-292` vs `:293-331`

Order is: mint App token (`permission-contents: write`, repo-wide) → checkout
the PR head → `mise run lock-image` (which runs `mise.toml` tasks, downloads
and executes tool binaries at versions the PR itself sets). The token could be
minted *after* the confinement check instead; nothing in the job needs it
before `:378`.

Reachability is gated to `renovate[bot]`-authored same-repo branches, so this
is defence-in-depth rather than a live hole — but the ordering is the opposite
of what the gate's own comment ("used ONLY in the push step below") implies.
Whether a step can read a prior step's output off disk (`_temp/…`) is
**UNVERIFIED** — I did not probe the runner.

### F4 — MEDIUM — the loop terminator depends on a hand-maintained literal that nothing checks
`.github/workflows/refresh.yml:268`, `:371-372`

`github.actor != 'dotfiles-refresh-bot-org[bot]'` and the git identity
(`user.name`, and the `298071151+…` no-reply address) are three hardcoded
copies of the App's bot identity. The sibling precedent,
`gcc-sha-repair.yml:84,91-92`, derives it instead from
`steps.app-token.outputs.app-slug`.

If the App is renamed/reinstalled, the actor literal stops matching. The
comment at `:311-313` calls the drift-check the "primary loop terminator", but
that only terminates when regeneration **converges**. If it does not (an
upstream release between passes, a `"latest"` pin, the documented
"did not converge in 5 pass(es)" rate-limit failure at `:326-328`), the actor
guard is the *only* thing standing between this job and an unbounded
push → `synchronize` → push loop, each iteration also firing a full `ci.yml`.
No gate, test, or contract binds the literal (see F1).

### F5 — LOW/MEDIUM — `awk '{print $2}'` misreads several `git status --porcelain` shapes
`.github/workflows/refresh.yml:350-352`

- A rename prints `R  old -> new`; `$2` yields **`old`**, not the new path.
- A path containing a space is truncated at the space, so a stray
  `foo bar.txt` becomes `foo` — still caught as unexpected (fails safe), but
  the reported name is wrong.
- Porcelain v1 quotes paths with special characters (`"a\tb"`), again
  mis-split.

Direction of failure is mostly safe (spurious FAIL), but a rename of one image
lock to the other would report the *old* name, which the allowlist regex also
matches — so a rename **inside** the allowlisted pair passes silently.
`git status --porcelain -z` + `--untracked-files=all`, or
`git diff --name-only` + `git ls-files -o --exclude-standard`, is the
non-lossy form.

### F6 — LOW — pre-existing-job `if:` gates and the new job's gate are not the same predicate
`.github/workflows/refresh.yml:65`, `:169`, `:263-268`

`lock-refresh` and `tool-currency` are gated `github.event_name != 'pull_request'`
— correct and sufficient. Noted only because the contract in F1 binds *these
two* comment lines but not the new job's gate: the guard conditions that are

### F7 — MEDIUM — no "nothing to commit" guard: any transient drift-check failure red-Xes the Renovate PR
`.github/workflows/refresh.yml:373-377` vs precedent `.github/workflows/gcc-sha-repair.yml:87-90`

The cited precedent opens its commit step with

```bash
if git diff --quiet -- .devcontainer/Dockerfile; then
  echo "gcc-latest sha already correct — nothing to repair."
  exit 0
fi
```

The new job dropped that guard. Reachable path: `drift-check` fails for a
reason other than drift (network flake resolving a plugin, a pytest collection
error, a renamed node ID — pytest exits 4 with `ERROR: not found:`), the regen
changes nothing, the re-check then passes, the confinement check passes on a
clean tree, `git add` stages nothing, and **`git commit` exits 1 with
"nothing to commit"** — a red X on the bot PR with a misleading failure. The
job's own `continue-on-error: true` on `drift-check` (`:315`) is what converts
"the check could not run" into "there is drift", so this is not a remote path.

### F8 — MEDIUM/HIGH — `gcc-sha-repair.yml` uses the SAME App, so its push suppresses the next `image-lock-pr` run — and `group:all` makes that the common case
`.github/workflows/refresh.yml:268,290` vs `.github/workflows/gcc-sha-repair.yml:62`; `renovate.json:3-6`

Both workflows mint from `secrets.REFRESH_APP_ID` / `REFRESH_APP_PRIVATE_KEY`,
so both push as the same `dotfiles-refresh-bot-org[bot]`. The loop guard at
`:268` is keyed on that identity and cannot distinguish which workflow pushed.

`renovate.json:5` extends `"group:all"` — every bump lands in one
`renovate/all` PR (confirmed: `origin/renovate/all` exists). So a PR that bumps
both the dated gcc `.deb` in the Dockerfile and a `shared.toml` pin — the
default grouping, not an edge case — has both writers active on one branch:

1. `gcc-sha-repair` (trigger `push: renovate/**` + Dockerfile path) pushes its
   sha fix.
2. That push emits `synchronize` with `github.actor ==
   'dotfiles-refresh-bot-org[bot]'` → **`image-lock-pr` is skipped**.
3. The `image-lock-pr` run started at `opened` is not cancelled (a skipped job
   never enters its concurrency group), so it pushes a commit built on the
   pre-gcc-sha head onto a branch that has moved. There is no `git fetch`,
   no rebase, and no `--force-with-lease` (`:389`) — the push is rejected
   non-fast-forward and the job goes red.

Either ordering leaves the PR without regenerated image locks and with no
further `synchronize` to retry on: the #887 deadlock, restored, on the exact
PR shape this repo produces by default. Nothing in the diff mentions
`gcc-sha-repair` or `group:all`.
