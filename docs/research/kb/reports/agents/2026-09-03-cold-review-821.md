This directly conflicts with the pre-existing (unmodified by this commit)
blocking coverage assertion:

```
tests/test_lock_coverage.py:205-207
    assert locked - config == set(), (
        f"stale mise.lock entries for removed tools: {sorted(locked - config)}"

```

i.e. `test_root_lock_covers_host_config` requires **both** directions of exact
coverage (nothing missing, nothing stale). The new code only prevents the
under-coverage direction (task-scoped tools leaking in); it does nothing to
prevent the over-coverage/staleness direction the moment a top-level tool is
removed from `mise.toml` — the CI-run `lock-refresh-root` task would leave a
dangling lock entry, which `test_root_lock_covers_host_config` would then fail
on the next `pytest` run (locally or in CI), or would silently ship a lock with
an extra, unreferenced tool entry if that test isn't run before merge.

## Test quality check (independent, cold-review discipline)

The 6 new/changed tests in `tests/test_lock_refresh.py` are NOT tautological —
each injects a recording `run` callable and asserts the constructed argv shape
or return code, which is real, falsifiable behavior distinct from the
implementation's own computation:

- `test_top_level_config_tools_excludes_task_scoped_tools` — real (would fail
  if task-tool filtering were removed).
- `test_top_level_config_tools_keeps_all_tools_without_task_tools` — real.
- `test_top_level_config_tools_strips_only_extras` — real (exercises the
  `_EXTRAS_RE` stripping logic against literal expected sets).
- `test_lock_top_level_config_tools_builds_scoped_argv` — real; asserts the
  exact `["mise", "lock", "jq", "npm:@scope/pkg"]` argv via an injected fake,
  not a recomputation.
- `test_lock_top_level_config_tools_refuses_a_bare_fallback` — real; asserts
  rc=1 and zero subprocess calls when top-level `[tools]` is empty.
- `test_lock_refresh_wiring_calls_the_task_and_cli` — a wiring/grep test
  (string-presence assertions against `mise.toml` and `action.yml`); real in
  that it would fail if the task/CLI names were renamed independently, but it
  is a shallow "the strings exist" check, not a behavioral one — labeled here
  for completeness, not as a defect.

**Gap corroborating the P2 finding**: no test in this file (or elsewhere
touched by the diff) constructs the "a top-level tool was removed from
`mise.toml` since the last lock" scenario and asserts the resulting lock no
longer contains it. That is exactly the scenario the P2 finding says is
mishandled, so the absence of a test for it is consistent with (not
independent confirmation of, but corroborating) the finding — the feature
this fix claims to deliver (exact root-lock coverage on every refresh) has no
test proving the removal direction, only the addition/leakage direction.
