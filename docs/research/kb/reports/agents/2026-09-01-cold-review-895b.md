## F1 — MEDIUM — Both safety guards in the file-deletion path are untested; each can be removed with all 14 tests still green

`python/src/dotfiles_setup/lint.py:117-140` (`_prune_old_logs`) is the only code in
this diff that calls `unlink()`. Its two safety conditions are the 24h age floor
(`lint.py:135-136`) and the `candidate.is_symlink()` skip (`lint.py:132`).

Mutation evidence (tree restored clean afterwards, `git diff --quiet` verified):

- Replaced `if age < _PRUNE_MAX_AGE_SECONDS: continue` with `_ = age`
  (i.e. delete every sibling per-run log unconditionally, including a
  concurrently-live one): `14 passed`, rc=0.
- Removed `or candidate.is_symlink()` from the skip at `lint.py:132`:
  `14 passed`, rc=0.

So a later "tidy-up" of either guard is invisible to the suite. The age floor is
what stops a second concurrent run of the SAME workspace from deleting the first
run's live log — exactly the evidence-integrity property #895 exists to protect.
Only the maximally-destructive mutation (unscoped glob + no symlink skip + no age
floor) is caught, and then only incidentally, by the two symlink tests.

There is no test at all for `_prune_old_logs`: not that it deletes a >24h file,
not that it spares a fresh one, not that it spares the stable symlink, not that it
spares another workspace's file.

## F2 — MEDIUM — Legacy `~/.local/state/dotfiles/hk-lint.log` is never removed or matched by the pruner; it becomes a permanently-frozen decoy

Live host state (`ls -la ~/.local/state/dotfiles/`):

```
-rw-r--r--  304027  Sep  1 11:09  hk-lint-273897ea-45482.log
lrwxr-xr-x      65  Sep  1 11:08  hk-lint-273897ea.log -> .../hk-lint-273897ea-45482.log
-rw-r--r--  304027  Sep  1 02:55  hk-lint.log            <-- legacy, orphaned
```

The pruner globs `hk-lint-<hash>-*.log` (`lint.py:126`), which cannot match
`hk-lint.log` (probe-confirmed: the glob returned only `hk-lint-<hash>-999.log`
against a fixture containing the stable name, a `.tmp-` symlink and another
workspace's file). Nothing else in the diff removes it.

The consequence is the exact failure this rule exists to prevent: every persisted
report, receipt and auto-memory entry in this repo still names `hk-lint.log`
(`docs/rules-evidence/long-running-command-hangs.md:60`,
`docs/research/kb/reports/agents/2026-09-01-mount-uniqueness-audit.md:286`,
`.../20260829-session-resume-codex-implementer.md:43`, and several more). An
agent that reaches for the remembered path now reads a 304KB file that looks
exactly like a real lint log and will never change again — "reading the wrong one
made a live hang look idle" (`.claude/rules/long-running-command-hangs.md:57`),
made permanent. This is the same shape as the `doppler.env` legacy file sitting
beside it from #893.

## F3 — MEDIUM — The documented read path is still shared between two concurrent runs of the SAME workspace; the evidence doc overstates the guarantee

`docs/rules-evidence/long-running-command-hangs.md:67` claims the symlink is
"repointed atomically via a single `Path.replace` so two runs never observe or
destroy each other's file."

The per-run *files* are indeed separate. The *stable symlink* is not: it is one
name per workspace (`lint.py:90`), and every run repoints it
(`lint.py:193-194` → `_update_stable_symlink`). Two windows on one clone — a case
`lint.py:30-31` names explicitly — therefore still fight over the only name the
rule tells a reader to open (`.claude/rules/long-running-command-hangs.md:54-56`).

Rule 2's own prescribed monitor loop (`while ... grep -q RC "$LOG"`,
`.claude/rules/long-running-command-hangs.md:44-46`) reads that symlink; when a
second lint starts in another window the link flips and the loop silently begins
reading the other run's log. The truncation/interleaving is fixed; the
"you are reading someone else's run" half is not — it moved from the file to the
link. The `lint.py` docstring is honest about this ("always names the most recent
run"); the evidence doc's "never observe each other" is not.

## F5 — LOW — Orphaned `hk-lint-<hash>.log.tmp-<pid>` symlinks are never cleaned by anything

`lint.py:110-113` creates `<stable>.tmp-<pid>` and relies on the same PID
recurring to clear a leftover (`tmp.unlink(missing_ok=True)`, `lint.py:111`). A run
killed between `symlink_to` and `replace` leaves a dangling symlink whose name
ends `.tmp-<pid>`, which the pruner's `*.log` glob cannot match (`lint.py:126`;
probe-confirmed). They accumulate indefinitely in the shared state dir.

## F6 — INFORMATIONAL — `_default_project_root()` and `main.py`'s `project_root` are written differently but agree in practice

`lint.py:78` resolves then climbs four parents; `main.py:2426` climbs four parents
without resolving. Both are fed to `workspace_hash`, which resolves
(`devcontainer_names.py:174`), so they agree for any ancestor-symlink route. The
fallback in `lint.py:78` is only reachable by direct library import — `main.py`
always threads the real root (`main.py:2233-2238`) — and `git grep run_guarded`
finds no other production caller. Non-issue today; noted because the two spellings
will diverge if the package is ever installed non-editable and the fallback is hit
(it would then hash a site-packages ancestor).

## F7 — INFORMATIONAL — `test_run_guarded_replaces_pre_existing_regular_file_at_stable_path` guards a state the previous version could not produce

`tests/test_lint.py:159-183`. The pre-#895 default was `hk-lint.log`, never

## Things checked and found sound

- Prune glob scoping: probe-confirmed it matches only `hk-lint-<this hash>-*.log`
  — not the stable symlink, not the `.tmp-` symlink, not another workspace's file
  (`lint.py:126`).
- `os.replace` semantics: correctly handles first-run creation, repointing an
  existing symlink, and replacing a regular file, with no check-then-act window;
  the deliberate absence of a migration branch (`lint.py:98-107`) is right.
- Deletion blast radius: nothing else in `~/.local/state/dotfiles` uses the
  `hk-lint-` prefix (live listing shows `doppler-*`, `dag-tick.lock`, `sync-*.json`,
  `ssh-agent*`, `authorized_keys`, `guard-fail-open.log`).
- Container safety: `~/.local/state/dotfiles` is bind-mounted to
  `/tmp/dotfiles-host-state`, NOT onto the container `$HOME`
  (`.devcontainer/devcontainer.json:123`), so the docstring's claim at
  `lint.py:35-40` that in-container `HOME` is what discriminates is correct.
- `except OSError` breadth in both helpers is appropriate (directory-at-path,
  read-only dir, no-symlink-support each raise a different subtype) and neither
  can fail the run.
- Symlink following: `lstat` in the pruner (`lint.py:135`), `unlink` never
  follows, `_print_log_tail` reads the per-run path not the link.
- `logger.info(..., "log %s", log_file)` (`lint.py:227-229`) prints the derived
  path at INFO, and `main.py:2417-2421` configures INFO to stderr — so the
  `<hash>` the rule now names is at least emitted at the start of every run.
- `uv run --project python pytest tests/test_lint.py -q` → `14 passed`, rc=0.

## Post-hoc check against the commit message (read only after forming the above)

The commit message states the defect as: "two clones **or two windows on one
clone** truncated and interleaved the same file, so an agent diagnosing a hang by
rule 2 could read a different run's log body next to a correct rc."

F3 is therefore a real gap against the change's own stated motivation, not a
difference of intent: for the two-windows-on-one-clone case, an agent following
rule 2 opens `hk-lint-<hash>.log` and still gets whichever run repointed the link
last. The cross-clone half is genuinely fixed; the same-clone half is fixed only
for the underlying bytes, not for the documented read.

"Updates the two docs naming the old fixed path" is accurate for authored docs;
F2 is about the file left behind on disk, which no doc edit reaches.
