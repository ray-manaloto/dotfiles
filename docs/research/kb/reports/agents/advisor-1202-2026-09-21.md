# Advisor Report — spec-1202

**Decision:** How to fix a deny-capable Claude Code function hook that has bricked two sessions.

## Evidence Gathered

**Spec:** `/private/tmp/claude-501/-Users-rmanaloto-dev-github-ray-manaloto-dotfiles/dd442cf4-4469-4773-9f50-6f6c2584afae/scratchpad/spec-1202.md`

**Key constraint:** Operator ruling 2026-09-21 — pin-only failures must be REPORTED but NOT enforce-eligible; every other verdict state keeps its prior enforcement.

**Current implementation:**
- `DoctorVerdict.enforcement_eligible` → `return self.verdict is Verdict.INVALID` (claude_doctor.py:165)
- Verdict becomes INVALID when `failed_assertion=true`, which includes ANY of: method_findings, pin_findings, clean_findings, or running!=latest (lines 469-471)
- The hook caches the verdict once at SessionStart (register.ts:42, :183) and gates on `cachedReport?.verdict !== "invalid"` (line 210)
- Currently, the hook denies on INVALID verdict AND the call is not repair-permitted

**The problem:** Pin-only failures (where only `pin_findings` is populated) currently set verdict=INVALID → enforcement_eligible=true → denies on PreToolUse, even though the operator ruled they should report but not deny.

## Analysis of Decision Points

### Q1: Pin-only representation

**Recommend: New verdict value (e.g., "drift")**

Rationale:
- Option (a) `verdict="invalid" + enforcement_eligible=false` creates a semantically false state (invalid judgment that doesn't enforce).
- Option (c) routing to "unknown" conflates pin-only with unanswered questions — they're distinct.
- **New verdict value** is explicit and clear: "drift" means "repo pin is behind upstream, repo state question answered differently from host state."

The hook gates on `enforcement_eligible`, so the TS side doesn't care which verdict value it is — it reads the flag. Python still owns the judgment. This is sound.

### Q2: Re-validation on about-to-deny path

**Recommend: Yes, acceptable, but require a minimum interval or bounded cache.**

The cost (up to 90s per denied call) is unavoidable if the goal is in-session repair. However:
- **Without re-validation:** A repair (Edit/Write to doctor.toml) doesn't take effect until restart, defeating the fix.
- **With re-validation:** Each denied call respawns the check, so repairs take effect immediately.
- **Risk:** Every denied call pays 90s. If a developer is troubleshooting, they could be rate-limited by their own check.

**Mitigation:** Cache the re-validation result for 5-10 seconds. If a tool call 8 seconds after the previous one is about to be denied, reuse the prior result instead of re-running. This bounds the cost (1 re-run per ~10 seconds, not per call) while keeping repairs responsive (an Edit takes effect in ~10s, not at restart).

If re-validation returns null, the spec says keep the old deny — this is correct because a null means "couldn't ask", which is UNKNOWN-like and should not become more permissive.

### Q3: Exact-path permit for Edit/Write

**Recommend: Path normalization + string equality is sufficient. Symlink/APFS case risk is acceptable.**

Rationale:
- A strict path comparison after normalization (`Path.resolve()` or equivalent) prevents `x/doctor.toml`, relative paths that escape, `..` traversal, and decorated paths.
- **Symlink risk:** A symlink to `doctor.toml` would not match after normalization. This is acceptable because the edit is to the real file, not a symlink — the user can still edit the target directly.
- **APFS case risk:** macOS APFS is case-insensitive but case-preserving. A comparison on `doctor.toml` vs `DOCTOR.toml` would differ. This is acceptable because the file itself is case-preserving, and an honest typo should not accidentally permit a write.

No filesystem access is needed in the hook. The TS path is minimal and correct.

### Q4: Unintended enforcement loosening

**No.** The change only affects pin-only findings. Every other combination (method+pin, clean+pin, method+clean, method+clean+pin, running!=latest) remains enforcing. The fail_assertion logic at line 469 is not changed — only the routing after it.

## The Single Risk That Decides It

**Re-validation cost without bounds creates operational friction.** A developer fixing a broken install faces 90s latency per denied call. With a bounded cache (5-10s), each attempt to repair gets feedback within ~10s. Without it, they're stuck in a wait loop: call → deny (90s) → check findings → try fix → call → deny (90s again).

**Mitigation is cheap:** Cache the re-validation result for 5-10 seconds. This trades "maybe 10s stale" (acceptable for a troubleshooting loop) against "never stale but always slow". The verdict itself is cached at SessionStart, so this re-check is only for the deny path anyway — not on every call.

## Verdict

**Implementation is sound.** The design correctly:
1. Preserves enforcement for non-pin failures
2. Permits in-session recovery via Edit/Write to doctor.toml
3. Re-validates before denying so repairs take effect immediately
4. Routes pin-only to a distinct state that reports but doesn't enforce

**Mitigate the re-validation latency with a bounded cache (5-10s).**
