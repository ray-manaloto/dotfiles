Repository and installed-plugin claims below are cited to live file lines. ## 1. Ranked list: what to do next

### 1. Do not ship `eaf3cc6`; replace `codex-operator` with a deterministic Claude-side background task runner

**Action:** Retire the proposed full-access reasoning lane and make the already-authorized `mise run <task>` command itself the background job, with its exit status captured directly by the launcher.

**Why this ranks first:** The proposed lane gives a probabilistic model `danger-full-access` for `land`, `automerge`, `sync`, and `verify-local`, then explicitly admits that its only containment is a prompt, “a seatbelt, not a cage” (`eaf3cc6:.claude/agents/codex-operator.md:16-41`). Its job is only to run one named command and relay `EXIT=` (`eaf3cc6:.claude/agents/codex-operator.md:73-108`), so Codex adds no reasoning value but adds an unconstrained mutation principal and another exit-status translation layer. Claude Code already has native background Bash jobs with task IDs and cleanup (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/agent-harness-docs/docs/claude-code/interactive-mode.md:287-306`); the repo also already has a bounded start/wait/reap supervisor pattern (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/scripts/run-lane.sh:171-218`). The plan itself records the motivating failure: a wrapped command exited 2 while the background notification reported 0 (`task_plan.md:1441-1445`). The safe repair is therefore to remove the model boundary, not to grant the model a wider sandbox and ask it to quote an inner status.

### 2. Make the Claude/Fable wrapper the sole commit owner for Codex implementation lanes

**Action:** Keep Codex in `workspace-write`, remove “Then commit on the current branch” from the prompt, and always let the Claude-side settlement step make the scoped commit after captured verification.

**Why this ranks second:** Fable pins the implementation process to `--sandbox workspace-write` (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/scripts/run-lane.sh:84-94`) while its prompt tells Codex to commit (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/agents/codex-implementer.md:89-101`). Today's accepted measurement says that sandbox recursively protects `.git`, so the default path necessarily asks every implementation lane to attempt a denied operation. The same wrapper already contains the correct backstop: after validating branch/ancestry and task scope, it commits uncommitted lane work itself (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/agents/codex-implementer.md:174-176`). Removing the impossible inner commit makes ownership match the actual security boundary without weakening the sandbox. The orchestration doctrine currently repeats the obsolete dual-owner contract (“by the CLI or by the wrapper as backstop”) and should change with it (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/skills/orchestration/SKILL.md:111-120`).

### 3. Prototype one specialty lane on the enabled official Codex companion runtime, then consolidate lifecycle plumbing if the control matches

**Action:** Migrate `codex-advisor` first from its raw shell recipe to a thin role-prompt adapter over `codex-companion`; compare output, sandbox, visibility, cancellation, and failure behavior before extending the pattern to the other three read-only lanes or Fable.

**Why this ranks third:** All four shipped wrappers independently spell fixed prompt/result paths and `codex exec --ephemeral` (representative examples: `.claude/agents/codex-advisor.md:68-103`, `.claude/agents/codex-adversarial-critic.md:69-101`, `.claude/agents/codex-claude-code-expert.md:73-112`, `.claude/agents/codex-staleness-auditor.md:45-82`). Meanwhile, the official `codex@openai-codex` plugin is already enabled (`.claude/settings.json:96-113`) and its own contract says to prefer its helper over direct CLI strings (`/Users/rmanaloto/.claude/plugins/cache/openai-codex/codex/1.0.6/skills/codex-cli-runtime/SKILL.md:11-18`). That runtime natively tracks persistent/resumable threads, background jobs, touched files, command executions, and output schemas (`/Users/rmanaloto/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/lib/codex.mjs:1095-1158`; `/Users/rmanaloto/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/codex-companion.mjs:461-529,671-709,762-823`), duplicating much of the custom tempfile/PID/watchdog surface in Fable (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/scripts/run-lane.sh:84-115,171-218`). This is a prototype, not a blind replacement: the plugin captures inner command exit codes (`/Users/rmanaloto/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/lib/codex.mjs:271-279,480-486`) but still derives its overall result from the Codex turn status (`/Users/rmanaloto/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/lib/codex.mjs:732-755`). Therefore native lifecycle management does **not** by itself fix the wrapped-command-exit problem; that remains an explicit acceptance check.

### 4. Use native Claude managed worktrees for parallel writers, but make base selection and ignored-file exposure explicit

**Action:** Route concurrent implementation subagents through `isolation: worktree`, explicitly choose `worktree.baseRef` for this repo's feature-branch fan-out, and create `.worktreeinclude` only for ignored files that are safe and correct in **every** Claude-created worktree.

**Why this ranks fourth:** Claude natively creates, locks, isolates, and eventually cleans temporary subagent worktrees (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/agent-harness-docs/docs/claude-code/worktrees.md:81-136`), and `isolation: worktree` is a supported subagent field (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/agent-harness-docs/docs/claude-code/sub-agents.md:286-305`). Fable currently describes worktree isolation only as a caller-selected heavy-fan-out technique (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/skills/orchestration/SKILL.md:133-139`). The missing correctness decision is the base: native subagent worktrees default to the repository's default branch, not the caller's current `HEAD` (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/agent-harness-docs/docs/claude-code/worktrees.md:98-117`), so a lane dispatched from an unmerged feature branch can silently start without its prerequisite commits unless `worktree.baseRef` is deliberately set. Absence probe: `rg -n 'worktree|baseRef|bgIsolation' .claude/settings.json .claude/settings.local.json` returned zero matches; the same-shape control `rg -n 'enabledPlugins' ...` found `.claude/settings.json:96` and `.claude/settings.local.json:3`.

The plan's `.worktreeinclude` recommendation is directionally useful but over-broad and assigns it to the wrong lifecycle layer **for the Fable use case**: Claude Code applies the file to **every** worktree it creates, including subagent worktrees (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/agent-harness-docs/docs/claude-code/worktrees.md:179-195`), whereas Phase 17 calls it simply a native Codex feature and treats per-spec provisioning as redundant (`task_plan.md:1422-1425`). Fable's per-spec copying still has a legitimate role for secrets because it intentionally makes the architect decide what a vendor CLI may read (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/skills/orchestration/SKILL.md:133-137`). In this repo, the obvious ignored candidate `mise.local.toml` can pin a collision-prone SSH port and select a Doppler config (`.gitignore:32-34`; `mise.local.toml.example:15-31,35-46`), so copying it globally without a field-level decision would trade missing-config failures for cross-worktree port collisions or unnecessary secret exposure. Absence probe: `rg --files --hidden --no-ignore -g '.worktreeinclude' .` returned zero paths; the same-shape control with `-g '.gitignore'` found the root `.gitignore` and plugin-cache controls.

Codex Desktop's native managed worktrees are real, but they are a **separate surface** from these Claude-launched CLI lanes (official Codex documentation snapshot: `https://learn.chatgpt.com/docs/environments/git-worktrees:805-946`, including `.worktreeinclude` at `:885-905`). The repo's own parity module says Desktop consumes the TOMLs while the wrapper's `codex exec` stdin path does not read them (`python/src/dotfiles_setup/codex_agent_parity.py:14-19`), and the four wrappers visibly launch raw CLI processes (for example `.claude/agents/codex-advisor.md:68-92`). Therefore a Codex-app managed worktree does not automatically isolate or provision a Fable/Codex CLI subprocess launched by a Claude subagent; the outer Claude lane must use Claude's managed worktree, after which the nested Codex process remains subject to its own sandbox.

### 6. Remove the invalid `--full-auto` recipe and stop treating copied CLI strings as the canonical interface

**Action:** Correct the immediate implementation example, then make the rule route project lanes through the official helper (or an executable version-gated launcher) rather than declaring prose examples to be the reference.

**Why this ranks sixth:** The live policy still tells implementers to run `codex exec --full-auto --sandbox workspace-write` (`.claude/rules/ai-cli-invocation.md:11-24`) even though Phase 17 records that 0.152.0 rejects the flag (`task_plan.md:1420-1423`). ## 3. What the plan is missing for this theme

1. **A decision that `codex-operator` should not be a Codex lane at all.** Phase 17 records the sandbox facts and the unshipped branch but not the architectural consequence (`task_plan.md:1432-1434,1452-1457`): because the proposed role's only boundary is prompt text (`eaf3cc6:.claude/agents/codex-operator.md:35-55`), the native replacement is a deterministic background command job, not a fifth reasoning role.

2. **The Fable commit-ownership contradiction.** The plan records that workspace-write cannot write Git metadata (`task_plan.md:1432-1434`) but does not connect that fact to Fable telling Codex to commit (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/agents/codex-implementer.md:89-101`) before its Claude wrapper performs a backstop commit (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/agents/codex-implementer.md:174-176`). That causal link is the highest-frequency defect in the current implementation lane.

3. **The enabled official Codex runtime as the native consolidation target.** The plan discusses raw CLI flags and Fable's custom launcher but never compares them with the already-enabled `codex@openai-codex` runtime (`.claude/settings.json:96-113`), which provides persistent threads, background-job records, touched files, command execution records, and structured outputs (`/Users/rmanaloto/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/lib/codex.mjs:1095-1158`; `/Users/rmanaloto/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/codex-companion.mjs:671-709,762-823`).

4. **Managed-worktree base semantics.** The plan mentions copying ignored files but omits that native subagent worktrees branch from the default branch unless configured otherwise (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/agent-harness-docs/docs/claude-code/worktrees.md:98-117`). It also omits that `.worktreeinclude` is global to all Claude-created worktrees (`/Users/rmanaloto/dev/github/ray-manaloto/knowledge-base/sources/agent-harness-docs/docs/claude-code/worktrees.md:179-195`), so it cannot safely replace Fable's per-spec secret decision wholesale (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/skills/orchestration/SKILL.md:133-137`).

5. **Runtime semantics in `codex_agent_parity`.** The plan treats “4 -> 5 lanes” as parity work (`task_plan.md:1452-1457`), but the checker enforces pairing, identity, effort, model, and a no-substitute sentence—not sandbox, lifecycle, output isolation, structured results, or wrapped-command evidence (`python/src/dotfiles_setup/codex_agent_parity.py:102-121,155-207,270-345`). A fifth pair can be structurally valid while being operationally unsafe.

6. **Same-lane concurrency collisions in the four hand-authored wrappers.** Their prompt and result paths are fixed per role (examples: `.claude/agents/codex-advisor.md:80-92`, `.claude/agents/codex-adversarial-critic.md:79-91`, `.claude/agents/codex-claude-code-expert.md:89-102`, `.claude/agents/codex-staleness-auditor.md:56-68`), so two concurrent calls to the same role in one checkout can overwrite each other's input or verdict. Fable's own wrapper explains why it uses unique prompt files: parallel lanes on fixed paths corrupt one another (`/Users/rmanaloto/.claude/plugins/cache/fable-orchestrator/fable-orchestrator/1.21.0/agents/codex-implementer.md:44-48`).

7. **A measured choice about `--ephemeral`.** All four specialty wrappers force ephemeral sessions (`.claude/agents/codex-advisor.md:87-91`, `.claude/agents/codex-adversarial-critic.md:86-90`, `.claude/agents/codex-claude-code-expert.md:97-101`, `.claude/agents/codex-staleness-auditor.md:63-67`), while the official companion intentionally persists task threads for resume (`/Users/rmanaloto/.claude/plugins/cache/openai-codex/codex/1.0.6/scripts/codex-companion.mjs:461-495`). **UNVERIFIED:** whether removing `--ephemeral` changes Codex Desktop/AgentsView visibility or introduces unacceptable session-store overhead was not runtime-probed in this review. The plan should require that side-effect/control-arm measurement before standardizing either behavior.

## 4. Single highest-value next action

**Do not ship `eaf3cc6`; replace `codex-operator` with a deterministic Claude-side background runner that executes the one authorized `mise` task and returns that process's captured exit status directly.**
