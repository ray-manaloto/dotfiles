### 2. [MEDIUM] `STATUS: complete` definition contradicts the dissent-classification rule

`codex-sol-implementer.md:276-277` (closing section, "What you return"):

> `complete` means signal 1 with `rc=0` and a non-empty `$OUT`. Everything
> else is one of the other four statuses with the evidence attached.

This is stated as the operative definition, with no mention of *content*.
But `codex-sol-implementer.md:98-105` ("Refusing is a success, not a
failure") requires the opposite classification for the same observable
state:

> when its report says which two sections disagree, or which gate the
> instruction would fail, relay that as `STATUS: dissent` — it is a
> completed run, not a failure

A codex refusal is very plausibly still `rc=0` with a non-empty `$OUT` — codex
successfully produced a final message, the message's *content* just says "I
refuse to implement this." That satisfies the literal `complete` test
(line 276) exactly as well as a real implementation does. Nothing in the file
says "inspect `$OUT`'s content for a refusal before applying the `complete`
rule," and the two sections are ~180 lines apart, so a supervisor mechanically
applying the closing definition (the more "final-word"-sounding of the two)
could label a dissent `complete` — silently reporting a refusal as a
successful implementation. That is precisely the "failure that looks exactly
like success" pattern the same document calls out elsewhere (lines 236-238,
re: backfilling a failed gate).

Fix direction: state explicitly that `$OUT`'s content must be checked for a
refusal shape before `rc=0` + non-empty `$OUT` is read as `complete`, or fold
the ordering into the `complete`/`dissent` bullets directly.

### 3. [MEDIUM] Timeout-budget arithmetic doesn't bound what it claims to bound

`codex-sol-implementer.md:195-201`:

```bash
deadline=$((SECONDS+540))
while [ $SECONDS -lt $deadline ]; do grep -q '^rc=' "$LOG" && break; sleep 15; done
```

with the framing at line 195-196: "One slice per Bash call, each under the
600 s cap, as many as the budget allows — `ceil(TIMEOUT / 540)`, four for the
default 1800 s."

The per-slice deadline is **hardcoded** at `SECONDS+540`, independent of
`TIMEOUT`; only the slice *count* is derived from `TIMEOUT`. Consequences:

- For the documented default (`TIMEOUT=1800`): `ceil(1800/540)=4`, so signal 3
  ("slices exhausted") cannot fire before `4 × ~540s ≈ 2160s` — roughly 20%
  past the stated 1800s budget the calculation implies it enforces.
- For any `TIMEOUT < 540` (a spec author is free to set this — the file gives
  no floor), `ceil(TIMEOUT/540)=1`, so a single slice alone can run the full
  ~540s before the "slices exhausted" check even applies — several times the
  stated budget.

The `ceil(TIMEOUT/540)` framing reads as though it yields a precise timeout;
it only bounds the slice *count*. Not unsafe — the error is in the direction
of more patience, consistent with "A SLOW lane is not a FAILED lane"
(line 41) — but the documented number and the actual mechanism disagree, in a
file whose entire ethos is exact, checkable arithmetic (`ceil(TIMEOUT / 540)`
stated as if authoritative elsewhere in the same paragraph).

### 4. [MEDIUM] "Relaunch ONCE" on early death is unspecified and can self-defeat

`codex-sol-implementer.md:207-211` (signal 2, the process died without
writing `rc=`):

> If this happens inside the first minute with a clean `git status`, relaunch
> ONCE with the identical spec and say so in the report

Unlike every other actionable instruction in this file, this has **no code
block**. It's ambiguous whether "relaunch" means redo the whole numbered
procedure from "1. Claim the lane's files" or skip straight to "2. Launch
codex" reusing the already-known `$PROMPT`/`$OUT`/`$LOG`. The literal
reading — redo step 1 — recreates the exact `( set -C; : > "$OUT" )` guard at
line 140, which uses `noclobber` specifically to *refuse* a path that already
exists. `$OUT` was already created (even if still empty) by the first,
crashed attempt, so re-running the claim step would immediately print
`refusing: $OUT already claimed` and abort — defeating the one recovery path
this branch exists to provide. The correct action (skip to step 2, reuse the
existing paths) is inferable from the surrounding "shell variables don't
survive between calls, re-assign from the printed literals" guidance
(lines 151-153), but it is not stated for this specific branch, in a document
that otherwise treats every action as literal, copy-pasteable bash.

### 6. [LOW — design observation, not a proven functional defect] Core new rule is enforced by prose only

`codex-sol-implementer.md:23-28` and `:246`: "You never edit a repository
file. Not with `Edit` (you do not have it), and not through Bash either — a
heredoc into a tracked path, `sed -i`, `>` or `>>` into anything outside
`.agent/kb/raw/` is editing." This is the commit's central fix, directly
responding to a measured incident (lines 30-39) where the prior wrapper
ignored an equivalent (weaker) instruction and edited files via Bash anyway.
The fix is entirely prompt-level — stronger, more repeated wording, plus a
model upgrade (`haiku` → `sonnet`) — with no new *mechanical* backing (e.g., a
`PreToolUse` hook scoped to this subagent denying `sed -i`/heredoc-into-
tracked-path/etc., in the style of this repo's other hard invariants such as
`branch_guard` or the `secrets-out-of-the-shell-env.md` `Read()`/`Bash()`
deny-list). `hook_guard`-style enforcement is technically available for this
subagent's *own* Bash calls (unlike a codex lane's internal shell use, which
is genuinely invisible to Claude Code hooks per `codex-sdlc-team.md`) but
isn't used here. The self-check this file does rely on — cross-referencing
`git status --short` against codex's own report (lines 251-252, 269) — is
performed by the same agent that is the risk being guarded against, which is
weaker than an independent check by the coordinator. This is consistent with
this repo's own stated doctrine elsewhere
(`.claude/rules/mise-tasks-only.md`: "markdown alone is 'relying on the
LLM', never the only layer") but I'm flagging it as a design gap, not a
proven bug — the fix may well be sufficient given the model upgrade and the
much-clarified role framing.
