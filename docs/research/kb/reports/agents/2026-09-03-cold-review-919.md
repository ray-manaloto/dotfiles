## F1 (HIGH, LIVE TODAY) — `check_settings_wiring` matches per-EVENT, never per-ENTRY: an unrelated hook satisfies another hook's requirement

`python/src/dotfiles_setup/hook_selfcheck.py:192` (`joined = "\n".join(...)`)
and `:207` (`tokens = {... for m, _ in entries ...}`) both collapse EVERY entry
of an event into one blob. Requirements are then checked against the blob, so
a required matcher token can be supplied by an entry that does not carry the
required command, and vice versa.

`.claude/settings.json` already has THREE `PreToolUse` entries
(`pretooluse-guard.sh` @ `Bash|AskUserQuestion|Edit|Write|NotebookEdit`,
`graphify-hook-guard.sh search` @ `Bash|Grep`, `graphify-hook-guard.sh read` @
`Read|Glob`), so this is not hypothetical.

Probes (real `.claude/settings.json`, mutated in memory, `check_settings_wiring`):

| Probe | Mutation | Result |
|---|---|---|
| baseline | none | `[]` |
| A | pretooluse-guard matcher -> `AskUserQuestion\|Edit\|Write\|NotebookEdit` (drops `Bash`) | `[]` **PASS — guard unwired for Bash** |
| B | mise-config-context matcher -> `Write`, plus a 2nd PostToolUse entry matching `Edit\|Write\|NotebookEdit` | `[]` |
| C | mise-config-context matcher -> `""` (fires on EVERY tool), plus a 2nd entry supplying the tokens | `[]` |
| D | guard command moved onto the `Bash\|Grep` graphify entry, guard entry given web-setup.sh | `[]` |

Failure scenario for A: someone tidies the guard's alternation (or a rebase
collapses it) so it no longer names `Bash`. Every mise-tasks-only Bash redirect
(`gh pr create`, `--no-verify`, backgrounded `mise run`, the head/tail gate rule)
stops firing. `mise run lint`, pytest, `verify`, `ship`, `land` and
`hook-selfcheck` all stay green: `test_real_settings_wiring_passes` passes,
and `check_pretooluse_endtoend` invokes `scripts/pretooluse-guard.sh` by path,
which never reads the matcher. This is #343 reproduced with a green gate — the
exact class the module's own comment at `:60-71` claims to close.

Probe C is the pointed one for THIS change: the new row's comment
(`:117-119`) says "The matcher is scoped, not None: an unscoped PostToolUse
would fire the dispatcher after EVERY tool call" — the check cannot detect
that once a second PostToolUse hook exists, which is a likely near-term
addition (a formatter, another observer).

Fix shape: require the matcher tokens on the entry (or entries) whose command
carries the required substring, i.e. pair `(matcher, cmd)` rather than
flattening.

So "pytest … green" is false, and pytest is itself a ship/land gate. This
matters beyond pedantry: the comment is the row's whole justification, it is
the sentence a future reader will trust when deciding whether this row is
load-bearing, and it is the kind of inherited-unverified claim
`probes-need-a-control-arm.md` rule 6 exists for.

**What the row DOES genuinely add** (and what the comment should say instead):
the pre-existing test's matcher assertion is `any("Write" in m and "Edit" in m
for m in matchers)` — substring containment, and `"Edit" in "NotebookEdit"` is
True. So the old test cannot see a matcher narrowed to `Write|NotebookEdit`;
the new row's alternation-token check can. That is the real, non-redundant
delta, and `test_post_tool_use_dropping_one_matcher_token_fails` is the one new
test that proves something the repo did not already prove.

**What the row silently does NOT carry over** from the pre-existing test: the
`"mise run" not in command` invariant (the hook must not depend on a mise.toml
task, since a wholesale Write of `mise.toml` would delete the task before
PostToolUse could run it) and the non-empty-`timeout` invariant. Those remain
pytest-only.

## F3 (LOW-MEDIUM) — a pre-existing negative assertion is no longer event-scoped, so it can now go red for the wrong reason

to be required on any other event today. Fix: scope the negative assertions to
the event, e.g. `not any("PreToolUse" in f and "'Write'" in f …)`.
