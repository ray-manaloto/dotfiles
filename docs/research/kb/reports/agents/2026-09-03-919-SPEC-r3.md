## 1. Objective

The invariant that actually matters is: **the specific hook entry we care about
is wired, AND it carries the tool scope we require.** Both round-1 and round-2
approximated that with pooling — first across all entries of an event, then
across "owning" entries — and pooling is exactly what lets one entry launder a
requirement for another.

Three things measured against the REAL `.claude/settings.json`, each with a
control arm:

- **The command half of `3ac54a5` is a provable no-op.** `owners` is defined as
  "entries whose command contains at least one required substring", so any entry
  that could contribute a required token IS an owner. Filtering the command
  check by ownership is a tautology. Evidence: reverting `joined` to `entries`
  while keeping `tokens` scoped leaves 29/29 tests passing; reverting `tokens`
  alone fails 1. Only the matcher half ever carried the fix.
- **The class is live on the COMMAND axis.** Split `SessionStart` into
  `{matcher: "startup" -> web-setup.sh}` and
  `{matcher: "resume" -> tool-currency-check; doctor}`, and
  `check_settings_wiring` returns GREEN. On a `startup` session the #418 project
  doctor and the tool-currency check never run — and this module's own comment
  at `:81-85` records that settings.json is the ONLY place either is wired.
  `SessionEnd` has the same shape (`run command-audit` in one entry, the
  `--output ...command-audit.md` argument in another).
- **The class is live on the MATCHER axis, across owners.** Ownership is
  substring containment IN THE COMMAND, so an entry that merely MENTIONS the
  command donates its matcher tokens. Narrow the real guard entry to
  `"matcher": "Bash"` and add
  `{matcher: "AskUserQuestion|Edit|Write|NotebookEdit", command: 'echo "disabled: .../pretooluse-guard.sh" >/dev/null'}`
  -> GREEN, with `ask_quality` and `branch_guard` (#400) silently absent while
  ship, land and hook-selfcheck all pass. Control arm: the same narrowing
  WITHOUT the decoy -> RED, so the probe discriminates.

## 4. Constraints and invariants

C1. **The pinned rule.** For each `_SETTINGS_WIRING` row, the event passes iff
    **at least ONE SINGLE entry** satisfies BOTH:
    - its command contains every required substring in the row, AND
    - its matcher's alternation tokens include every required matcher token.

    No pooling across entries, in either direction. Remove the `owners` /
    `scoped` / fallback machinery from `3ac54a5` entirely — it is superseded,
    its command half was a no-op, and its fallback comment (see C4) describes
    behaviour it does not have.

    I verified this rule before specifying it: simulated against the real
    `.claude/settings.json` it is **GREEN**; against the split-SessionStart
    shape **RED**; against the decoy-donation shape **RED**.

C2. **Deliberate, documented trade-off.** This rule rejects a *legitimate* shape:
    one logical hook split across two entries carrying the same command with
    complementary matchers (e.g. `Bash` -> guard.sh plus
    `AskUserQuestion|Edit|Write|NotebookEdit` -> guard.sh). That is functionally
    equivalent to a single merged entry and is NOT in use today. Say so in the
    comment: if such a split is ever wanted, merge the entries or change the row
    — do not reintroduce pooling. A gate that accepts "some combination of
    entries covers it" cannot distinguish that shape from the laundering ones
    above, and the laundering ones are the reason this module exists.

C3. **Failure messages must stay actionable, and must keep their current
    shapes** — existing tests assert them as substrings:
    - a required command substring no candidate entry carries ->
      `settings.json {event} hook is missing {token!r}`
    - a required matcher token missing ->
      `settings.json {event} hook must be scoped with matcher {matcher!r} ...`
    - no entry at all -> `settings.json has no {event} hook wired`

    When no single entry qualifies, report against the CLOSEST candidate (the
    entry carrying the most required substrings) so the message names what to
    fix rather than dumping every entry's shortfall. Preserve alternation-token
    membership for matchers — never substring containment (`Edit` is a substring
    of `NotebookEdit`).

C4. **F3 — delete the invented rationale.** The comment at
    `hook_selfcheck.py:209-211` claims the fallback exists "so a missing command
    still reports missing rather than silently passing or crashing". Both halves
    are false: with an empty owner set `joined == ""`, so every required token is
    already reported missing. I confirmed it — pointing the PostToolUse command
    at a nonexistent script returns RED via the missing-substring failure. The
    fallback only ever suppressed redundant matcher failures. It is going away
    with the rest of the machinery; do not carry its rationale forward into the
    new comment. State what the new rule does and why, and nothing you have not
    checked.

C5. **F1 — the "scope BOTH checks" claim goes too.** Whatever comment you write
    must not repeat it. The honest statement is the C1 invariant.

C6. **F4 — two new test comments have their direction backwards.**
    - `tests/test_hook_selfcheck.py:134-138` is a non-sequitur: it argues that
      because PostToolUse requires `'Bash'` nowhere, an unscoped check would pass
      for the wrong reason — but if nothing else requires it, the unscoped form is
      equivalent.
    - `:167-171` attaches the laundering argument to the NEGATIVE assertion
      (`assert not any(...)`); narrowing the set that assertion scans makes it
      EASIER to satisfy, i.e. weaker, and can only prevent a future false RED.
      The real laundering risk is on the POSITIVE assertion one line above
      (`:166`, `any("'Edit'" in f ...)`), because PostToolUse does independently
      require `'Edit'`.
    Fix both comments to say what the filtering actually buys, and attach the
    laundering argument to the assertion it applies to.

C7. **Cover the axis that has ZERO coverage today.** Round 2 proved it: replacing
    the token union with a per-owner intersection left 29/29 passing, because
    `_full_settings_with_graphify_pretooluse` has exactly one owner and one

    - **multi-owner matcher laundering** — two entries both carrying the required

    - **command-axis splitting** — an event's required substrings split across two

    - **the control arm** — a single entry carrying the command and the full
      matcher -> green, so neither test is merely always-red.

C8. **Mutation-prove the new tests before you report.** Revert the C1 rule to
