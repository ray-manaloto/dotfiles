## Short answer

**No, `task_plan.md` did not need to move. The repo never migrated to `.planning/` as a practice.** A codex lane created one named plan. In pwf, a root `task_plan.md` is the default single-task layout: the docs call it "legacy" but never deprecate it. `.planning/<slug>/` is for running several tasks in parallel. Mixing the two layouts is what breaks things: any `.planning/<slug>/task_plan.md` silently wins over the root plan. That is exactly what happened last session.

## 1. What the plugin's own docs and code say

### Layout
- **Root is the default.** README `$P/3.20.5/README.md:110-119` shows the root `task_plan.md` / `findings.md` / `progress.md` tree, then: "Parallel tasks get isolated directories instead: `.planning/YYYY-MM-DD-slug/` with the same three files, selected via `.active_plan` (v2.36.0+)."
- SKILL.md `$P/3.20.5/skills/planning-with-files/SKILL.md:76` says: "Selected task directory (project root in legacy mode)".
- SKILL.md:225: `init-session.sh` with a name creates `.planning/YYYY-MM-DD-<slug>/`. Without arguments it writes root `task_plan.md` ("legacy mode, backward-compatible").
- The `/plan` command (`$P/3.20.5/commands/plan.md`) still creates the files "in the current project directory", i.e. at the root.
- **Root is not deprecated.** I searched README, MIGRATION.md, docs/*.md, SKILL.md and commands/*.md with one command shape. `deprecat` matched 0 files and `obsolete` 0 files. Control: `legacy` matched 13 files and `backward` 2, so the search works.

### Version history
- `.planning/` arrived in **v2.36.0 (2026-05-01)**: CHANGELOG `$P/3.20.5/CHANGELOG.md:1228`, "Legacy zero-argument behavior is unchanged."
- v2.40.0: "hook resolution order inverted so slug-mode wins over legacy root" (README:398).
- v3.17.1 (#240): two named plans without `PLAN_ID` means nothing is injected (README:362).

### How the resolver picks the plan (`$P/3.20.5/scripts/resolve-plan-dir.sh`)
- **Order** (header lines 4-8): `$PLAN_ID`, then `.planning/.active_plan`, then the newest `.planning/<dir>/` by mtime, then empty. Empty means the caller falls back to root `./task_plan.md`.
- `PWF_PLAN_ROOT` is an absolute pin that fails closed (:39-52).
- A set `PLAN_ID` is a binding and never falls back to another plan (:315-338, #237).
- The newest-mtime scan only counts directories containing a file literally named `task_plan.md`. It skips hidden, symlinked and invalid names (:285-313).
- More than one named plan with no `PLAN_ID` means no plan is selected (:342-361). The root plan only joins that count when `.planning/sessions/` exists.
- SKILL.md:42: "A root `task_plan.md` must not override a selected `.planning/<id>/` plan." **So one named plan beats the root plan even without an `.active_plan` pointer**, through the mtime scan.
- The installed 3.17.2 SKILL.md carries the same lines (42, 225).

### Start, switch, archive
- **Start:** `init-session.sh ["<name>"]` (SKILL.md:225). `/pwf [--gated|--autonomous] [name]` is documented for the other hosts (README:608-628).
- **Switch:**
  - `set-active-plan.sh <id>` moves one shared pointer; it is for switching sequentially.
  - `--list` is read-only (SKILL.md:226, :235-257).
  - Concurrent sessions must have `PLAN_ID` set in the host environment *before* the agent starts, or use separate worktrees (SKILL.md:239-257).
- **Archive: there is no native archive step.** `docs/workflow.md:115-127`: "nothing archives them when a task finishes. In root mode the next task overwrites `task_plan.md`; in slug mode the old directory just stops being the active plan… not built in today." That file also suggests un-ignoring `.planning/` if you want plans tracked (:124).
  - Control: `archived` appears only in that prose, while `active_plan` is found in scripts.
  - So this repo's rename to `task_plan.archived.md` is ad hoc. It only works because the resolver needs the literal filename.
  - For contrast, knowledge-base moves finished plans into `.planning/.archive/<id>` (a hidden directory the resolver skips): `knowledge-base/.claude/skills/clear-prep/references/plan-archive.md:16-36`.

### Attestation is a native feature
- `/plan-attest` or `scripts/attest-plan.sh` shipped in v2.37.0 (CHANGELOG:1149; SKILL.md:230, :470-472).
- It stores a SHA-256 of `task_plan.md` in `.planning/<active>/.attestation` (named plan) or `./.plan-attestation` (root).
- Every hook fire recomputes the hash. A mismatch prints `[PLAN TAMPERED — injection blocked]`, and injected context carries a `Plan-SHA256:` line.
- It is opt-in for root plans. In v3 autonomous/gated modes it is on by default at init, and those modes refuse to inject an unattested plan (SKILL.md:481).
- SKILL.md:470 caveats: the digest is "not a keyed signature", and auto-attestation at init "is not proof of human review".

### Does the repo's `plan_attest.py` duplicate it?
**No.** `python/src/dotfiles_setup/plan_attest.py:166-188` only shells out to the plugin's script (`subprocess.run(["sh", script, *args])`). It adds an operator-only path and an argparse `--` fix (:86-133). The only real overlap problem is the version mismatch in section 0.

**Divergences from the canonical setup**
1. dotfiles is 9 releases behind (3.17.2 vs 3.20.5), and the hooks and the attest wrapper run different versions.
2. Both layouts exist at once. A lane can create a named plan that silently shadows the root plan (SKILL.md:42).
3. The root plan is a 90 KB multi-program ledger ("supersedes the 2026-09-09 program", 31 headings). pwf's model is working memory for one task, overwritten by the next (`docs/workflow.md:117-119`).
4. The `task_plan.archived.md` rename is not a pwf convention (see section 1).
5. `plan-pointer.json` and handoff-check hard-code root `task_plan.md`, so they would break under a named-plan layout.
6. `/.active_plan` in `.gitignore:147` is not a pwf path; pwf uses `.planning/.active_plan` (resolver :25, :54).
7. The `.gitignore:137-142` comment says the plugin "hardcodes the project root". That has been stale since v2.36.0, though pwf still cannot point at `.agent/`.
8. Not every codex spawn path sets `PLANNING_DISABLED`, while codex's pwf plugin is enabled globally.
9. The tracked root `.mode = autonomous` quietly raises every new named plan to autonomous with auto-attestation.
10. The plan files are big: the injection is 12.8 KB per prompt, and hook latency is near or over the 10 s timeout.

## 5. Recommendation

**Option A (recommended): keep the root layout, and make it the only layout.**
1. Update the dotfiles project install to 3.20.5 (command in section 3) and restart. Re-run `plan-doctor` and `mise run plan-attest -- --show` so the hooks and the wrapper are on the same version.
2. Stop lanes creating named plans:
   - set `PLANNING_DISABLED=1` on every codex spawn path, including `sdlc_team.py`, not just `codex_lane.py`;
   - or disable codex's pwf plugin for this project.
3. Deal with the stale `.planning/2026-09-21-…/` directory: delete it, or move it to `.planning/.archive/`, the hidden directory the resolver skips. The plugin docs name no location.
4. Bring the plan back to pwf's model: one task's working memory. Move program history, goals and phase ledgers into tracked docs (goal-history, specs), and cut the three root files down. That also shrinks the 12.8 KB injection and the near-timeout hook.
5. Clean up the `.gitignore` comment and the `/.active_plan` line.

Why A: `/plan` and a no-argument init both default to the root; the repo has one coordinator writer; and plan-pointer/handoff tooling already assume the root.

**Option B: named plans.**
1. Run `init-session.sh "<task>"` and move the root contents into `.planning/<date>-<slug>/`.
2. Remove the root `task_plan.md`, otherwise it can be read by mistake.
3. Point `.active_plan` at it with `set-active-plan.sh`.
4. For concurrent sessions, set `PLAN_ID` in the host environment before launch, or use worktrees.
5. Re-attest; the file moves from `.plan-attestation` to `.planning/<id>/.attestation`.
6. Update everything that hard-codes the root path:
   - `plan_pointer.py:17` (resolve the plan through the resolver instead) and `handoff_check.py`
   - the session-handoff/resume skills
   - `.claude/rules/agent-report-persistence.md` and `notepad-enforcement.md`
   - the SubagentStart hook text in `settings.json` and `hook_selfcheck`'s required tokens
   - `pwf-scribe` and the codex agent definitions (26 tracked files mention `task_plan.md`)
   - `suites.toml:1708+`
