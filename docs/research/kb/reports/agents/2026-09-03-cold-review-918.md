## HIGH

### H1 — `_strip_frontmatter` is entirely uncovered; the test that names it CANNOT fail

`rule_registry.py:120-129` · `tests/test_rule_registry.py:394-411`

Two independent arms prove it:

1. **Mutation.** Replacing `_strip_frontmatter` with a no-op (returns the full text,
   frontmatter included) leaves the suite at **27 passed, rc=0**. Every other mutation
   I ran killed at least one test (`no_fence` → 1 failed, `no_eager_reason` → 4,
   `inject_empty` → 1, `no_symlink_recurse` → 1, `heading_any` → 5). This one is the
   sole survivor.
2. **Poison.** Replacing `_find_eager_reason` with a function that raises on call, then
   running `test_setext_frontmatter_boundary_is_not_a_phantom_heading` alone → **rc=0**.
   The function is *never invoked* on that fixture's code path.

Root cause: the test's fixture carries a `paths:` list, so `_build_record` returns on
the **scoped** branch (`rule_registry.py:231-242`) before `_find_eager_reason` is
reached. Its assertions `eager_reason is None` / `eager_reason_heading is None` are true
by construction for every scoped record, forever. It is a tautology wearing the name of
the hazard it claims to cover.

Compounding: the docstring's stated reason for the function
(`rule_registry.py:122-124`, "so the closing `---` never masquerades as a **setext H2
underline**") describes a hazard the parser is structurally immune to — `_ATX_HEADING_RE`
(`:55`) matches ATX headings only; there is no setext detection anywhere in the module.
The *real* thing stripping buys is different and untested: a `#`-prefixed **YAML comment**
inside frontmatter reading as an ATX heading. Probed —

```
fixture: ---\n# Why this rule is eager: a YAML comment\ntitle: x\n---\n\n# Real Title\n\nreal body
stripped (current): eager  heading=None  reason=None
unstripped        : eager  heading='# Why this rule is eager: a YAML comment'  reason='title: x\n---'
```

So the code is correct and the comment explaining it is wrong, and nothing guards either.

**Fix shape:** the covering test must use a fixture that reaches the eager branch —
frontmatter *without* a `paths:` list, plus a `#` line inside the frontmatter.

### H2 — A non-UTF-8 rule file crashes `build_registry`, contradicting the module docstring

`rule_registry.py:181-196` · docstring claim at `rule_registry.py:28-31`

The docstring states: *"this module never silently drops a rule it cannot parse or read:
malformed frontmatter and an unreadable file both become `load_class == "malformed"`
records (C3)"*. Only `OSError` is caught. `Path.read_text` raises `UnicodeDecodeError`
on invalid UTF-8, which is a `ValueError`, **not** an `OSError`.

Probed with `b"---\npaths:\n  - \xff\xfe\n---\n\nbody\n"`:

```
registry:             RAISED UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 15
scoped_rules_on_disk: RAISED UnicodeDecodeError  (control arm: the pinned sibling fails identically)
```

One un-decodable byte anywhere in `.claude/rules/` takes down every consumer
(#927 gate, #928 dispatcher) with an unhandled traceback rather than one `malformed`
record. It also takes down `test_three_classifiers_agree_on_the_real_corpus`, which
calls `read_text` directly at `tests/test_rule_registry.py:284`.

Note this is a *worse* outcome than the swallow it replaces: `scoped_rules_on_disk`
also crashes, so C1 parity is preserved — but the module's advertised improvement
("never silently drops") is not delivered for this input class.

### H3 — `rglob_corpus == gate_corpus` fails on any untracked rule file (git-state dependent)

`tests/test_rule_registry.py:295-306`

`tracked_files()` is `git ls-files`; `rglob` is the working tree. Any untracked `.md`
under `.claude/rules/` makes them unequal. Control-armed:

```
touch .claude/rules/zzz-untracked-probe.md   → rc=1, FAILED test_three_classifiers_agree_on_the_real_corpus
rm   .claude/rules/zzz-untracked-probe.md    → rc=0   (control: green again)
```

This fires during the *normal authoring workflow for a new rule* — write the file, run
the tests, then stage. It also fires on a staged-delete-not-yet-removed and in any
checkout without git available. The failure message will point at classifier
disagreement, which is not the cause; the docstring at `:247-255` explicitly instructs
the reader that a failure here means "the corpus moved under us … a finding to report",
which will mis-triage this.

Also breaks: `test_rule_id_matches_declared_rules_stem_spelling` (`:535-544`) and
`test_real_corpus_*` (`:414`, `:428`, `:444`) all read the live corpus, so any rule
file added, deleted, or re-headed in an unrelated PR reds this suite.

## MEDIUM

### M1 — Three fence shapes corrupt the eager-reason section

`rule_registry.py:60`, `151-156`

`_FENCE_RE` toggles on any line whose stripped form starts with ` ``` `. Probed
outcomes (`probe2.py`):

| fixture | result | correct? |
|---|---|---|
| **unclosed fence** inside the section | reason runs to EOF, swallowing `## Applies to` and its body | no |
| **`~~~` fence** containing `## not a heading` | section **truncated** at the fake heading; the real `## Next` boundary is never reached | no |
| prose line starting with ```` ```` ```` (a literal) | fence opens, never closes → swallows `## Next\n\nNOT-REASON` | no |
| ```` ```text ```` closing line | treated as a close (CommonMark: opens a new fence) | benign here |

The docstring at `:58-59` claims *"nested fence depth is not tracked because markdown
fences don't nest"*. That is false — a 4-backtick fence legitimately contains
3-backtick fences, and an odd number of inner fences desynchronises the toggle. The
even-count case I probed happened to survive.

Current corpus is clean (all 26 `.claude/rules/*.md` have balanced ` ``` ` counts, zero
`~~~` fences), so this is latent, not live. It becomes live the first time someone
documents a `~~~` block or a fence-in-a-fence in a rule.

### M2 — `globs` is not validated; non-string items pass through, dict items make the record unhashable

`rule_registry.py:236` (`globs=tuple(front["paths"])`), annotation at `:91`

```
paths: [1, 2.5]      → globs == (1, 2.5)        # annotation says tuple[str, ...]
paths: [{a: b}]      → globs == ({'a': 'b'},)   # hash(record) → TypeError: unhashable type: 'dict'
```

`RuleRecord` is `@dataclass(frozen=True)` (`:81`), so it advertises hashability;
`hash()` raises on the dict case. Any consumer that puts records in a set or dict key —
a natural thing for a "registry" — crashes on a malformed-but-YAML-valid rule. And a
downstream glob match against `1` is a `TypeError`, not a classification error.

### M3 — `by_id` silently returns the first of colliding ids

`rule_registry.py:108-113`, id derived from `path.stem` at `:178`

Nested subdirectories are a supported traversal (`test_recurses_into_nested_subdirs`,
`:502`; `scoped_rules_on_disk`'s R8 docstring calls them "a documented sharing
mechanism"). `rule_id` is therefore **not unique**. Probed:

```
records: [('dup', '.claude/rules/dup.md', ('top.pkl',)),
          ('dup', '.claude/rules/shared/dup.md', ('nested.pkl',))]
by_id('dup') -> .claude/rules/dup.md ('top.pkl',)     # the nested rule is invisible
```

`RuleRecord`'s docstring calls itself "One `.claude/rules/*.md` file's parsed identity"
(`:83`) and pins the field names for #927/#928 to key on. A lookup API that silently
drops a record is the same class of defect the module docstring says #917 was about.
(Real corpus has 0 nested rules today — `find .claude/rules -mindepth 2 -name '*.md'`
→ 0, control arm `-maxdepth 1` → 26.)

### M4 — The W1 divergence enumeration is incomplete: `paths:` **null** is a fourth shape

`tests/test_rule_registry.py:257-268`

W1 states the divergences with `has_paths_frontmatter` "are (a) `paths:` holding a
string, (b) `paths:` holding a dict, and (c) unparsable YAML that merely CONTAINS a
`paths:` line". Probed full matrix (`probe.py`):

| fixture | registry | `has_paths_frontmatter` | in W1? |
|---|---|---|---|
| `paths:` (null value) | `eager` | **True** | **no** |
| `paths: x` | `eager` | True | yes (a) |
| `paths:\n  a: b` | `eager` | True | yes (b) |
| `paths: []` | `scoped`, globs `()` | True | n/a (agree) |
| BOM + valid frontmatter | `eager` | False | n/a (agree, both wrong — see L1) |

`paths:` with a null value is the single most likely real-world typo of the four
(deleting the last glob from a scoped rule leaves exactly this), and the docstring
reads as exhaustive.

Aside, verified as a *non*-finding: CRLF is a false alarm. `Path.read_text` applies
universal newlines, so `---\r\npaths:\r\n…` classifies `scoped` correctly on both
sides (probe row `crlf_scoped`).

## LOW

- **L1 — A BOM'd scoped rule is silently reclassified `eager`.** `﻿` defeats the
  `\A---` anchor (`:49`); result is `eager, globs=()`, no `malformed` signal, and
  `has_paths_frontmatter` agrees, so the C2b tripwire cannot catch it. Editors that
  write UTF-8-BOM are the realistic source.
- **L2 — `eager_reason` can be `""` rather than `None`** when the qualifying heading is
  immediately followed by a same-level heading (`:167`, `:170` — `.strip("\n")` of an
  empty slice). The record then has a non-None `eager_reason_heading` and a falsy
  `eager_reason`; `if record.eager_reason:` and `is not None` disagree. Probed
  (`empty_section` → `reason: ''`).
- **L3 — `_EAGER_HEADING_MARKERS`' comment claims an exclusion the code does not
  implement.** `:63-66` says it "deliberately excludes 'why this rule exists'". There is
  no exclusion list — the phrase merely happens not to contain the markers. Probed:
  `## Why this rule exists (and is eager)` **qualifies**.
- **L4 — Indented ATX headings never match.** `_ATX_HEADING_RE` (`:55`) is anchored at
  `^#`; CommonMark allows 1–3 leading spaces. Probed: `   ## Why this rule is eager` →
  `heading=None`.
- **L5 — `build_registry` on a missing/typo'd directory returns an empty registry
  silently** (`:265-274`; `Path.rglob` swallows the `ENOENT`). Probed →
  `RuleRegistry(records=())`. A consumer cannot distinguish "no rules" from "wrong path".
- **L6 — `test_real_corpus_known_non_qualifying_eager_rules` (`:428`) is a pure negative
  assertion** — it survives `MUT=no_eager_reason` (asserts everything is `None`). It is
  killed by `MUT=heading_any`, so it is not worthless, but on its own it certifies
  nothing.
- **L7 — Two tests hardcode corpus filename sets** (`:289-292` and `:421-425`), directly
  against `test_scoped_agreement_against_real_repo`'s own stated principle at `:185-187`
  that set-equality "is strictly stronger than pinning filenames". Adding one rule with
  a `## Why this rule is eager` heading reds the suite.
- **L8 — `project_root = rules_dir.parent.parent`** (`:176`) is positional, not passed.
  A caller handing in any directory not exactly two levels below the repo root gets
  silently wrong `path` values (and therefore silently wrong `inject`), or a
  `ValueError` from `relative_to`.
- **L9 — module-level `sys.path.insert` + `from kb_setup.md_budget import …`**
  (`tests:21`, `:30`) means a knowledge-base dependency problem reds all 27 tests, not
  one. This is documented at `:26-29` as deliberate, so it is a noted trade-off rather
  than an oversight — recorded because it is a real "breaks for an unrelated reason".

## What I verified as SAFE (control arms run, no defect)

- CRLF frontmatter → correctly `scoped` (universal newlines).
- EOF-terminated frontmatter, empty file, frontmatter-only file, a `---` horizontal rule
  after line 1, YAML that parses to a string or a list → all classified without crash and
  in agreement with `scoped_rules_on_disk`.
- Section boundary arithmetic `lines[heading_idx + 1 : idx]` (`:167`) is correct: it
  excludes both the qualifying heading and the terminating heading. Deeper headings
  (`### Sub`) correctly do **not** terminate a `##` section.
- No state leaks across `_find_eager_reason` calls or `_build_record` iterations —
  `in_fence` / `heading_idx` / `heading_level` are per-call locals, and there is no
  module-level mutable state.
- `chmod(0o000)` tests are root-guarded (`os.geteuid()`, `:159`, `:224`, `:481`).
- `recurse_symlinks=True` parity with `scoped_rules_on_disk` is genuinely covered
  (`MUT=no_symlink_recurse` kills `test_recurses_into_symlinked_subdirs`).
