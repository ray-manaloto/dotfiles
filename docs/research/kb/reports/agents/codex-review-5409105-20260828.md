## Findings

### [MEDIUM] The new `--tag` may not change which image the CLI actually runs the container from

- **Claim in the diff:** `.devcontainer/devcontainer.json:93-97` comment says "The
  CLI's own vsc-<folder-hash> tag is shared by both architectures, so without it the
  second arch's build orphans the first container's image (verify-arch: 'No such
  image'; #678)." The fix adds `"--tag=vsc-dotfiles-${localEnv:DEVCONTAINER_WORKSPACE_HASH}-${localEnv:DEVCONTAINER_ARCH}"`
  to `build.options` (`.devcontainer/devcontainer.json:97`).
- **Premise CONFIRMED against the pinned CLI source.** `Yo(A)` (the CLI's default
  image-tag function) is `` `vsc-${basename(cwd)}-${sha256(cwd)}` `` — a pure function
  of the workspace `cwd`, with no architecture component:
  `devContainersSpecCLI.js:486` — `function Yo(A){let{cwd:e}="cwd"in A?A:A.cliHost,t=F9(e),i=yr.basename(e);return UN(\`vsc-${i}-${t}\`)}function F9(A){return vv.createHash("sha256").update(A).digest("hex")}`.
  So bringing up amd64 then arm64 in the same clone does produce the same default tag
  string for both builds — the stated premise is correct.
- **The fix's mechanism does not appear to intercept the code path that actually
  selects the image for the container.** In the plain (non-features) Dockerfile build
  path (`C9`), the docker/buildx argv is built as: `-f <dockerfile>`, then
  `t.map(L=>l.push("-t",L))` where `t` is `[Yo(common)]` (the generic, arch-blind
  tag) unless `devcontainer.json` sets `"image"` (it doesn't, here — this repo builds
  via `build.dockerfile`). Only *after* that does the code read `build.options` and
  splice it in: `` let p=(R=s.build)==null?void 0:R.options;p!=null&&p.length&&l.push(...p) ``
  (same source file, in the region containing `l.push("-f",c),t.map(L=>l.push("-t",L))`
  … `let p=(R=s.build)==null?void 0:R.options;p!=null&&p.length&&l.push(...p),l.push(...u)`).
  So our `--tag=vsc-dotfiles-<hash>-<arch>` becomes a **second, additional** `-t` flag
  on the same `docker buildx build` invocation — it does not replace `-t vsc-<hash>`.
  `_Q` (the features-augmented build path) returns `updatedImageName:t` from that same
  `t` array — i.e. still `[Yo(common)]`. That `updatedImageName[0]` value (the
  generic, arch-blind tag) is what `qQ()`/container-creation code actually consumes to
  run/create the container (`zV`/`qQ` reference `t` = `E.updatedImageName[0]`), not
  our new arch-scoped tag.
- **Net effect (as best I can tell from static reading):** the built image ends up
  with *two* tags — the shared `vsc-<hash>` (still reassigned to whichever arch built
  most recently, exactly as before) and the new arch-scoped
  `vsc-dotfiles-<hash>-<arch>` — but the CLI's own bookkeeping for "which image do I
  run this container from" still goes through the shared tag. I could not determine,
  from source alone, that the added tag is the thing that stops the
  "No such image" failure described in the comment; it may simply be a harmless extra
  label unless something (this repo's code, or the CLI in a path I did not trace, e.g.
  `updateRemoteUserUID` — which is explicitly disabled on macOS here via
  `updateRemoteUserUIDOnMacOS:!1` in `vn()`, so that particular arch-blind derived tag
  `${Yo(common)}-uid` is not built on this host) reads it back.
- **Not independently reproduced** — per the review brief I did not run
  `mise run up`/`dev-rebuild`. `.claude/rules/local-devcontainer-first.md` is exactly
  on point here: this is a claim best settled by actually bringing up both
  architectures in one clone and confirming neither `verify-arch` run regresses,
  rather than by re-deriving the CLI's minified control flow.
- **Citations:**
  - `.devcontainer/devcontainer.json:93-97`
  - `python/src/dotfiles_setup/devcontainer_names.py:301-317` (`names_env` — confirms
    `DEVCONTAINER_WORKSPACE_HASH`/`DEVCONTAINER_ARCH` really are exported before
    `devcontainer up`/`build` runs, so the substitution itself is wired correctly)
  - `mise.toml:277-315` (`[tasks.up]` — `_dc_env` eval before `devcontainer up`)
  - `@devcontainers/cli@0.88.0` `devContainersSpecCLI.js`, functions `Yo`, `C9`, `_Q`,

### [LOW] `mise.local.toml.example`'s new literal platform strings sit outside the `no_platform_literals` gate purely because of the `.example` suffix

- The new block (`mise.local.toml.example:35-44`) adds
  `DOTFILES_PLATFORM = "linux/arm64/v8"` twice as illustrative TOML inside a comment
  and inside the real `[env]`-shaped example. `python/src/dotfiles_setup/platform_target.py`'s
  `_in_scope()` (`platform_target.py:436-443`) gates scanning on
  `rel_path.endswith(_SCANNED_SUFFIXES)`, and `_SCANNED_SUFFIXES` (`platform_target.py:126`)
  is `(".py", ".toml", ".hcl", ".json", ".sh", ".yml", ".yaml")`. `Path.endswith` on
  the literal string `"mise.local.toml.example"` does not match any of those (the
  file's actual last extension is `.example`), so this file is **not scanned** by
  `find_violations` at all — not because it is deliberately exempted (the exemption
  list is `_SCAN_EXCLUDED_PREFIXES = ("docs/", "missions/", "plugins/", "tests/")`,
  which this path doesn't match either), but incidentally, via the suffix filter.
- This is not a functional bug — it's a doc/example file meant to show a user a
  literal value to type themselves, and the module's docstring already carves out
  "two files… permitted to carry the literal" without mentioning example files as a
  deliberate third category. But the stated project invariant is "exactly one place
  chooses" the platform outside `mise.toml`/`docker-bake.hcl`
  (`platform_target.py:34-42` docstring, `AGENTS.md` "THE platform is ONE parameter"),
  and this commit is the first to put a `linux/arm64/v8` literal into a third tracked
  file that the gate does not see, coincidentally rather than by design. Worth a
  one-line note in the module docstring's "two files" list if this is meant to be a
  third permitted site, otherwise it is a silent scope gap for future `.example`/
  `.sample` files.
- **Citations:** `mise.local.toml.example:35-44` (new); `platform_target.py:126`
  (`_SCANNED_SUFFIXES`); `platform_target.py:436-443` (`_in_scope`); `platform_target.py:34-42`
  (module docstring, "Where the literal is still allowed").

## Claims verified as CORRECT (no defect found)

1. **`--tag`/`--platform` substitution mechanism is wired correctly.**
   `DEVCONTAINER_WORKSPACE_HASH` and `DEVCONTAINER_ARCH` (`devcontainer_names.py:96-97`)
   are exported by `names_env()` (`devcontainer_names.py:301-317`) via
   `dotfiles-setup devcontainer env`, which both `[tasks.up]` (`mise.toml:277-315`)
   and `[tasks.dev-rebuild]` (`mise.toml:335-352`) `eval` into the shell *before*
   invoking `devcontainer up`, so `${localEnv:DEVCONTAINER_WORKSPACE_HASH}` /
   `${localEnv:DEVCONTAINER_ARCH}` resolve correctly for both entry points that
   actually trigger a build. Same mechanism the pre-existing `"name"` field
   (`devcontainer.json:83`) already relied on.
2. **`no_platform_literals` gate is not tripped by the `devcontainer.json` change.**
   `_LITERAL_RE` (`platform_target.py:120`) matches `linux/(?:amd64|arm64|x86_64|aarch64)(?:/v\d+)?`;
   the new `--tag=...` string contains only `${localEnv:...}` substitutions, no bare
   arch words or `linux/...` literals, so it doesn't match.
3. **`mise.{MISE_ENV}.local.toml` profile mechanism is real, current mise behaviour,
   correctly named and correctly gitignored.** Confirmed against mise's own docs:
   `mise.{MISE_ENV}.local.toml` is a documented file (config precedence, highest of
   the four: `mise.{MISE_ENV}.local.toml` > `mise.local.toml` > `mise.{MISE_ENV}.toml`
   > `mise.toml`) — `~/dev/github/ray-manaloto/knowledge-base/sources/mise/docs/configuration/environments.md`.
   `.gitignore:34` already has the `mise.*.local.toml` glob (predates this commit),
   so `mise.arm64.local.toml` is correctly ignored without any change needed. On this
   actual clone, `mise.local.toml` (`DOTFILES_PLATFORM = "linux/amd64/v2"`,
   `DEVCONTAINER_SSH_PORT = "26233"`) and `mise.arm64.local.toml`
   (`DOTFILES_PLATFORM = "linux/arm64/v8"`, `DEVCONTAINER_SSH_PORT = ""`) both already
   exist and match the new doc text's worked example exactly — this wasn't a
   theoretical design, it was tested against Ray's own real per-clone config.
4. **"mise config beats the ambient env" claim is consistent with documented mise
   behaviour and with what's on disk.** mise's `[env]` docs state plain
   `[env] VAR = 'value'` in a config file is unconditional (only the `{ default =
   ... }` form preserves an existing/ambient value) —
   `.../mise/docs/environments/index.md` "To set a fallback while preserving an
   existing non-empty value, use `default`… This keeps NODE_ENV if it was already
   set". `mise.toml`'s own `[env] DOTFILES_PLATFORM` (`mise.toml:144`) is itself a
   template reading the ambient var with a default, so a higher-precedence
   `mise.local.toml`/`mise.arm64.local.toml` literal for the same key wins outright,
   independent of shell state — this matches the observed behaviour described in the
   diff.
5. **Blank `DEVCONTAINER_SSH_PORT` in the arm64 profile correctly derives a distinct
   port rather than erroring or colliding.** `ssh_port()`
   (`devcontainer_names.py:170-203`) explicitly falls through to hash-derivation when
   the override is blank/whitespace (`override is not None and str(override).strip()`
   guards the pinned-value branch), so `DEVCONTAINER_SSH_PORT = ""` in
   `mise.arm64.local.toml` does what the comment says.
6. **`require_tokens`/`per_path_tokens` substring match for both new tokens is exact
   and present in the file, with no duplicate-match risk.** Checked both listed
   tokens character-for-character against `.devcontainer/devcontainer.json`; the
   `--platform=...","` (with trailing comma) token only matches the `runArgs` line,
   not the `build.options` line (which is followed by `]` not `,` at that position),
   so there's no ambiguity about which site each token is asserting.
7. **Docker tag string validity.** `vsc-dotfiles-<8-hex-char-hash>-<amd64|arm64>` uses
   only lowercase alphanumerics and hyphens — a valid docker tag/reference component;
   `DEVCONTAINER_ARCH` comes from `platform_arch()` → `_ARCH_ALIASES`
   (`platform_target.py:100-105`), which always yields `"amd64"`/`"arm64"`.
