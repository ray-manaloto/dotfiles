**What I ran:** I simulated the retry loop in scratch git repos. I used a `--depth 1` clone, which is the `actions/checkout` default the workflow gets, plus a `git pull --rebase` against the remote given as a URL, exactly as the workflow does. I tested two cases:
- **Fast-forward race (the #1449 case the fix targets):** another commit is added on top of the branch before the job pushes. The first push is rejected, the rebase succeeds, and the second push succeeds. The fix works here, and this run is the control that shows the probe can pass.

## Findings

1. **`.github/workflows/gcc-sha-repair.yml:105` — medium.** After a force-push, the rebase-and-retry puts stale content back on the branch.
   - **Why:** `actions/checkout` runs with the default `fetch-depth: 1`, and `git pull --rebase "$remote"` uses a raw URL, so there is no remote-tracking ref for fork-point detection. If Renovate rebases or recreates the branch (its `rebaseWhen: "conflicted"` path) or force-pushes it while this job runs, the new tip does not contain the checked-out SHA. There is then no merge-base, and the rebase replays both that SHA and the repair commit.
   - **Measured result:** a file the rewrite had dropped came back as a duplicate commit ("main-moved" re-adding `f2`), and `git pull` returned rc=0. The loop then pushes that junk commit to the Renovate branch. If the old and new content differ, you get add/add conflicts and a red run instead.
   - **When it bites:** only when the force-push does not itself re-trigger this workflow (for example, the paths filter doesn't see the Dockerfile change). A re-triggered run would cancel this one through `cancel-in-progress`.
   - **Possible fix:** check that the fetched tip still descends from `${GITHUB_SHA}` before rebasing, and exit 0 as a no-op if it doesn't. That matches the `refresh.yml` image-lock-pr pattern (`--force-with-lease` against the checkout SHA, then re-read the remote). Alternatively, fetch enough history and use `git rebase --onto FETCH_HEAD "${GITHUB_SHA}"` so only the repair commit is replayed.

2. **`.github/workflows/gcc-sha-repair.yml:100-107` — low.** On attempt 3, a rejected push still runs one more fetch and rebase whose result is never pushed before `exit 1`. The run fails either way, so nothing breaks, but the failure log ends with a successful rebase instead of the push rejection.
