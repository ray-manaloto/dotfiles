## 5. The symmetry test — one schema, four projections

Fixture: `build_event.schema.json` from §2. Every command below was run; rc
captured to a file, never through a pipe.

### Python — `datamodel-codegen --output-model-type msgspec.Struct` (rc=0)

```python
class LogLevel(StrEnum):            # from $defs/LogLevel
class Arch(StrEnum):                # from the inline enum
class Target(Struct):               # from $defs/Target
class BuildEvent(Struct):           # from the root, via "title"
```

### `json-schema-to-typescript` 16.0.0 (rc=0, real rc read from a file)

```typescript
/* eslint-disable */
/**
 * This file was automatically generated by json-schema-to-typescript.
 * DO NOT MODIFY IT BY HAND. Instead, modify the source JSONSchema file,
 * and run json-schema-to-typescript to regenerate this file.
 */

export type LogLevel = "debug" | "info" | "warning" | "error";

export interface BuildEvent {
  id: string;
  level: LogLevel;
```

⭐ **`BuildEvent`, `LogLevel`, `Target` — the names MATCH the Python side
exactly.** Two runs 2 s apart are byte-identical, so the header is deterministic
and needs no `--disable-timestamp` analogue. The banner even carries the
never-hand-edit instruction D23 requires as prose. Directory-in/directory-out
works: `-i multi/schemas -o multi/out` produced `build_event.schema.d.ts` +
`target_tag.schema.d.ts` at rc=0, each honoring its own `title` — that is the
multi-schema story D23 solves with named profiles.

### `quicktype` 26.0.0 (rc=0) — **fails the symmetry test**

```typescript
export interface QtRun1 {          // <-- named after the OUTPUT FILE
    attempt?: number;
    id:       string;
    level:    LogLevel;
    tags?:    string[];
    target?:  Target;
    text:     string;
}
export type LogLevel = "debug" | "info" | "warning" | "error";
export interface Target {
    arch:    Arch;
    digest?: null | string;
    [property: string]: unknown;
}
export type Arch = "amd64" | "arm64";
```

The root type is named from the **filename**, not the schema's
`"title": "BuildEvent"`: `-o qt.run1.ts` → `QtRun1`, `-o qt.run2.ts` → `QtRun2`,
and to stdout with no `-o` → `BuildEventSchema` (from `build_event.schema.json`).
Proof this is filename-derivation and not nondeterminism: with `--top-level
BuildEvent` pinned, two runs to *different* output filenames are byte-identical.
So the root name can be forced, but only by a per-schema argv flag — which is
precisely the shape D23 moved away from, and it does not scale to a profile set.
`--just-types` also emits **no header at all**, so nothing on disk says
"generated, do not edit".

Live corroboration from the `last30days` sweep (all GitHub, last 30 days):
quicktype PR [#3479](https://github.com/glideapps/quicktype/pull/3479)
(2026-09-06) fixes a naming collision where a JSON Schema model named `RegExp`
renders as `export class RegExp` and shadows the global constructor —
`ReferenceError: Cannot access 'RegExp' before initialization` on import. The
naming layer is an active defect surface, not a cosmetic preference. And PR
[#3473](https://github.com/glideapps/quicktype/pull/3473) exists because "41
keys were added to `keywords.json` by hand without touching `keywords.txt`" —
a hand-edit-of-generated-output incident inside quicktype's own repo, which is
exactly the failure D23's "never hand-edit generated output" rule prevents.

### `jsonschema codegen` 16.10.0, native C++ (rc=0, empty stderr) — **fails harder**

```typescript
export type SchemaText = string;
export type SchemaTarget = _SchemaTarget;
export type SchemaTagsItems = string;
export type SchemaTags = SchemaTagsItems[];
export type SchemaLevel = SchemaLogLevel;
export type SchemaId = string;
```

14 exported aliases for a 6-property object. The root is `Schema` (the `title`
is ignored); every property gets a positional alias; `additionalProperties`
leaks out as a top-level `never`. `--name BuildEvent` rebases the prefix
(`BuildEventText`, `BuildEventLogLevel`, `_BuildEventTarget`) but the explosion
stays — and note the `$defs/LogLevel` shared definition becomes
`BuildEventLogLevel`, i.e. **named after whichever root referenced it**, which
breaks `$def` reuse across schemas. Deterministic across a 2 s gap; no header
at all.

Two hard blockers beyond naming, both measured:

- `docs/codegen.markdown` states plainly: **"This command is experimental …
  things might break or change without notice"** and **"currently only supports
  JSON Schema 2020-12 and TypeScript"**. Its keyword table marks `oneOf`, `if`,
  `then`, `else`, `patternProperties` and `additionalProperties` as *Partial*
  and `not` as **"Cannot support"**.
- ⚠️ **`jsonschema codegen a.json b.json` exits rc=0 and silently drops the
  second schema.** Output is byte-identical to the single-file run (42 lines
  both); `grep -c TargetTag` → **0** while the control `^export type Schema` →
  13 and the known-absent arm `xlofrendu` → 0. A multi-schema wiring mistake
  would pass a gate that checks only rc. json2ts handles the same directory
  correctly at rc=0.

### What settles the drift question: `git diff --exit-code`, armed three ways

No TS candidate has a native `--check`, so the honest options are a homegrown
generate-to-tmp-and-diff (what `use-tool-builtins.md` exists to prevent) or
**git's own mechanism**, which is a tool builtin and the canonical pattern for
generated files. Measured in a throwaway repo (not this one):

| Arm | Action | rc |
|---|---|---|
| A | regenerate unchanged, `git diff --exit-code -- models.d.ts` | **0** |
| B | append `export interface HandEdited {...}`, commit, regenerate, diff | **1**, diff removes the hand edit |
| C | add `duration_ms` to the **schema**, regenerate, diff | **1**, diff shows exactly `+  duration_ms?: number;` |

(My first ARM C was contaminated — `git checkout -- models.d.ts` restored the
*committed* hand-edited version, per `feedback_git_checkout_is_not_undo`. Redone
clean in a fresh repo; the table above is the clean run.)

So drift detection is available and native — it is just **git's** native, not
the generator's. The asymmetry versus the Python side is real but bounded:
`datamodel-codegen --check` never writes, whereas the TS path must regenerate
into the working tree and then ask git. Given `clean-git-state.md` already
requires a clean tree before validation, that is compatible with the existing
gate discipline, but it must be stated in the design rather than discovered.

## 6. How it wires here

**Recommendation: one `mise run codegen` task, two generators, one hk step,
its own output directory.**

- **One task, not two.** `mise run codegen` invokes a single `python/` module
  that drives `datamodel-codegen` (config from `[tool.datamodel-codegen]`, zero
  argv, per D23) and then `json2ts` over the same schema directory.
  `mise run codegen-check` is the read-only twin: `datamodel-codegen --check`
  for Python (native, no write) **plus** regenerate-and-`git diff --exit-code`
  for TypeScript. Reasons it is one task: the two projections must never be
  regenerated from different schema revisions, and `mise-tasks-only.md` wants
  the seam at the task, with mechanics parameterized in the library. Profiles
  (D23's `[tool.datamodel-codegen.profiles.<name>]`) stay a *Python-side*
  concept; on the TS side the analogue is simply the directory sweep, which
  json2ts does natively.
- **`json2ts` has no config file**, so the one place its flags live is that
  `python/` module — which is functionally what D23 wanted from
  `pyproject.toml` (one definition, identical local and CI). Do not try to
  reproduce a TS config file; there isn't one, and the `--configuration` flag
  that does exist belongs to the tool I am not recommending.
- **hk step:** add a `codegen_drift` step beside `fnhook_gates`:

  ```pkl
  ["codegen_drift"] {
    glob = List(
      "schemas/**/*.json",              // the source of truth
      "python/src/dotfiles_setup/generated/_models.py",
      "python/src/dotfiles_setup/codegen.py",
      "src/generated/*.d.ts",           // see below
      "pyproject.toml",
    )
    check = "mise run codegen-check"
  }
  ```

  Glob the **schemas** as well as both outputs — a schema edit with no
  regeneration is the drift this gate exists to catch, and globbing only the
  outputs makes it a check that cannot fail on the interesting case.
- **Tools to pin:** `jsonschema` is available as `aqua:sourcemeta/jsonschema`
  if the schema-side gates below are wanted; the codegen itself needs
  `npm:json-schema-to-typescript` in `mise.toml`. It runs under the already-pinned
  `bun` (`npm.package_manager = "bun"`, `shared.toml:32`), and `bunx --bun` ran
  it here at rc=0. Note `typescript 5.9.3` is already pinned (`mise.toml:27`)
  but **nothing currently runs `tsc -p tsconfig.json`** — only `fnhook_gates`
  invokes tsc, through a temp project (see §7).
- ⭐ **Free win, independent of the codegen decision:** `jsonschema fmt --check`
  and `jsonschema lint` gate the **schemas themselves** — the shared input both
  projections read. Measured: `jsonschema fmt --check build_event.schema.json`
  → **rc=2** with a `--- current / +++ expected` diff on an unformatted schema.
  Neither Python nor TS generator offers this. If JSON Schema becomes a source
  of truth here, this is the missing gate on it, it is native, it has a real
  `--check`, and mise can already install it. Recommend adopting it **whether
  or not** the TS projection ships.

## 7. Do the function-hook types collide? No — but not for the reason you'd guess

Answer: **put generated model types in their own directory, NOT in
`.claude/types/`.** Evidence:

1. **The drift checks cannot collide.** `fnhook_gates` compares a hard-coded
   2-tuple, not a directory scan: `python/src/dotfiles_setup/fnhook_gates.py:30`
   is `_TYPE_FILENAMES = ("claude-code.d.ts", "claude-code-mcp.d.ts")`. A third
   `.d.ts` in that tree is invisible to it. Conversely a `codegen_drift` step
   globbing `src/generated/*.d.ts` never sees the harness files. No mutual
   failure in either direction.
2. **But the hk *trigger* does overlap.** `hk.pkl:257` globs
   `.claude/types/*.d.ts`, so a generated file placed there would fire
   `fnhook-gates` on every model change — running the wrong gate, and (per that
   gate's own design) re-invoking `/plugin-types` against the harness. Noise at
   best, and a confusing failure at worst.
3. **Neither gate would type-check the new file.** `fnhook_gates` writes a temp
   tsconfig that `extends` the repo one but overrides discovery with an explicit
   `"files": [...]` list (`fnhook_gates.py:283-306`), so `include` does not
   apply. The repo `tsconfig.json`'s `include: [".claude/types", …]` *would*
   pick it up — but nothing runs `tsc -p tsconfig.json`. So co-locating buys
   an illusion of coverage.
4. **The trees have different provenance and different owners.**
   `.claude/types/` is written by an *external* generator (`/plugin-types` from
   the pinned harness), is explicitly documented as environment-dependent, and
   its drift gate needs a bespoke normalizer for the `BuiltinToolInputs`/
   `BuiltinToolResults` bodies (see `.claude/types/README.md`). Generated model
   types are internal, fully deterministic, and need no normalizer. Mixing two
   different determinism contracts in one directory is how a later reader
   reaches for the wrong gate.

Concretely: `src/generated/*.d.ts` (or `python/src/dotfiles_setup/generated/`
for the Python half and a sibling TS dir). If the TS output should be
type-checked, that is a **separate** decision needing a `tsc` invocation the
repo does not currently have, and adding `src/generated` to `tsconfig.json`'s
`include` without running `tsc` anywhere would be a check that can only pass.

## 8. Recommendation

**Adopt `json-schema-to-typescript` 16.0.0 as the TypeScript projection, and
adopt `sourcemeta/jsonschema` for schema-side `fmt --check` + `lint`.**

Why json2ts wins on the only test that mattered: it is the **one** candidate
whose output names line up with the msgspec side —`BuildEvent`, `LogLevel`,
`Target`, three-for-three — because it honors `title`/`$defs` the same way
`datamodel-codegen` does. That is what "two projections of one source of truth"
means operationally; the alternative is a hand-maintained mapping table between
`BuildEvent` and `QtRun1`/`Schema`, which is the second vocabulary the whole
exercise is meant to eliminate. It is also deterministic with a DO-NOT-EDIT
banner and no timestamp, and it handles a schema directory natively.

Why **not** the native C++ tool, despite it being exactly the shape the operator
asked for: its own docs call `codegen` experimental and "may break without
notice", it ignores `title`, it explodes one object into 14 aliases, it names
shared `$defs` after the referencing root (breaking reuse), it marks six
keywords Partial and `not` unsupportable, and it **silently drops extra schema
arguments at rc=0**. Revisit it — the maintainer is on the JSON Schema TSC, it
ships binaries for both our architectures, and mise already knows it. But do not
make a source of truth depend on it today.

Why not quicktype despite 13.9K stars: filename-derived root names, no header
under `--just-types`, and a live naming-collision defect class.

**Honest cost of the recommendation:** a Node tool in the codegen loop. That is
not free, and the 30-day sweep contains a project paying for it —
`hashintel/hash` PR [#9445](https://github.com/hashintel/hash/pull/9445)
(2026-08-29) *removed* quicktype from `build.rs` specifically because "building
the Graph needed a working yarn install". Here the cost is much smaller: `bun`
is already pinned host+image (`shared.toml:32`), codegen runs at authoring time
rather than in the image build, and `json2ts` is one `npm:` pin. But it is a
real dependency and it should be accepted knowingly rather than absorbed.

**External validation of the architecture itself:** `Mumunu-team/mununu` PR
[#486](https://github.com/Mumunu-team/mununu/pull/486) (2026-09-02) ships JSON
Schemas whose stated purpose is that "Consumers who point `quicktype` /
`openapi-typescript` / `datamodel-code-generator` at the new files get typed
clients" — i.e. an independent project running the exact
one-schema-many-projections pattern, `datamodel-code-generator` included.

## 9. Premises I could NOT settle, and what would settle them

1. **Whether JSON Schema really is the right source of truth for THIS repo's
   models.** I was told to assume it. But nothing in the repo emits JSON Schema
   for these models today — `datamodel-code-generator` is not even installed —
   so there is no existing `schemas/` tree, and the choice of *who authors the
   schema* is open. **Settles it:** name the first two concrete models and where
   their schema will live; if the answer is "we hand-write the JSON Schema", the
   schema is then the hand-maintained vocabulary and R16's "only generated"
   guarantee applies one level up, not away.
2. **Whether the TS projection has a consumer at all.** I found no TypeScript
   source in this repo that would import a generated model type — the only `.ts`
   is function-hook code under `**/hooks/*.ts`. A projection with no consumer is
   cost with no benefit. **Settles it:** name the importing module. If the
   consumer *is* a function hook, note that `tsconfig.json` sets `types: []` and
   `lib: ["es2023"]`, which constrains what the generated file may reference.
3. **`--check` never writing, vs. regenerate-then-`git diff`.** Measured and
   working (§5), but I could not test it inside `mise run lint`'s actual
   sequencing, where a step that *writes* during a read-only gate may interact
   with hk's per-file locks. `mise run lint` is explicitly the read-only
   `hk run check --all`. **Settles it:** prototype the step and run
   `mise run lint` twice — once clean, once with a schema edited and the output
   stale — and confirm rc=0/rc=1 and that no source is left rewritten.
4. **`formatters` for datamodel-codegen.** Every 0.72.2 run warns that black/isort
   default formatting becomes opt-in, and the generated bytes currently depend on
   those pinned versions. I did not measure whether `formatters=[Formatter.BUILTIN]`
   changes the output for a msgspec target. **Settles it:** generate the same
   fixture under both formatter settings and diff.
5. **The firecrawl / exa / context7 lanes the brief specified.** Not available in
   this lane (§1), so the "current chatter" dimension rests on
   `/last30days:last30days` plus registry/API probes. `ctx7` resolves and could
   be run; I did not, because every load-bearing claim here came from running the
   tool rather than reading about it. **Settles it:** if independent doc
   corroboration is wanted, `ctx7 library json-schema-to-typescript` then
   `ctx7 docs <id> "check mode"`.
6. **Whether blaze's merged codegen will surface as a stable `jsonschema`
   command.** The source is in `sourcemeta/blaze`, the README does not mention
   it, blaze's only release is v1.0.0 (2025-02-13) despite daily pushes, and the
   CLI marks the command experimental. **Settles it:** watch
   `sourcemeta/jsonschema` releases for `codegen` leaving experimental, or ask
   in `sourcemeta/jsonschema` issues whether `title` will be honored.

## 10. Method notes (control arms, for audit)

Every negative in this report ran a positive control arm with the same probe
shape, and every known-absent term was invented fresh for its single use
(`vraknuzzil`, `grelbwonk`, `plurnwex`, `dwomblexi`, `yolbrexq`, `snorvaleth`,
`frimbazzo`, `kwethrizal`, `qwjvbx9`, `xlofrendu`) rather than reused from an
earlier receipt.

- One claim I corrected mid-run: I initially read `rc=1` from `json2ts` when
  that was **grep's** exit code at the end of a pipe. Re-measured with the rc
  written to a file: **rc=0** (`feedback_pipe_kills_exit_code`).
- One fixture I had to rebuild: ARM C of the git-drift test (§5).
- `mise run graphify-query` was run first per `graphify-first.md` and came back
  `TRUNCATED: showing 40 of 89 nodes` / `ERROR task failed`, which that rule
  defines as the graph being **unavailable** — not as an empty answer. Repo
  facts here are from source.
- The `last30days` sweep's X lane returned pure noise for
  `json-schema-to-typescript` (OpenAI Agents SDK posts, a Typebase promo, a Groq
  schema-validation error) and its `sourcemeta` lane surfaced two Digg items the
  engine itself labeled "Does not mention the target entity; irrelevant". I have
  not treated any of those as evidence. The GitHub lane is where that run earned
  its keep.
