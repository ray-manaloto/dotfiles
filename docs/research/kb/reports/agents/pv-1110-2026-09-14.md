
## MISSING premises

### M1 — the objective cannot be met without changing the exception type (design-determining)

`CalledProcessError.__str__` is fixed by CPython and omits stderr. Measured on this interpreter (3.14.0), non-repo tmp dir:

```
str(exc)   = "Command '['git', '-C', '/var/folders/…/pytest-of-probe-7se0fu1r', 'ls-files', '--', '*']' returned non-zero exit status 128."
exc.stderr = 'fatal: not a git repository (or any of the parent directories): .git\n'
```

The one route that preserves the type — PEP 678 `add_note` — does **not** reach `str()`:

```
__notes__ = ['git ls-files stderr: fatal: not a git repository (or any of the parent directories): .git']
"not a git repository" in str(e) -> False
CONTROL (RuntimeError carrying the message) -> True
```

So §5's "assert the raised exception's `str()` contains git's own stderr" forces a new type, and the `A` row's fallback instruction ("stop and report rather than changing the exception type") presupposes an option that does not exist. **The spec should name the type.** If the architect would accept `add_note` instead, §5's assertion must change to `__notes__` — that variant keeps `CalledProcessError`, keeps row 10 vacuously true, and still shows the cause in a pytest traceback and under `logger.exception`.

### M3 — git's stderr wording DIFFERS between host and devcontainer (the test would be green locally and red in the container)

Both arms, same probe, both environments:

| Environment | git | stderr on a non-repo dir | rc |
|---|---|---|---|
| macOS host | 2.54.0 (Apple Git-157), via mise shim | `fatal: not a git repository (or any of the parent directories): .git\n` | 128 |
| devcontainer (amd64) | 2.55.0, `/usr/local/share/mise/installs/conda-git/2.55.0/.mise-bins/git` | `fatal: not a git repository (or any parent up to mount point /home)\nStopping at filesystem boundary (GIT_DISCOVERY_ACROSS_FILESYSTEM not set).\n` | 128 |

The **only** substring common to both is `not a git repository`. An assertion on the host's full first line passes locally and fails under `mise run verify-local` / `mise run land` — which is the exact local/CI divergence class this very module was hardened against (PR #359; see the `find_local_only_refs` docstring, `doc_refs.py:260-275`). The spec's §5 instruction "assert on a substring git actually emits" is right but under-specified.

Two safe routes: assert only `not a git repository`, or — version-proof and self-arming — have the test run `subprocess.run([...], check=False)` against the same directory, take `result.stderr.strip()`, and assert **that** text appears in `str(exc)`. The second removes the wording dependency entirely.

Note also the container's message is **two lines**. Any assertion or format must tolerate a newline.

### M5 — `FileNotFoundError` is not covered, and `git` here is a shim

`which -a git` on the host → `/Users/rmanaloto/.local/share/mise/shims/git`, then `/usr/bin/git`; in the container it is a mise conda install. A broken shim fails two ways: rc≠0 with **mise's own** diagnostic on stderr (a `CalledProcessError`, which the change does cover — measured live this session: `mise ERROR No version is set for shim: timeout`), or `FileNotFoundError` if the shim is absent, which a `CalledProcessError`-only catch leaves as undiagnosable as the original defect. The repo catches `OSError` alongside `SubprocessError` in five places (`branch_guard.py:99`, `dependency_currency.py:112`, `plugin_health.py:157`, `session_state.py:87`, `handoff_check.py:116`). One sentence in §4 either widens the catch or records the omission.

### M6 — a house pattern EXISTS, and the spec's "no logger" constraint deviates from it

`python/src/dotfiles_setup/p2996_refresh.py:82-96` is the repo's pattern for precisely this problem:

```python
    cmd = ["git", "ls-remote", repo_url, f"refs/heads/{branch}"]
    try:
        result = subprocess.run(cmd, capture_output=True, text=True, check=True)
    except subprocess.CalledProcessError as exc:
        logger.exception(
            "git ls-remote failed (rc=%d). stderr:\n%s", exc.returncode, exc.stderr
        )
        raise
```

It surfaces stderr **and** keeps the type — satisfying both of the spec's goals — at the price of a module logger. The second shape is `image_promote._resolve_marker` (`image_promote.py:150-165`): catch, inspect `exc.stderr`, narrow or re-raise unchanged. So §4's "the module has no logger — do NOT add one" is a deliberate deviation from the only convention in the tree, and per the spec's own instruction I am reporting rather than resolving it.

The spec's reasoning is nonetheless sound and worth recording as the justification: on the **CLI** path a logger is redundant, because `main()` already routes the failure through `logger.exception` (`main.py:2821-2822`); on the **pytest** path — where #1110 actually failed — the exception message is the only carrier. A reviewer applying `use-tool-builtins.md` will ask why the house pattern was not followed, so that sentence belongs in §4 or the commit body.

## Emission row — four corrections

1. **The absolute repo path is already disclosed today.** `str(CalledProcessError)` embeds the full argv, including `str(repo_root)` — measured above. The change's marginal path disclosure is therefore **zero**; what is new is git's diagnostic sentence. The row over-states the delta.
2. **"Filled by: git's own diagnostic text" is incomplete.** Because `git` resolves through mise on both host and container, stderr can be *mise's* tool-resolution diagnostic instead of git's — a class the row does not anticipate. Still paths and tool names only.
3. **"no credential material passes through `git ls-files` stderr"** — true for every class I could produce, and `ls-files` reads no remotes, so I found no counter-example. But it is a claim about all git config-error paths and I did not verify it exhaustively; treat it as confirmed-in-practice, unproven-in-general.
4. **"Bounded: not formally" is right, but the text is multi-line** — the container's message is two lines. A cap is unnecessary at this size; newline tolerance is not.
