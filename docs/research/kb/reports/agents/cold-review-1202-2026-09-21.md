## F1 — the live enforcement loss, proven with both arms

The measured payload is not hypothetical. Running exactly what the hook spawns, with
the network unreachable:

```
$ HTTPS_PROXY=http://127.0.0.1:1 uv run --project python dotfiles-setup claude-doctor
{ "verdict": "unknown", "enforcement_eligible": false, "latest_version": null,
  "findings": ["cannot determine latest version, so currency is unknown (NOT 'current')…"] }
```

Feeding that report to the production `register` through the bun harness:

```
ARM A first call after oracle-down refresh : {"allow":true,"additionalContext":["base"]}
ARM A second call (cache now UNKNOWN)      : {"allow":true,"additionalContext":["base"]}
CONTROL null refresh                        : {"deny":"claude-doctor: refusing tool calls…"}
BOTH ARMS RAN
```

The control arm proves the probe discriminates: a refresh that fails **hard** still
denies, because `register.ts:325` reads `if (refreshed !== null)`. A refresh that
**succeeds with a non-enforcing verdict** replaces the cache, and because
`classic.SessionStart` does not run again, the enforcing verdict is gone for the
remainder of the session — the second call above no longer even refreshes.

The comment at `register.ts:317-318` states the guarantee that holds ("A null refresh
never weakens the prior enforcing verdict") and is silent on the case that actually
occurs. Before this commit the PreToolUse path performed no refresh at all, so the
SessionStart verdict stood for the whole session and this was unreachable.

## F2 — the refresh straddles the hook budget

`.claude/types/claude-code.d.ts:4180-4189`:

> `readonly ms: 10_000;` — "A hook's budget per dispatch, from its call to its return;
> past it the hook is absent (its `.catch` asked, else `next(e)` run on its behalf)."

This module registers no `.catch`, so an overrun means `next(e)` runs on the hook's
behalf and the tool call proceeds.

Measured on this host, the exact command `readVerdict` spawns:

| Condition | run 1 | run 2 | run 3 |
|---|---|---|---|
| network reachable (control arm) | 2.82 s | 2.43 s | 2.36 s / 2.91 s |
| network unreachable | **10.04 s** | **9.73 s** | — |
| leg breakdown, healthy | `claude doctor` 1.05 s | oracle 1.20-1.27 s | wrapper 0.05 s |
| leg breakdown, unreachable | oracle alone **8.93 s** | | |

Both arms run, so the probe discriminates. The unreachable-network case crossed 10 s
on one of two runs. The ceilings the code itself accepts are far above the budget:
`timeoutMs: 90_000` (`register.ts:90`) and `_TIMEOUT_S = 20.0` per subprocess
(`claude_doctor.py:141`).

The two triggers are **correlated with the condition the gate exists to report**: a
broken `claude` install is exactly when `claude doctor` is slowest, and the refresh
only ever runs when the verdict is already `INVALID`. F1 and F2 compound — under a
network failure the gate is disarmed by either route.
