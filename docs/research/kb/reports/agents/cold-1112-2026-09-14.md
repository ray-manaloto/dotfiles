## F1 — the guard cannot fire in the window it claims (HIGH)

The commit message asserts:

> refuses to start if `$OUT` already exists — so a same-second collision degrades
> to a loud refusal instead of a silent wrong answer

That is not what the snippet does. `$OUT` is created by `codex exec -o "$OUT"`, which
writes it **when the run finishes** — minutes later. The guard runs before `codex` is
even invoked. So in the concurrent case both lanes find `$OUT` absent, both pass, both
write the same `$PROMPT`, and both hand the same `-o` path to codex.

Reproduced in scratch with a stub standing in for `codex exec` (sleep, then write `-o`),
two lanes sharing one `LANE_ID`:

```text
lane A wrote OUT=.agent/kb/raw/v-89916-1789425535.md prompt-contents=payload from A
lane B wrote OUT=.agent/kb/raw/v-89916-1789425535.md prompt-contents=payload from A
--- files produced ---  p-89916-1789425535.md   v-89916-1789425535.md
```

One prompt file, one output file, and **lane B shipped lane A's payload** — the original
#1112 defect, unchanged, straight through the new shape. No "refusing:" line was printed.

Control arm (the guard is not dead, it is just aimed at the wrong window) — sequential
re-run with the same `CODEX_LANE_ID`:

```text
lane C wrote OUT=.agent/kb/raw/v-reuseid.md prompt-contents=payload from C   first rc=0
refusing: .agent/kb/raw/v-reuseid.md already exists                          second rc=1
AFTER=payload from C          <- prior content unchanged
```

So the guard discriminates; it just cannot see a concurrent peer, because a concurrent
peer has not written `$OUT` yet. The author's own "guard arm -> pre-existing `$OUT`
refused at rc=1" receipt is the *sequential* arm, and the commit message generalises it
to the concurrent one.

The fix for the claim, if the claim is wanted: take the identity as a lock rather than
testing for the product — e.g. `mkdir "$OUT.lock"` (atomic, fails if it exists) or
`set -o noclobber; : > "$OUT"` before invoking codex. Both make the refusal reachable in
the window that matters. As written, the guard is decorative in the default path.

## F2 — what is actually protecting the lanes (MED)

Measured in this session's own harness: each `Bash` tool call runs in a **distinct**
shell process.

| Probe | Result |
|---|---|
| call 1 | `PID=88959 PPID=9422` |
| call 2 | `PID=89248 PPID=9422` |
| control: `$$` inside `$( … )` in call 1 | `88959` — identical to the parent, so the probe reads a real PID and a subshell does not change it |

So two lanes pasted into two separate tool calls get different `$$` and therefore
different `LANE_ID` — which is why the fix works, and simultaneously why the guard can
never fire on the default path. Collisions remain reachable in exactly two shapes:

1. the snippet inlined **twice in one tool call** and backgrounded (`$$` is the calling
   shell's PID in a subshell — measured: `$( echo $$ )` == `$$`), started in the same
   second; and
2. `CODEX_LANE_ID` set once and reused across two lanes, which is the documented override.

Shape 2 is the one an orchestrator is most likely to produce — exporting one id for a
batch of lanes is the obvious reading of "overridable via `CODEX_LANE_ID`" — and it is
the shape F1 shows is unprotected while concurrent. Nothing in the snippet or its
comment warns that the override must be unique **per lane**, not per batch.

`${CODEX_LANE_ID:-…}` (not `${…-…}`) is correct: an exported-but-empty value falls back.
Measured: `CODEX_LANE_ID= zsh -c …` -> `89770-1789425515`.

## F3 — unvalidated caller value in a path (MED)

`LANE_ID="${CODEX_LANE_ID:-$$-$(date +%s)}"` then
`OUT=".agent/kb/raw/…-$LANE_ID.md"`. The override is a raw string interpolated into a
path. `CODEX_LANE_ID=../../../tmp/x` yields `OUT=.agent/kb/raw/…-../../../tmp/x.md`, and
`codex exec -o` writes there. Measured: `CODEX_LANE_ID=fixedid` -> `LANE_ID=fixedid`, so
the value passes through verbatim with no sanitisation.

Quoting itself is correct throughout — the assignment is quoted, and every use is
`"$PROMPT"` / `"$OUT"`, so a value containing spaces does not word-split in either
shell. The repo's zsh-vs-bash hazard (`feedback_zsh_no_word_splitting`) does not bite
here for the same reason. Derivation verified identical in both shells:
`zsh LANE_ID=89752-1789425515`, `bash LANE_ID=89760-1789425515`.

## `exit 1` reachability — NOT a defect

Probed, because the brief asks. `exit 1` inside a shell **function** in a script aborts
the whole script in both shells (`zsh-function rc=1`, `bash-function rc=1`, and the line
after the guard did not print). Inside `( … )` it exits only the subshell and the parent
continues (`PARENT CONTINUED rc=1`) — but the rest of the snippet is inside the same
subshell in every way an agent would paste it, so `cat`/`codex` are still skipped. The
one real hazard is `source`-ing the snippet into an interactive shell, where `exit` kills
that shell; that is not how the code block is presented.

## Verdict

occurs (separate tool calls -> distinct PIDs). Mechanically it is clean: complete across
12 files, no incidental drift, mirror-consistent, no stale path left behind.

The one claim that does not hold is the guard's. **F1 is the finding to act on**: the
commit message, and the comment the snippet now carries, both assert a protection the
code cannot provide, and the `CODEX_LANE_ID` override — the documented escape hatch — is
precisely the path where a collision is still silent. Either make the refusal atomic, or
say in the snippet that `CODEX_LANE_ID` must be unique per lane.
