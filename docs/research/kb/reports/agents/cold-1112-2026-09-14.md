## F1 — the guard cannot fire in the window it claims (HIGH)

The commit message asserts:

> refuses to start if `$OUT` already exists — so a same-second collision degrades
> to a loud refusal instead of a silent wrong answer

That is not what the snippet does. `$OUT` is created by `codex exec -o "$OUT"`, which
writes it **when the run finishes** — minutes later. The guard runs before `codex` is
invoked at all. In the concurrent case both lanes find `$OUT` absent, both pass, both
write the same `$PROMPT`, and both hand the same `-o` path to codex.

Reproduced in scratch with a stub standing in for `codex exec` (sleep, then write `-o`),
two lanes sharing one `LANE_ID`:

```text
lane A wrote OUT=.agent/kb/raw/v-89916-1789425535.md prompt-contents=payload from A
lane B wrote OUT=.agent/kb/raw/v-89916-1789425535.md prompt-contents=payload from A
--- files produced ---  p-89916-1789425535.md   v-89916-1789425535.md
```

One prompt file, one output file, and **lane B shipped lane A's payload**: the original
#1112 defect, straight through the new shape. No `refusing:` line was printed.

Control arm — the guard is not dead, it is aimed at the wrong window. Sequential re-run
with the same `CODEX_LANE_ID`:

```text
lane C wrote OUT=.agent/kb/raw/v-reuseid.md prompt-contents=payload from C   first rc=0
refusing: .agent/kb/raw/v-reuseid.md already exists                          second rc=1
AFTER=payload from C          <- prior content unchanged
```

So the guard discriminates; it simply cannot see a concurrent peer, because a concurrent
peer has not written `$OUT` yet. The author's own receipt ("guard arm -> pre-existing
`$OUT` refused at rc=1") is the *sequential* arm, and the commit message generalises it
to the concurrent one.

If the claim is wanted, take the identity as a **lock** rather than testing for the
product: `mkdir "$OUT.lock"` (atomic, fails when it exists) or `set -o noclobber; : >
"$OUT"` before invoking codex. Either makes the refusal reachable in the window that
matters. As written, the guard is decorative on the default path.

## F2 — a slash in `CODEX_LANE_ID` sends codex an EMPTY prompt at rc=0 (HIGH)

`LANE_ID` is interpolated into a filename *prefix*, so any `/` in the override puts a
directory component where none exists. The prompt write then fails, and because nothing
checks it, the next line pipes a nonexistent file into codex.

Measured, with a stub reporting what it received (`batch1/lane2` is a plausible thing for
an orchestrator to set):

```text
zsh:8: no such file or directory: .agent/kb/raw/codex-sol-advisor-prompt-batch1/lane2.md
cat: .agent/kb/raw/codex-sol-advisor-prompt-batch1/lane2.md: No such file or directory
STUB codex received        0 bytes on stdin
snippet rc=0
```

Control arm, identical snippet with the default `LANE_ID`: `STUB codex received 44 bytes
on stdin`, `rc=0`. So the probe discriminates, and the failing arm **exits 0** — a caller
reading `rc` sees success while an `xhigh`-effort model was handed nothing and will
answer anyway. That is the same failure shape #1112 was filed for (a well-formed wrong
answer), reached by a different route.

The underlying missing check (`cat > "$PROMPT"` unguarded, `$PROMPT` never asserted
non-empty) predates this commit, but before it the path was a literal with no caller
input, so there was no way to trigger it. This commit introduces the trigger.

Cheap fixes: `LANE_ID="${LANE_ID//[^A-Za-z0-9._-]/_}"` after the assignment, or
`cat > "$PROMPT" <<'EOF' … EOF` followed by `test -s "$PROMPT" || exit 1`.

**Correction to my own first pass:** I initially wrote this up as a path *traversal*
(`CODEX_LANE_ID=../../../tmp/x` escaping `.agent/kb/raw/`). I ran the arm and it
**failed** — `.agent/kb/raw/codex-sol-advisor-verdict-../../../victim/pwned.md` needs
`codex-sol-advisor-verdict-..` to be a directory, so the write errors out (control arm:
`CODEX_LANE_ID=benign1` wrote successfully inside the directory). Traversal is not
reachable through this prefix shape without a pre-existing attacker-made directory; the
real consequence is F2's silent empty prompt.

## F3 — what is actually protecting the lanes (MED)

Measured in this session's own harness: each `Bash` tool call runs in a **distinct**
shell process.

| Probe | Result |
|---|---|
| call 1 | `PID=88959 PPID=9422` |
| call 2 | `PID=89248 PPID=9422` |
| control: `$$` inside `$( … )` in call 1 | `88959` — equal to the parent, so the probe reads a real PID and a subshell does not change it |

So two lanes pasted into two separate tool calls get different `$$`, hence different
`LANE_ID` — which is why the fix works, and simultaneously why the guard can never fire
on the default path. Collisions remain reachable in two shapes:

1. the snippet inlined **twice in one tool call** and backgrounded (`$$` in a subshell is
   the calling shell's PID — measured above), started in the same second;
2. `CODEX_LANE_ID` set once and reused across two lanes.

Shape 2 is the one an orchestrator is most likely to produce — exporting one id for a
batch is the obvious reading of "overridable via `CODEX_LANE_ID`" — and F1 shows it is
unprotected while concurrent. Neither the snippet nor its comment says the override must
be unique per lane.

`${CODEX_LANE_ID:-…}` (rather than `${…-…}`) is the right choice: an exported-but-empty
value falls back. Measured: `CODEX_LANE_ID= zsh -c …` -> `89770-1789425515`.

Quoting is otherwise correct throughout — quoted assignment, and every use is `"$PROMPT"`
/ `"$OUT"` — so a value containing spaces does not word-split in either shell, and the
repo's zsh-vs-bash hazard (`feedback_zsh_no_word_splitting`) does not bite. Derivation
verified in both: `zsh LANE_ID=89752-1789425515`, `bash LANE_ID=89760-1789425515`.

## `exit 1` reachability — NOT a defect

Probed because the brief asks. `exit 1` inside a shell **function** in a script aborts the
whole script in both shells (`zsh-function rc=1`, `bash-function rc=1`, and the line after
the guard did not print). Inside `( … )` it exits only the subshell and the parent
continues (`PARENT CONTINUED rc=1`) — but the rest of the snippet sits in that same
subshell in any way an agent would paste it, so `cat`/`codex` are still skipped. The one
real hazard is `source`-ing the block into an interactive shell, where `exit` kills that
shell; that is not how the code block is presented.

## Verdict

Directionally right and mechanically clean — complete across 12 files, no incidental
drift, mirror- and parity-consistent, no stale path left behind, and it does close the
measured defect for the shape that actually occurs (separate tool calls -> distinct PIDs).

Two claims do not hold, and both live in the `CODEX_LANE_ID` override — the one input the
commit added:

- **F1**: the guard cannot refuse a concurrent peer, which is the case the commit message
  and the new in-snippet comment both say it handles.

Smallest change that closes both: sanitise `LANE_ID` to `[A-Za-z0-9._-]`, assert
`test -s "$PROMPT"`, and make the refusal atomic (`mkdir "$OUT.lock"`) instead of a
`-e` test on a file codex has not written yet.
