# Advisory: Renovate Lock Deadlock Fix (Issue #887)

**Decision:** Choose the mechanism that permanently stops hosted-Renovate dependency PRs from being blocked by a lockfile-coverage contract test.

**Status:** Premises verification in progress.

---

## Analysis: Candidate Shapes Evaluated

### Shape A: Extend refresh.yml to run on bot PRs

**Mechanism**: Add a `pull_request` trigger to refresh.yml (new job) that detects `renovate/**` branches and runs the existing lock-refresh composite, then commits the locks back to the PR.

**Pros**:
- Uses existing, proven `lock-refresh` composite (no new code)
- Leverages GitHub App token infrastructure already in place
- Autofix.yml precedent already exists for commit-back flow
- All machinery (App token, write permissions, auto-merge) already operational
- Solves the core deadlock: lock regenerated from a branch that HAS the bump

**Cons**:
- **Lock churn objection**: Re-solves ALL `latest` pins alongside exact-pin updates
  - BUT: This objection is WEAKER than team-lead implied
  - Premise 2 documents test exempts `latest` specifically because per-PR churn is expected/accepted
  - refresh.yml itself (line 18) says "per-PR lock↔config coverage is gated deterministically ... a per-PR regen would false-fail on any upstream release"
  - The REASON refresh.yml exists as daily-only is to batch `latest` resolution; but when a bot PR forces a regen anyway, some churn is unavoidable
  - **The churn is a CONSEQUENCE of the unblocking, not evidence the approach is wrong**

**Security Analysis**:
- Uses `pull_request` (not `pull_request_target`) — caller controls checkout, safe
- App token still required (GITHUB_TOKEN doesn't fire `pull_request` CI)
- No recursion risk: autofix.yml ALREADY excludes renovate[bot], preventing loops
- Commit authored by the GitHub App, not the bot
- **Safe**: matches existing pattern in refresh.yml itself

**Verdict on A**: **VIABLE and LOW-RISK**. The lock churn objection is real but expected and documented as the tradeoff for per-PR regeneration. Premise 2's test exemption rationale acknowledges this.

---

### Shape B: Narrow regeneration (only exact-pin drift)

**Mechanism**: Compute which exact-pinned tools drifted, then re-lock only those (e.g., `mise lock "<backend/npm:@openai/codex>"`).

**Pros**:
- Minimizes lock churn to only affected tools
- Honours the daily-vs-per-PR split premise 2 draws

**Cons**:
- **NEW CUSTOM CODE**: Violates `.claude/rules/use-tool-builtins.md` — "homegrown code is the LAST resort"
- **KNOWN TRAP in this repo**: `mise lock "<backend/name>"` reuses locked version unless `[[tools.X]]` block deleted first (#650 case history) — this is a subtle failure mode waiting to be discovered
- **Test-driven by necessity**: Would need its own tests to avoid silent truncations
- **Fragile**: If a tool appears in config as `npm:foo` but locked as something else, the correlation breaks

**Verdict on B**: **NOT RECOMMENDED**. Homegrown narrowing contradicts use-tool-builtins, introduces a known sharp edge, and pays implementation cost to save churn that premise 2 already accepts.

---

### Shape C: Stop exact-pinning shared tools

**Mechanism**: Change `.config/mise/conf.d/shared.toml` pins from `"0.152.1"` to `"latest"`, so test exempts them, and daily refresh.yml owns resolution.

**Pros**:
- No new code or workflow changes
- Aligns with test exemption philosophy

**Cons**:
- **REVERSES DELIBERATE POSTURE**: AGENTS.md line 17-18 explicitly documents `.config/mise/conf.d/shared.toml` as "the exact-pinned shared fragment both host and image merge"
- **ROOT CAUSE NOT FIXED**: A future exact-pin still hits the same deadlock
- **Abandons precision**: The decision to exact-pin was made to keep host and image synchronized; reverting it broadens divergence risk
- **Policy violation**: CLAUDE.md memory notes memo "2026-08-31b" explicitly calls out "the deadline DoD is NOT met" and "aws-cli 2.36.36, pydantic 2.13.5, ty 0.0.77" — exact pinning is part of that discipline

**Verdict on C**: **WRONG DIRECTION**. Treats symptom, not root cause; reverses deliberate architecture.

---

### Shape D: Native Renovate or GitHub mechanism

**Investigation**:
- **Renovate's `postUpgradeTasks`**: Does NOT exist in renovate.json (confirmed 0 matches); Renovate-hosted cannot execute tasks anyway (no admin CLI access)
- **GitHub's native auto-merge**: Already used (PR:auto-merge:true in refresh.yml) — doesn't solve the test block
- **GitHub's `pull_request_target`**: WRONG here — it runs on main context, refresh.yml's lock wouldn't reflect the bot bump
- **Renovate's native `mise` manager**: Documented limitation — rewrites version strings only, doesn't regenerate locks

**Native Mechanism**: NONE. The bottleneck is Renovate's lack of lock-generation capability, not GitHub's.

**Verdict on D**: **NO NATIVE SOLUTION**. The deadlock exists because Renovate cannot do what only `mise lock` can do.

## Single Risk That Decides It

**Shape A is recommended** (extend refresh.yml to run on bot PRs). The deciding risk is:

**Lock churn on every bot PR** — BUT this risk is ACCEPTABLE because:
1. Premise 2 (test docstring) explicitly documents that per-PR churn is expected when resolution happens
2. The test EXEMPTS `latest` pins for exactly this reason
3. Premise 2's rationale: "per-PR lock↔config coverage is gated deterministically ... a per-PR regen would false-fail on any upstream release"
4. Unblocking the deadlock REQUIRES resolving ALL pins (mise doesn't support partial re-lock without the trap in shape B)
5. The daily-vs-per-PR split was never intended to prevent lock updates on bot PRs; it was to prevent false-fails when upstream moved. That problem doesn't apply here — the test runs AFTER the bump, not before.

**The lock churn is a consequence, not a failure mode.**

## Security Assessment: Is it safe to push commits onto Renovate PR branches?

**YES**, with the infrastructure already in place:

- **Trigger**: `pull_request` (bot controls checkout, safe from injection)
- **Auth**: GitHub App token (identical to refresh.yml's own PR) — required because GITHUB_TOKEN doesn't fire subsequent CI
- **Author**: GitHub App (not renovate[bot]), so autofix.yml's exclude still fires on any autofix back to the Renovate PR
- **Loop guard**: autofix.yml line 42 already excludes renovate[bot]
- **Recursion**: GITHUB_TOKEN-created PRs don't fire `pull_request` anyway (GitHub's guard); App token PRs do, so the flow terminates after one push (the lock commit)
- **Automerge risk**: Not applicable — Renovate's own automerge runs after CI; the lock commit just adds a commit to the same PR

**No security problems.**

## Lock Churn Reality-Check

**Is the churn objection real or overstated?**

Real, but **proportionate and accepted by the test's design**:

1. **The test EXEMPTS `latest` pins** — this is proof that the team knows per-PR resolution is expected and acceptable
2. **The exemption is in the SAME TEST** that blocks exact-pin drift — the two are linked by design
3. **Premise 2 docstring**: "per-PR lock↔config coverage is gated deterministically ... asserting [freshness] per-PR would false-fail"
4. **The daily job re-resolves everything ANYWAY** — so a per-PR regen just brings forward the daily cycle, it doesn't add new churn

**Not overstated. It's the designed behavior when a bot PR forces regeneration.**

## Recommendation for Implementation

**Shape A** with infrastructure already in place:

1. Add `pull_request` job to `refresh.yml` that triggers on `renovate/**` (or `dependabot/**`) branches
2. Run existing `.github/actions/lock-refresh` composite
3. Commit result back to the PR branch using `autofix-ci/action` (or direct `gh api` write)
4. Use GitHub App token (same as current refresh.yml PR)
5. Existing autofix.yml exclusion of `renovate[bot]` prevents loops

No new code. No security risk. Solves the deadlock permanently.
