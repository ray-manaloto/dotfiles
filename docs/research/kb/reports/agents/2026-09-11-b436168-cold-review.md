## Findings

Ranked most severe first. Everything below is measured unless explicitly labelled.

### F1 — MEDIUM · The gate accepts `success()` as a rescue, and `success()` *is* the default it exists to catch

`STATUS_FUNCTIONS` at
`python/src/dotfiles_setup/workflow_skip_cascade.py:91-93` contains `success`.
GitHub's own reference says the opposite of what the adjacent comment
(`:88-90`, *"Each one, called, ANDs a value other than the implicit
`success()` into the job's evaluation"*) claims:

> A default status check of `success()` is applied unless you include one of
> these functions.
> — `github/docs` `content/actions/reference/workflows-and-actions/expressions.md:322`

and again at `expressions.md:377`: *"you must still include `failure()` to
override the default status check of `success()`"*. So writing `success()`
explicitly overrides the default with a call to the very same function — the
condition is unchanged, and the job is left in exactly the shape #995 shipped.

**Two-arm, file-level probe** (`.github/workflows/zz-probe.yml` in a scratch
copy, `dev-tag-clone` downstream of a skippable `dev-prep` via `build`):

| Arm | `if:` on the downstream job | Gate |
|---|---|---|
| stand-in | `success()\n&& needs.build.result == 'success'` | **`OK`, rc=0** |
| control | `needs.build.result == 'success'` | rc=1, flags `dev-tag-clone` |

Same file, same command, one line different — so the probe discriminates and
the acceptance is real, not a mis-read.

`UNVERIFIED` sub-claim: I could not measure on a live runner whether an
explicit job-level `success()` reproduces the transitive skip. The docs make it
the strong reading (`### failure` at `expressions.md:365` states the job-level
functions consider the whole *ancestor* chain, not just direct `needs`), but
the point stands regardless of which way it resolves: this module's stated
doctrine is to *assert the capability, never assume* (`:55-64`), and it admits
the one function GitHub documents as the default without a test or a probe
saying that is safe. There is no test covering `success()` in
`tests/test_workflow_skip_cascade.py`.

Same class, lower reach: `cancelled` and `failure` are accepted bare. `if:
cancelled()` on a downstream job passes the gate and means "run only on
cancel", which is not a rescue either. Only `always()` and `!cancelled()` are
actually rescues, and the module's own canary uses only those two.

### F5 — LOW / informational · A new failure coupling on the nightly, not called out in the diff

`manifest` gates on `(needs.dev-tag.result == 'success' || … == 'skipped')`
(`.github/workflows/build-publish.yml:1189`). Before this change the nightly
always produced `dev-tag: skipped`, so `manifest` always ran. After it,
`dev-tag` runs on the nightly, and a **failure** on a blocking leg
(`continue-on-error: ${{ !matrix.target.blocking }}`, `:1088`) flips `result`
to `failure`, which matches neither arm of the whitelist — `manifest` is then
skipped and nothing is published for that run.

The direction is conservative (don't publish a manifest whose validated marker
failed to stamp) and is probably what you want. It is a behaviour change the
commit message does not mention, and it moves a previously-unreachable state
onto the nightly path.

## Checked and clear

- **The workflow condition is correct for every terminal state.** Enumerated
  against the real graph (`plan → {base-prep, p2996-prep} → dev-prep → build →
  smoke-test → dev-tag`): `smoke-test` can only be `success` when `build` is
  `success`, which requires `base-prep`/`p2996-prep` success and `dev-prep` in
  `{skipped, success}` (`:822-827`), so `!cancelled() && needs.smoke-test.result
  == 'success'` cannot let `dev-tag` run on a failed ancestor. Cancellation is
  excluded by design (the job moves registry tags). `!cancelled()` over
  `always()` is vendor-endorsed — `expressions.md:344`.
- **The block scalar is required, not stylistic.** `if: !cancelled()` as a
  plain scalar is a YAML tag indicator; `if: |` makes it literal.
  `yaml.safe_load` of the shipped file returns
  `"!cancelled()\n&& needs.smoke-test.result == 'success'\n"`, and the three
  sibling jobs already prove multi-line `if:` works on this runner.
- **`fromJSON(needs.plan.outputs.matrix)` under a status function** is not a
  new risk: five other jobs, including `build` with `always()`, already use the
  identical matrix expression (`:143,281,437,549,828,1078`).
- **Test craft.** Every assertion fails on revert. `test_real_tree_is_clean`
  is anchored to the live `REPO_ROOT` and fails on the parent tree (measured,
  rc=1). The `_POST_FIX_…`/`_ALWAYS_RESCUE_…` fixtures are built by `.replace()`
  on the pre-fix body — a silent no-match would leave the pre-fix shape in
  place and the test would *fail*, so the decay mode my memory flags for
  `PER_FILE`-style override tables does not apply here.
  `test_find_violations_runs_the_control_arm_first` monkeypatches the canary and
  requires `RuntimeError`, so the control arm cannot be quietly dropped.
  The only fixture gap is F1's missing `success()` case.
- **Nothing weakened, no scope creep.** No suppression widened, no existing
  check relaxed; the hk glob (`hk.pkl:416-420`) is narrow and the checker is
  whole-tree regardless. `docs/hk-builtins-audit.md` counts reproduce exactly
  (`hk_builtins_audit_main(check=True)` → rc=0).
- **`except yaml.YAMLError, OSError, UnicodeDecodeError:`**
  (`workflow_skip_cascade.py:145`) is PEP 758, valid on this project's pinned
  Python 3.14.0, and the established convention here (12+ sites across
  `branch_guard.py`, `dag_tick.py`, `env_blob_scan.py`, …).
- **Swallowing YAML parse errors** (`:143-148`) makes the gate silently pass on
  an unparseable workflow. Justified in-file (actionlint owns syntax) and I
  accept it, but it is a second place a broken file reads as clean.
