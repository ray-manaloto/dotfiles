## Q1 — `graphify reflect` on a fresh clone: NO, it is trivially empty

### What writes `graphify-out/memory/`

**Exactly one writer.** `graphify.ingest.save_query_result` (`ingest.py:274`, `mkdir` + write at
`ingest.py:297-298`, `ingest.py:339`). Its only call site in the whole package is the
`save-result` CLI branch — `cli.py:1465-1474` (`elif cmd == "save-result"`, `cli.py:1446`).
Enumerated, not asserted: `grep -rn save_query_result` over the package returns 4 hits —
the def (`ingest.py:274`), the lazy-import map (`__init__.py:23`), the CLI call (`cli.py:1465`),
and a comment in `reflect.py:61`. **No hook, watcher, server or query path writes memory docs.**

So the directory is populated *only* by an agent explicitly running
`graphify save-result --question … --answer … [--outcome useful|dead_end|corrected]`.

`reflect` reads it and never writes it: `load_memory_docs` (`reflect.py:133`) globs `*.md`
and returns `[]` when the dir does not exist (`reflect.py:141-142`).

Also: `graphify-out/` is **gitignored** in this repo (`.gitignore:89`, only `wiki/` negated) —
`git ls-files graphify-out` → 0 files (control arm: `git ls-files python/pyproject.toml` → 1 hit).
`graphify-out/memory/` does not even exist in this long-lived clone. A fresh clone therefore
starts with zero memory docs, guaranteed.

### What `reflect` emits with an empty/absent memory dir — PROBED

`python -m graphify reflect --memory-dir <nonexistent> --out <tmp>` →
**exit 0**, prints `Reflected 0 memories (0 useful, 0 dead ends, 0 corrected)`, and writes a
14-line skeleton whose entire body is:

```
# Lessons

_Auto-generated by `graphify reflect` from 0 session memories in graphify-out/memory/. …_

## Summary

- 0 useful · 0 dead ends · 0 corrected · 0 unmarked

## Lessons

_No marked outcomes yet._
```

Source: `render_lessons_md` (`reflect.py:489`) always emits the header/summary; the
`_No marked outcomes yet._` line is `reflect.py:486`. No error, no non-zero exit,
no "nothing to do" short-circuit — it unconditionally writes the file
(`reflect.py:599-600`: `mkdir(parents=True, exist_ok=True)` + `write_text`).

**Control arm (the probe can produce the other answer):** two `save-result --outcome useful`
docs citing the same node, then `reflect` → the same command emits
`**Preferred sources** — corroborated by ≥2 useful results` / `` `foo.py` (2× useful)``.
So the empty result is a real "nothing recorded", not a broken probe.

### Trap found while arming that control (worth knowing)

`reflect` **auto-attaches the graph in the current working directory**: if
`./graphify-out/graph.json` exists and `--graph` was not passed, the CLI sets it
(`cli.py:1499-1503`), and `reflect` then loads `known_nodes` and **drops every source node not
present in that graph** (`reflect.py:589`, filter at `reflect.py:392-393`).

Measured: the *same* memory dir with the *same* two `useful` docs rendered
`_No marked outcomes yet._` when run with cwd = the dotfiles repo (node `foo.py` unknown to the
repo graph), and rendered the `Preferred sources` block when run with cwd = a graph-less temp dir.
Counts (`Reflected 2 memories (2 useful …)`) were identical in both — **the summary line does not
tell you the lessons were filtered away.**

### Verdict

On a freshly cloned repo that has never been queried, `graphify reflect` is a **no-op producing a
boilerplate stub**: exit 0, a `LESSONS.md` with zero content beyond the header and
`_No marked outcomes yet._`. It has value only after a session has explicitly run
`graphify save-result` with `--outcome` and `--nodes`, repeatedly (`--min-corroboration`
defaults to 2, so a *single* useful save cannot promote anything past "Tentative").

## Q2 — `graphify extract <single file>`: REJECTED in practice

### The path argument is walked as a directory tree, never accepted as a leaf

`cli.py:3156-3164` only checks `target.exists()` — there is **no `is_dir()` check**, so a file
path passes validation. It then fails two lines later in two different ways depending on `--out`:

**(a) without `--out` — uncaught crash.** `out_root = out_dir.resolve() if out_dir else target`
(`cli.py:3342`), `graphify_out = out_root / "graphify-out"` (`cli.py:3343`),
`graphify_out.mkdir(parents=True, exist_ok=True)` (`cli.py:3344`). With a file as `out_root`
that is `mkdir("<file>/graphify-out")`.

PROBED — `python -m graphify extract <dir>/llms.txt --mode deep --no-cluster`:
```
NotADirectoryError: [Errno 20] Not a directory: '.../gprobe/ex/llms.txt/graphify-out'
  File ".../graphify/cli.py", line 3344, in dispatch_command
rc_file=1
```
A raw traceback, not a diagnosed error.

**(b) with `--out <dir>` — silent no-op, exit 0.** The mkdir now succeeds, and `_detect(target)`
(`detect.py:1665`) does `os.walk(root)` (`detect.py:1776-1777`). `os.walk` on a file yields nothing;
graphify's `onerror` hook (`detect.py:1764-1772`) turns it into a WARNING and continues.

PROBED — same file, plus `--out <dir>`:
```
[graphify] WARNING: could not scan .../llms.txt ([Errno 20] Not a directory); its files are
  missing from this run's enumeration.
[graphify extract] scanning .../gprobe/ex/llms.txt
[graphify extract] found 0 code, 0 docs, 0 papers, 0 images
[graphify extract] wrote .../outdir/graphify-out/graph.json — 0 nodes, 0 edges
rc=0
```
**An empty graph at exit 0.** This is the dangerous arm — it looks like success.

**CONTROL ARM (the probe can produce the other answer):** the *same file* inside a **directory**
target, `graphify extract <dir> --mode deep`:
```
[graphify extract] found 0 code, 1 docs, 0 papers, 0 images
[graphify extract] semantic extraction on 1 files via bedrock...
```
So the "0 docs" above is genuinely "a file target is not enumerated", not a `.txt` classification
problem or a broken probe.

**Workaround if you must do one file:** put it alone in a directory and point `extract` at the
directory (that is exactly what the control arm did, and it worked).

### `.txt` IS a supported semantic-extraction type

`DOC_EXTENSIONS` at `detect.py:45` = `{'.md', '.mdx', '.qmd', '.skill', '.txt', '.rst', '.html',
'.yaml', '.yml'}`. `classify_file` returns `FileType.DOCUMENT` for `.txt` (`detect.py:503`, `.txt` branch at `detect.py:526`),
which routes it to the **semantic LLM tier**, not the AST tier.

PROBED via `graphify.detect.classify_file`:
```
llms.txt      -> FileType.DOCUMENT
notes.txt     -> FileType.DOCUMENT
README.md     -> FileType.DOCUMENT
main.py       -> FileType.CODE
weird.qwixbraltz -> None      <- control arm: unknown ext really does return None
```
And the directory control-arm run above confirms end-to-end that `llms.txt` is counted as
`1 docs` and dispatched to semantic extraction. So `.txt` is **not** skipped as a non-code file.

(Caveat, not probed end-to-end: a *sensitive-looking* filename — `token.txt`, `secret_store.txt` —
is dropped later in the walk by the sensitivity heuristic at `detect.py:161-240`. `llms.txt`
does not match it.)

### `--mode deep` — what it actually changes

Only two things; it is **not** a different pipeline.

1. **Prompt suffix.** `deep_mode = extract_mode == "deep"` (`cli.py:3328`) →
   `_sem_prompt_for(deep=…)` (`cli.py:3845`) → `_extraction_system(deep=True)` (`llm.py:519-523`, suffix text at `llm.py:510`)
   appends `_DEEP_EXTRACTION_SUFFIX` (`llm.py:510`) verbatim:
   > `DEEP_MODE: include additional INFERRED edges only for concrete architectural signals
   > (shared data contracts, explicit lifecycle coupling, or multi-step flow dependencies visible
   > in the sources). Avoid broad conceptual similarity edges. Mark uncertain ones AMBIGUOUS
   > instead of omitting.`
2. **Separate semantic cache namespace.** `sem_cache_mode = "deep" if deep_mode else None`
   (`cli.py:3839`) → `cache/semantic-deep/`. Because of that, deep mode also **widens the
   incremental gate**: on a warm tree `deep_mode and incremental_mode and not code_only`
   re-dispatches the FULL live doc/paper/image set rather than the manifest's changed files
   (`cli.py:3538-3548`, issue #1894) — otherwise `--mode deep` would silently no-op.

`_VALID_MODES = {"deep"}` (`cli.py:3320`); any other value exits 2. Deep mode prints
`[graphify extract] deep mode enabled: richer semantic extraction`.

**Cost note:** deep mode's own cache namespace means the first deep run over an
already-extracted corpus re-dispatches *every* doc/paper/image file to the LLM — it does not
reuse the default-mode cache.

### Backends / keys — `extract` DOES hard-fail with no key

`detect_backend()` (`llm.py:3111`) priority: **gemini → kimi → claude → openai → deepseek →
azure → bedrock → ollama**. Keys: `GEMINI_API_KEY`/`GOOGLE_API_KEY`, `MOONSHOT_API_KEY`,
`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `DEEPSEEK_API_KEY`,
`AZURE_OPENAI_API_KEY`+`AZURE_OPENAI_ENDPOINT`, then **bedrock on the mere presence of
`AWS_PROFILE` / `AWS_REGION` / `AWS_DEFAULT_REGION`**, then ollama via
`OLLAMA_BASE_URL`/`OLLAMA_HOST`.

PROBED with `env -i` (every credential stripped), directory target holding one `.txt`:
```
error: no LLM API key found (1 doc/paper/image file(s) need semantic extraction). Set
GEMINI_API_KEY or GOOGLE_API_KEY (gemini), MOONSHOT_API_KEY (kimi), ANTHROPIC_API_KEY (claude),
OPENAI_API_KEY (openai), DEEPSEEK_API_KEY (deepseek), or pass --backend. A code-only corpus
needs no key. Or pass --code-only to index just the code (local AST, no key)…
rc=1
```
No `graph.json` was written (only `graphify-out/cache/`). So: **hard fail, rc=1**, whenever any
doc/paper/image file is in scope. `--code-only` (local AST) needs no key at all.

⚠️ **On this machine `extract` silently selects `bedrock`.** With only the `*_API_KEY` vars
unset but AWS vars still in the shell env, my probe auto-routed to bedrock and failed with
`UnrecognizedClientException: The security token included in the request is invalid` (rc=1,
after dispatching the corpus to AWS). Pass `--backend` explicitly rather than relying on
auto-detection here.
