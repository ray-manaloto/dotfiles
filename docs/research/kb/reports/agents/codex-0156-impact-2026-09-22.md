## 1. `daemon update --from-cli [-y]`: shipped in stable 0.156.0

**Is it in the release?**
- The notes for release `rust-v0.156.0` (not a prerelease, published 2026-09-22T19:51:01Z) list #45546, #45558, #45580 and #45780. None of the four is in the 0.155.0 notes, which list 243 PR numbers, so the search works.
- The source agrees. At the tag, `codex-rs/cli/src/main.rs` has `Update { #[arg(long)] from_cli: bool, #[arg(short='y', long, requires="from_cli")] yes: bool }` (lines 804–811, help text "Copy and pin this CLI package"). The same search against `rust-v0.155.1` finds nothing for `from_cli`. The control search in that file (`Bootstrap(`) finds 4, so the search is not blind.

**What `--from-cli` does** (`app-server-daemon/src/prepare_install.rs`):
- **Where it copies from.** The source is `InstallContext::current().package_layout`, meaning the package folder around the running binary (`bin/codex` plus `codex-package.json`). The copy is checked in `validate_package` (lines 427–471). On macOS it needs `codex-package.json`, `bin/codex`, `bin/codex-code-mode-host` and `codex-path/rg`, and each one must be executable.
- **npm/mise installs qualify.** This is shown, not inferred:
  - I downloaded the `codex-npm-darwin-arm64-0.156.0.tgz` asset. It contains `vendor/aarch64-apple-darwin/{codex-package.json, bin/codex, bin/codex-code-mode-host, codex-path/rg}`. Its manifest reads `{"layoutVersion":1,"version":"0.156.0","target":"aarch64-apple-darwin","entrypoint":"bin/codex",...}`.
  - `install-context/src/lib.rs:740` has the test `npm_managed_package_keeps_package_layout`.
  - `codex.js` spawns `vendor/<triple>/bin/codex` directly, so the running binary sits inside that folder.
  - Our **current** mise install already has this layout: `~/.local/share/mise/installs/npm-openai-codex/0.154.0/node_modules/@openai/codex-darwin-arm64/vendor/aarch64-apple-darwin/codex-package.json` exists.
- **It pins.** Replace mode names the release `local-<blake3-digest>-<target>` (lines 248–252) and deletes the `auto-update-version` marker (lines 327–334). It stops the updater loop (line 290). The success message says: "The CLI package is selected and pinned. Run `codex app-server daemon update` to return to production updates." PR #45580 says: "Explicit replacements disable automatic package updates."
- **Scheduled updates respect the pin.**
  - `ensure_managed_updater` (`lib.rs:846–883`) starts an updater only when `is_stable_standalone_release()` is true.
  - That check (`managed_install.rs:74–115`) needs a `<X.Y.Z>-<target>` release name **and** `auto-update-version == release_name`. A `local-*` release fails both tests.
  - `manual_update::run` accepts a pinned package only when the trigger is `RestoreProduction`.
  - PR #45780 says: "Scheduled updates and ordinary updater socket requests continue to respect pins."
- **What else happens during a replace:**
  - The copy is staged and its digest checked before the daemon is stopped.
  - The daemon restarts only if it was already running.
  - An old legacy install is moved to the dedicated folder, and the standalone CLI's own selection is left alone.
- **Trap: a first `daemon start` does not pin.** If no daemon package exists, `start`, `restart` or `bootstrap` copy the calling package (#45558). For a stable version, that copy writes the `auto-update-version` marker (`follows_latest`, lines 269–276), so the daemon **follows latest**. Only `update --from-cli` pins.
- **Trap: plain `daemon update` removes the pin.** Without `--from-cli` it moves a pinned or local package back to latest stable (#45780, README lines 61–67).

**Where daemon packages live now (#45546).** New daemons use `$CODEX_HOME/packages/app-server-daemon/{releases/…, current → release}` and run `current/bin/codex`. Legacy daemons keep `packages/standalone/current`. `package_root()` (`managed_install.rs:20–55`) picks the dedicated folder if it has a `current` link. Otherwise it picks standalone if legacy state files exist (`app-server.pid`, `app-server.stderr.log`, …).

**Is a standalone install still needed? No.** The README says "`bootstrap` can use any complete CLI package … A bare executable cannot supply a new installation" (lines 93–97). One condition applies to our replace path: `--from-cli` needs *some* daemon package to be selected already, or it fails with "no daemon package is selected; run `codex app-server daemon start` first" (line 121). On this host the legacy standalone package satisfies that.

**This host, checked read-only:**
- `~/.codex/app-server-daemon/` holds `app-server.pid` (Aug 29) and `app-server.stderr.log`, which are legacy files. So `package_root` resolves to `packages/standalone`, currently pointing at `0.151.0-aarch64-apple-darwin`.
- `packages/standalone/auto-update-version` is **absent**. The same test finds `install.lock` present, so the check works. That means no scheduled updater would run today.
- `packages/app-server-daemon` does not exist.
- There is no `daemon.pid`, no `settings.json`, and no managed app-server or updater process. The only running app-server is ChatGPT Desktop's bundled one (`/Applications/ChatGPT.app/Contents/Resources/codex`, pid 41755).

## 2. New pieces and the "pause → update → restart → continue" design

- **`/daemon` menu (#45854).** In the TUI you choose either "latest public stable" or "use the current CLI package". Cancel is the default. After you confirm, the TUI exits and runs the update through the CLI that launched it. It is disabled for remote connections. It is useful for people, but hooks should call the CLI command directly.
- **`--no-daemon` (#46088).** The session never starts or probes the shared daemon, and the flag carries through `resume` and `fork`. It cannot be combined with `--remote`, `codex agents` or `codex queue`. It is a clean way to keep our `codex exec` review and implementation lanes off the shared daemon, so a daemon restart cannot kill them. **Not verified:** whether `codex exec` attaches to the daemon by default at all. The PR mainly concerns the TUI.
- **Worktree sessions (#46498, together with #46529).** `--worktree` sessions can now use an existing daemon, and #46529 lets them auto-start it. So the daemon's blast radius covers worktree sessions too, which is another reason the version must be controlled.
- **Continuing interrupted work (#45807, #45820).** During shutdown the daemon saves a recovery snapshot of active turns. After a managed restart it starts one continuation turn, even with no client connected. This needs an idle thread with the same permissions and the same local environment.
  - Source detail: `--from-cli` first deletes any *stale* snapshot (`discard_pending`, line 299), then does a graceful stop, then calls `start_managed_backend` directly. That call does not delete snapshots.
  - A fresh `daemon start` **does** delete them (`lib.rs:409–412`, "A fresh start must ignore snapshots…").
  - **Rule for the hooks:** use `update --from-cli -y` or `daemon restart`. Never `stop` followed by `start`, which throws away the continuation.
  - **Not verified:** I did not run an actual restart and continuation.
- **#40969 (updates force-killing active turns).** The grace period after SIGTERM is now configurable: `shutdownGraceSeconds` in `settings.json`, default 60, allowed 0–300 (README lines 70–74). The 300 cap means a turn longer than 5 minutes is still force-killed. A pinned daemon has no updater, so it is never restarted without our action. The checkpoint pause stays necessary: set `shutdownGraceSeconds: 300`, pause at a checkpoint, and rely on #45820 as a backstop.

## 5. Verdict: switch back to "the mise npm pin is the only authority"

**Option B, recommended: mise npm pin plus `daemon update --from-cli -y`**
- Pros:
  - One version decision, made in a reviewed diff: `.config/mise/conf.d/shared.toml:44`, which `schemas/sources.toml` `pin_source` already names.
  - The daemon is pinned byte-for-byte to the CLI, and scheduled updates cannot move it (#45780). No surprise restarts at all.
  - The daemon copy is independent, so pruning the mise install dir does not break it.
  - It fits `pin-parity` and `tool-currency`.
- Cons:
  - Each bump needs an explicit `--from-cli` step (a hook).
  - Each bump leaves a new `local-<digest>` release, roughly 330 MB+ uncompressed. **Not verified:** whether old releases are cleaned up.
  - Our timing depends on npm's platform publish lag, as seen today.
  - #41188 is still officially open.

**Option A: the native installer owns everything**
- Pros:
  - Updates arrive automatically, fastest.
  - It is the vendor's own path (README "Bootstrap flow").
- Cons:
  - The daemon moves on OpenAI's schedule, not ours. That is exactly the #40969 kill risk, and it fights the checkpoint design.
  - A second authority outside mise, out of reach of `pin-parity`, `minimum_release_age` and review.
  - `schemas/sources.toml` would record a version we did not choose.
  - Its premise ("npm installs cannot be the daemon") is **false as of 0.156.0**.

**Resync to 0.156.0, Option B.** Wait until `npm view @openai/codex@0.156.0-darwin-arm64 version` succeeds.

3. **User-global** (`~/.config/mise/config.toml:144`, currently 0.155.1): this is an operator edit outside the repo. Set it to 0.156.0.
4. `mise install`, then `mise exec -- codex --version` should show 0.156.0.
5. Write `"shutdownGraceSeconds": 300` into `~/.codex/app-server-daemon/settings.json`. This is an operator action.
6. `mise exec -- codex app-server daemon update --from-cli -y`. Because the host is legacy, this moves the daemon to `packages/app-server-daemon/releases/local-*` and pins it. It stays stopped, since nothing is running now.

5. Keep lanes on `--no-daemon` where they can use it.
