# How other projects detect the LLVM version dynamically — research 2026-10-02 (coordinator fork 0de8)

## Live facts (probed 2026-10-02, control arms in brackets)
- GitHub latest LLVM release: `llvmorg-23.1.2` (github.com/llvm/llvm-project/releases/latest 302 → tag; [bogus repo → 404]).
- apt.llvm.org resolute: suite `-23` 200, `-22` 200 (22.1.8), `-24` 404, unnumbered = clang-24 snapshot [`-bogus99` → 404].
- **apt `-23` is NOT a release tag.** It is `1:23.1.3~++20260922…+67f4a076a097`. The `~` sorts below 23.1.3, and 67f4a076 matches none of llvmorg-23.1.0/.1/.2 (tags 9b0f9b1e / e7ce3600 / 2d567403) nor the release/23.x head 21ef2ddb, all via `git ls-remote`. So the numbered suite builds the release BRANCH between tags. The mise-system.toml claim "numbered suites build RELEASED TAGS" held for 22.1.8 only because branch 22 was frozen at its last tag. It is UNVERIFIED that 67f4a076 is on release/23.x (needs a git fetch).
- The apt.llvm.org pool keeps ONE build per suite, so an exact pin to 23.1.2 is impossible from apt.llvm.org. You get whatever the branch snapshot is, as with 22.
- apt.llvm.org's own channel labels are stale: the homepage says stable/qualification/development = 21/22/23, and `llvm.sh` says `CURRENT_LLVM_STABLE=22`.

## How other projects do it (GitHub code search: 7 queries, control `zzqqvv-llvm-nonexistent-17x` → 0; then rate-limited)
1. **GitHub releases/latest → apt suite** (the most common pattern):
   - apache/arrow-adbc `ci/docker/cpp-clang-latest.dockerfile`: `curl api.github.com/repos/llvm/llvm-project/releases/latest`, parse `llvmorg-M` → `llvm-toolchain-bookworm-M`, then install `clang-M` etc. Fully dynamic at build time and unpinned.
   - vdaas/vald `Makefile.d/dependencies.mk`: an `update/llvm` target writes `versions/LLVM_VERSION` from releases/latest (`grep -Po 'llvmorg-\K…'`). A committed version file, refreshed by a make target or CI job.
2. **Hardcoded major plus package-index resolution**: Cons-Cat/libCat `scripts/install_mise_llvm_debs.py` (MISE + apt.llvm.org!). `LLVM_MAJOR = 24` is a literal; it reads the suite's `Packages.gz`, resolves every `*-<MAJOR>` package to its single version, fails on mixed versions, downloads and extracts the debs into a mise-managed dir, and stamp-checks. This is our `apt_repo.py` approach, plus a bump-by-hand constant.
3. **Hardcoded trunk default + caller override**: NVIDIA/hpc-container-maker `building_blocks/llvm.py` (`_trunk_version='18'`, `upstream=True`). The version is a parameter and gets stale.
4. **llvm.sh-style dynamic suffix**: awslabs/aws-crt-builder `builder/imports/llvm.py` (a modified llvm.sh supporting "any future version dynamically", caller-supplied version).
5. **mise `apt:clang = "latest"`** (maplibre-native-ffi, cetanu/dotfiles, adonm/zuko): the distro's unversioned clang, not apt.llvm.org. Dynamic, but lags (Ubuntu resolute froze at 22.1.2), unpinned, and loses reproducibility.

## Implication for our design
Common dynamic practice = **source of truth is GitHub `releases/latest` (major M), and apt.llvm.org supplies `llvm-toolchain-<codename>-M`**. Reproducibility comes from a COMMITTED version file or pins, refreshed by an update task (vald), not from resolving at build time (arrow). That maps onto: detector = releases/latest ∩ suite-exists; committed truth = the mise-system.toml pins (regenerated by `apt-repo --llvm-version M --toml --pin`); `llvm-bump` = our `update/llvm`.
