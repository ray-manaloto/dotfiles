**The deciding risk is not in 1.58.1; it is in NOT taking it, because hk 2.0.0
shipped 2026-09-13 and is already queued behind this.** Holding at 1.57.0 means
the next hk PR Renovate opens is the breaking major, arriving into the same
broken two-PR split — a breaking migration and a config-grouping defect landing
together, with no benign step in between to prove the regrouping works.

The bump itself is about as low-risk as an hk bump can be:

- 1.58.1 is **documentation-only** over 1.58.0 ("no changes to hk's runtime
  behavior").
- 1.58.0 carries **five** behavioral changes out of 42 commits, and all five are
  verified no-ops against this repo's actual configuration (Evidence 3 table):

- The 1.58.1 pkl schema has **already evaluated green against this config** —
  PR #1079's run, 65 ✔ and one ✗ (the parity gate itself).

Residual risks, both bounded:

1. The 1.58.1 *binary* has not run against this config. Mitigated structurally:

**Pin 1.58.1, never 1.58.0** — 1.58.0 has no binary assets.

  host-resolved entry is wrong only on the platform no local gate exercises.
  A bare whole-file `mise lock` is destructive.
- Per `feedback_mise_lock_reuses_locked_version`, a re-lock can reuse the
  already-locked version rather than re-deriving it. If `lock-shared` leaves
  `version = "1.57.0"` at `.config/mise/mise.lock:413`, delete the whole
  `[[tools.hk]]` block first and re-run.

`image-lock-pr` still reports drift, `mise run lock-image`.

Push that commit to the Renovate branch **before** arming auto-merge, not after
(`feedback_amend_after_ship_races_automerge`: once auto-merge is armed the branch
is closed to new pushes). Then, and only then:

```bash
mise run automerge -- <PR#>       # bot-authored PR -> automerge, never ship
```
