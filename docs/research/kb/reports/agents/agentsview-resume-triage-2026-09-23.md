## Recommended minimal set for resume triage

All against the skill's daemon (`http://127.0.0.1:8080`, bearer token from the
`install-remote:` token file). Never a command without `--server`.

1. **Pick the previous session(s):**
   `GET /api/v1/sessions?project=dotfiles&agent=claude&limit=5`
   (CLI: `agentsview session list --project dotfiles --agent claude --limit 5 --json --server … --server-token-file …`).
   Drop any row with `signals_pending_since` set or equal to the current session
   id (P3). Flag a row when
   `outcome ∈ {abandoned, errored}` ∨ `final_failure_streak > 0` ∨
   `termination_status ∈ {tool_call_pending, truncated}` ∨ `ended_with_role == "user"` ∨
   `health_grade ∈ {D, F}` ∨ `mid_task_compaction_count > 0`. Treat a missing
   `termination_status` or `outcome=unknown/low` as **unknown, never clean**.
2. **Unfinished anywhere in the project:**
   `GET /api/v1/sessions?project=dotfiles&termination=unclean&date_from=<last handoff date>`
   (API-only).
3. **Children of each flagged/previous session:**
   `GET /api/v1/sessions/{id}/children`, then apply step 1's predicate to them.
4. **Where it broke, and whether it was fixed in-session:**
   `GET /api/v1/sessions/{id}/search?q=rc%3D1` (then `FAIL`, `Traceback`,
   `error:`) → ordinals; then
   `agentsview session messages <id> --around <ord> --before 3 --after 3 --json --server …`,
   and always the tail:
   `agentsview session messages <id> --direction desc --limit 6 --role user,assistant --json --server …`.
5. **(b) How it was resolved before:**
   `agentsview session search "<exact error string>" --in tool_input,tool_result --project dotfiles --exclude-session <prev-id> --json --limit 8 --server …`,
   then `session messages --around` on the top 2–3; `--fts` for prose. Optional
   weekly pointers: `GET /api/v1/analytics/signal-sessions?project=dotfiles&from=…&to=…&signal=tool_failure_signals|outcome_abandoned&limit=5`.

Owed items are not a field anywhere. Read them from the session tail (step 4)
and reconcile against the handoff, which stays the primary source.

## Can `recall brief` or `insight` replace hand-written handoff prose?

**No, not today and not on this design.**
- `recall brief` defaults to `--trusted-only=true`, which needs `human_reviewed`
  entries. Automated extraction can never create those. The corpus is 0 and
  extraction is `configured:false`. Upstream calls it experimental and warns of
  rebuilds. Each call also writes a `recall_query_events` row. (P12)
- `insight generate --type agent_analysis --session-id <prev>` could produce a
  model-written narrative of the previous session. It is non-deterministic,
  spends a model call through a local agent CLI, stores a row, and upstream
  itself says to use Quality metrics, not insights, when the result must be
  repeatable. At most it is an optional *supplement*, clearly labelled, never
  the handoff's replacement or a gate. (P13)
- The deterministic signals (step 1–4) can replace the *"did the last session
  end broken?"* part of the prose. The intent part ("what's next, what was
  decided, what is owed") has no AgentsView field.

## SDK vs documented HTTP API

- **No SDK to import.** Upstream ships a Go client under `internal/apiclient/`
  (`client.gen.go`, generated from `openapi.yaml` via `generate.yaml`), which Go's
  `internal/` rule makes unimportable, and a generated TypeScript client for its
  own frontend (`frontend/scripts/generate-api-client.mjs`). There is no Python
  package (tree @tag: no `*.py` outside docs/tooling scripts).
- **There IS a documented, versioned HTTP API:** `openapi.yaml` at the repo
  root and `agentsview openapi` (OpenAPI 3.1, 123 paths); `GET /api/v1/version`
  reports `api_version 10` / `data_version 113`; bearer auth (401 without it).
  The CLI is a thin client over it (its errors print the `/api/v1/...` URL, P2).
- **Recommendation: call the HTTP API from Python, not the CLI**, for the resume
  triage module:
  1. four of the capabilities triage wants are **API-only**: the `termination`
     filter, per-session `search?q=`, `children`, and the analytics signal
     routes;
  2. the CLI's no-`--server` commands silently read a different archive (P5),
     and a plain HTTP client structurally cannot make that mistake;
  3. `stdlib urllib.request` + the existing `pydantic`/`msgspec` deps are
     enough (no new dependency). Generate the models from the pinned
     `agentsview openapi` output instead of hand-writing field names, which fits
     the repo's code-generation preference. Keep the skill's `install-remote:`
     line as the single source of URL + token path, as `agentsview_pass.py`
     already does.
  Keep the CLI (with `--server`) for the agent-facing skill and ad-hoc probing.
  `agentsview_pass.py`'s existing subprocess path works and needs no migration
  unless it grows a termination/children check.
