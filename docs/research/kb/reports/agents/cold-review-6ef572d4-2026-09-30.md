## Focus-area answers

1. **Does the new credential-scrub test really bind what the installed graphify reads?** Only partly. It binds exactly this: *double-quoted* string literals ending in one of 9 suffixes, inside graphify's *own* `.py` files. Today that is complete for `detect_backend()`: the regex finds 22 names, the native function 14, and both sets are inside the scrub list. It misses:
   - single-quoted and f-string names;
   - other suffixes (`_PASSWORD`, which covers 2 names graphify reads today; `_CREDENTIALS`; `SECRET_ACCESS_KEY`; `_PROVIDERS`);
   - names that dependency SDKs read on their own;
   - every custom-provider `env_key`, whether user-global or project-local.

   The native `backend_detection_env_vars()` catches the M6 and custom-provider cases. The claim "a bump that reads a new name fails there" is therefore overclaimed (F1, F2).
2. **Is the receipt writer change safe for the "verbatim" contract?** Yes, for what it does:
   - I fetched the Graphify-Labs/graphify releases from `gh api` on 2026-09-30. All 7 new receipts (and the existing 0.9.65 receipt) are byte-identical to `body.rstrip("\r\n") + "\n"`.
   - No upstream body contains CR or trailing whitespace.
   - The only consumer, `_receipt_drift` (`graphify_currency.py:392-399`), checks that the file exists, not its bytes.

   Residuals are listed in F6: shapes that still fail hygiene, and a test that cannot see CR or pin "trailing only". A structural alternative is to add `docs/receipts/graphify/**` to the verbatim-tree excludes, with a secret scan by path as `workflow.verbatim-trees-secret-scanned` already does elsewhere. That would also make F3's allowlist unnecessary.
3. **Does the uv.lock move carry anything besides graphifyy?** Yes. There are five new transitive packages and no other version moves (F5). The notable ones are the 326 MB `tree-sitter-language-pack` and the wheel-less aarch64 `tree-sitter-vb-dotnet`. Both arrive through the existing `override-dependencies = ["graphifyy[all]"]` (`python/pyproject.toml:57`).
4. **Is anything in the 0.9.66-0.9.72 receipts a risk for the zero-token / data-loss posture?**
   - **0.9.72 skill auto-refresh (#3895): YES, see F4.** It writes to user-level HOME directories, not repo data. It backs up edits to `SKILL.md.bak`, so nothing is lost, but the write happens without consent.
   - **0.9.66 PYTHONHASHSEED re-exec:** no risk. It forwards `{**os.environ, "PYTHONHASHSEED": "0"}` (`__main__.py:660`), so the child inherits the already-scrubbed env and the scrub survives.
   - **0.9.72 "hosted platform" banner:** no risk. It only prints the URL (`__main__.py:942`). `__main__.py`/`cli.py` contain no `urlopen`/`requests`/telemetry.
   - **Security fixes in 0.9.68 (shell injection in the `--watch` reference), 0.9.70 (Fortran cpp host-file read GHSA-pcc4-rvhr-2pr8; Terraform secret redaction) and 0.9.72 (atomic label/signature sidecars):** these reduce risk.
   - **Vendor skill bytes:** unchanged by any hand edit. `.claude`/`.codex` `SKILL.md` and `references/add-watch.md` are byte-identical to the installed package's `skill.md`, `skill-codex.md` and `skills/*/references/add-watch.md`. The `.agents` stub is byte-identical to base, and all three stamps read 0.9.72.
