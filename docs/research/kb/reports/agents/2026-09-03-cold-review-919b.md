## What the change does (inferred)

`check_settings_wiring` previously flattened every hook entry of an event into one
command blob and one matcher-token pool before checking a `_SETTINGS_WIRING` row.
The change selects "owning" entries — those whose command contains at least one of
the row's required substrings — and checks both the command blob and the matcher
pool against only those, with `scoped = owners or entries` as a fallback. Plus two
new tests, two rewritten assertions, one rewritten comment block, one rewritten
module docstring.

## Primary verdict on the brief's axis 1 (a hole the scoping opens): NONE

Proof: `owners ⊆ entries`, and every excluded entry contains **none** of `required`.
So the command check is *identical* (any entry that could satisfy a required token is
by definition an owner), and the matcher token set only shrinks. Therefore
`failures_new ⊇ failures_old` for every settings shape; the fallback restores exact
parent behaviour when `owners == []`.

Control: randomized differential, **4,000 shapes** (11 command strings × 11 matchers ×
5 events, 0–3 entries each) run against the parent module (`git show 33bdaed:…`) and
HEAD. **0 shapes where the new code is greener than the parent.**

Riskiest shape that held: **S7** — the guard legitimately split across two entries with
complementary matchers (`Bash` → guard.sh, `AskUserQuestion|Edit|Write|NotebookEdit` →
guard.sh). Stays GREEN, correctly, because both entries really run the guard. That same
property — ownership is command-based, pooling is across owners — is exactly what makes
F2 below possible.

The commit's motivating measurement is **real and reproduced**: parent code + real
`.claude/settings.json` + guard matcher narrowed to drop `Bash` → GREEN ("reported
fully wired"); HEAD → RED with `settings.json PreToolUse hook must be scoped with
matcher 'Bash'`.

### F2 — MEDIUM. Ownership pooling re-opens the same hole one level down, and the
### multi-owner axis has zero test coverage in either direction.

`python/src/dotfiles_setup/hook_selfcheck.py:212-213, 229`

`tokens` is still a **union across all owners**. An entry becomes an owner by
substring containment in its command, so an entry that merely *mentions* the required
command donates its matcher tokens. Two live green shapes against HEAD:

- **S2** (PreToolUse): real guard entry narrowed to `"matcher": "Bash"`, plus
  `{matcher: "AskUserQuestion|Edit|Write|NotebookEdit", command: 'echo "disabled: bash

  `dotfiles-setup mise-config-context` supplies `Edit|NotebookEdit` → **GREEN**.

Neither is a regression versus the parent (both were green there too) — but the fix's
comment frames this class as handled, and it is not.

**No test covers the multi-owner axis at all.** Mutation M3 — replace the union with a

### F3 — MEDIUM. Comment states something the code does not do: the fallback rationale.

`python/src/dotfiles_setup/hook_selfcheck.py:209-211`

> "If none owns the row, fall back to every entry — the old behaviour — so a missing
> command still reports missing **rather than silently passing or crashing**."

Both halves are false. With `scoped = owners` and `owners == []`: `joined == ""` so
**every** required token is reported missing, and `tokens == set()` so **every**
required matcher is reported missing. There is no crash and no silent pass — the
no-fallback form is strictly redder.

Measured, 6,000 random shapes (`scratchpad/diff2.log`), comparing HEAD against a
`scoped = owners` variant:

```
shapes where fallback changes verdict: 3986;  fallback ADDS a failure: 0;
fallback turns RED->GREEN: 0
```

The fallback's only real effect is suppressing redundant matcher failures when the
command is already reported missing. That is a fine reason — it is just not the reason
the comment gives, and the comment invents a crash/silent-pass risk that does not exist.
(Live check, shape **S6**: rename the guard command → RED with exactly one failure,
`settings.json PreToolUse hook is missing 'scripts/pretooluse-guard.sh'`.)

### F4 — LOW-MEDIUM. The two rewritten test comments have the direction backwards, and
### the change they justify is currently inert.

`tests/test_hook_selfcheck.py:134-138` and `:167-171`

- `:134-138` — "PostToolUse independently requires `'Bash'` nowhere, so an unscoped
  check here would pass for the wrong reason" is a non-sequitur: if nothing else
  requires `'Bash'`, the unscoped form is *exactly equivalent*.
- `:167-171` — the comment is attached to the **negative** assertion
  (`assert not any("'NotebookEdit'" … or "'Write'" …)`). Narrowing the list scanned by
  `assert not any(...)` makes it **easier** to satisfy — weaker, not stronger; it can
  only prevent a future false RED, never a false PASS. The laundering risk it describes
  is real but belongs to the **positive** assertion one line above
  (`assert any("'Edit'" in f …)`, line 166) — PostToolUse *does* independently require
  `'Edit'`, so an unscoped `any` there really could pass for the wrong reason. The fix
  is right, on the wrong line, for the stated-wrong reason.
- Empirically inert today: stripping the `pretooluse_failures` filter from both tests
  (M1) → **29 passed** (`scratchpad/m1.log`).
