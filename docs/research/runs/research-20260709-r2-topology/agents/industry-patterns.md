# Run B / Angle 5 — Industry patterns: monorepo image fan-out and shared-base toolchains

Date: 2026-07-09. Researcher: industry-patterns agent (remote container; Bash disabled — evidence via mintlify cache, Read/Grep, WebSearch/WebFetch).
Grounding: `docs/research/runs/research-20260709-r2-inventory/report.md`; repo files `docker-bake.hcl`, `.devcontainer/Dockerfile`.

## Scope

Survey how serious projects structure dev/CI image families — devcontainers/images, Codespaces prebuilds, Uber Devpod (Google/Meta-style monorepo dev environments), nix dockerTools layering, mise's own Docker/CI guidance, bake shared-base graphs, GitHub runner-images — and extract the patterns most applicable to a solo-maintainer repo whose single `:dev` image is ~38GB.

## Findings

### F1 — The officially-endorsed fork mechanism is exactly what this repo already has: ONE multi-stage Dockerfile, multiple bake targets

Docker's own Bake documentation, on the page describing cross-target `contexts = { base = "target:base" }` wiring, states: *"In most cases you should just use a single multi-stage Dockerfile with multiple targets for similar behavior. This case is only recommended when you have multiple Dockerfiles that can't be easily merged into one."* (<https://docs.docker.com/build/bake/contexts/>, fetched 2026-07-09).

Depot's bake deep dive (published 2024-02-19, updated 2025-12-12) confirms the dedup behavior that makes a two-target fork cheap: *"BuildKit will only build the `base` target once, even though there are two different targets specifying it"* — shared base work is built once per bake invocation regardless of how many targets consume it (<https://depot.dev/blog/buildx-bake-deep-dive>).

Repo mapping: `.devcontainer/Dockerfile` already has the stage graph `devcontainer-base` (line 33) → `devcontainer` (line 319) → `devcontainer-runtime` (line 386), plus the decoupled `clang-builder-cold`/`p2996-export` (lines 224, 307). `docker-bake.hcl` already expresses per-stage targets that `inherits = ["_common"]` and pin different `target =` stages (`dev`:77, `base`:122, `p2996-cache`:146). Adding a lean `ci`/web variant is, per the industry-canonical pattern, one new `FROM`-stage + one new bake target — NOT a second Dockerfile and NOT a separate repo. The warm-path trick the repo already uses (digest-pinned `docker-image://` named contexts overriding local stages, `docker-bake.hcl:72-76`) is the registry-flavored version of the same `contexts` mechanism the docs describe.

### F2 — Image families everywhere: lean shared base + per-purpose variants; vendors steer users AWAY from the one-giant-image shape

**devcontainers/images** (the reference dev-image family, cached docs): the repo is a monorepo of per-image directories `src/<image-name>/{Dockerfile,manifest.json,meta.env,test-project}` (cache `docs/research/mintlify-cache/devcontainers/images/llms-full.txt:16-185`), publishing three categories — base images, language images, and the one `universal` image (llms-full.txt:968-976). The decision guide is explicit: multi-language / Codespaces-without-config → `universal`; otherwise use a language image or a base image, and *"If your project is primarily one language but occasionally needs another, use the language-specific image and add the other language as a Dev Container Feature rather than using the universal image"* (llms-full.txt:1357-1367). The `universal` image — the industry's biggest "one image everywhere" — is called out as *"the largest image in this set"*, is **published only for x86-64** (llms-full.txt:1073, 1097), and is versioned independently via a `manifest.json` `version` property because it *"receive[s] upstream changes that could introduce breaking changes independently"* (llms-full.txt:904-912). Notably the variants are NOT all layered on one registry base: `universal` builds `FROM ubuntu:noble` directly (<https://raw.githubusercontent.com/devcontainers/images/main/src/universal/.devcontainer/Dockerfile>) and `python` builds `FROM python:${VARIANT}` upstream (<https://raw.githubusercontent.com/devcontainers/images/main/src/python/.devcontainer/Dockerfile>) — the sharing is at the **script/Feature layer** (common-utils), not the byte layer. For a solo repo that wants byte-level sharing, the single-Dockerfile fork (F1) is strictly stronger than the devcontainers approach.

**Uber Devpod** (blog 2022-12-13, <https://www.uber.com/blog/devpod-improving-developer-productivity-at-uber/>): the monorepo dev environment ships as **six "flavors"** — Go, Java, Android, Web, ML, and Base — where a flavor is *"a Devpod docker image tailored for a specific set of engineers"*, all built on a shared base that itself sits on the production Debian base image (*"Critical software configuration can be reused by simply building on top of the production base image"*). Freshness is handled with release channels (stable / RC / dev-nightly / none) and overnight automatic updates with gradual rollout. This is the Google/Meta-shape answer at scale: **N per-audience variants forked from one maintained base, refreshed on a nightly channel** — structurally identical to "lean `:ci` + heavy `:dev` from one base stage, both republished by the nightly cron".

**devcontainers/images tag discipline** is also worth copying: every image gets a *release* tag family (immutable semver, `1.2.3-variant`) and a *dev* tag family (mutable, regenerated weekly from main) (llms-full.txt:924-952). The repo's `:dev` + promote-retag flow already matches the "dev tags" half; a second variant should simply join the same tag families (`:ci` / `:ci-<sha>`), not invent a new lifecycle.

### F3 — Nobody in industry delivers a ~38-50GB toolchain by registry pull at session start; the big players sidestep the pull entirely

- **GitHub Actions runner-images**: ubuntu-latest arrives with **>50GB already consumed** by preinstalled toolchains (34GB in /usr, 11GB /opt toolcaches) — delivered as a **VM disk image**, never docker-pulled by the job (<https://dev.to/mathio/squeezing-disk-space-from-github-actions-runners-an-engineers-guide-3pjg>, <https://github.com/actions/runner-images>). The industry's biggest "everything image" is a machine image, not an OCI pull.
- **GitHub Codespaces prebuilds**: a prebuild is a **stored snapshot of the fully-created container** per (repository × branch × devcontainer.json), updated by a GitHub-managed Actions workflow on every push; codespace creation *"downloads the existing container snapshot from storage and deploys it on a fresh virtual machine"* — i.e., the expensive create/pull happens once in CI, and each prebuild consumes billable storage (<https://docs.github.com/en/codespaces/prebuilding-your-codespaces/about-github-codespaces-prebuilds>). The economic model: pay storage per branch-snapshot to make session start O(snapshot-restore), not O(image-pull).
- **Hyperscaler lazy pulling** (eStargz / AWS SOCI / Nydus): the ≥10GB-image cold-start problem is treated as a *platform* problem solved below the runtime — SOCI parallel pull cut 10GB pulls ~60% in 2025 AWS benchmarks; eStargz gives ~10x cold-start improvements — but every approach *"requires replacing the containerd snapshotter on every node"* plus a daemon/FUSE (<https://blog.zmalik.dev/p/lazy-pulling-container-images-a-deep>, <https://aws.amazon.com/blogs/containers/introducing-seekable-oci-parallel-pull-mode-for-amazon-eks/>). None of that is available to a Claude-Code-web sandbox or a stock GHA runner.

Implication for this repo: there is **no industry-sanctioned mechanism** by which a web/CI session pulls the 38GB `:dev` at start. The consistent answer is a thin variant image (F1/F2) for pull-at-start consumers, with the heavy payload reserved for the persistent local devcontainer (which already amortizes the pull via `mise run sync` + the content-hashed `base-<hash16>` registry cache, `docker-bake.hcl:104-121`).

### F4 — For GitHub Actions specifically, mise's own docs treat mise-on-runner (mise-action + cache) as the first-class pattern; a mise-preinstalled image is their GitLab pattern

mise's CI docs (local cache, `docs/research/mintlify-cache/jdx/mise/llms-full.txt:3420-3442`) recommend `jdx/mise-action@v3` with `cache: true` on GitHub Actions — *"Tool caches are keyed on `mise.toml` and `mise.lock` so they invalidate automatically when your tool versions change."* The "build a Docker image with mise pre-installed, cache `MISE_DATA_DIR`" recipe is presented for **GitLab CI** (llms-full.txt:3446-3482), where jobs natively run inside an image. The mise Docker cookbook (<https://mise.jdx.dev/mise-cookbook/docker.html>) adds the devcontainer-relevant `mise install --system` pattern (tools in `/usr/local/share/mise/installs`, immune to home-volume mounts) but says nothing about purpose-split images. Conclusion: keeping ci.yml's lint/contract jobs on mise-action-with-lockfile-keyed-cache is aligned with upstream guidance and already near-optimal on GHA; the motivation for a lean image is **web sessions** (which cannot run mise-action-style host installs against a 30-tool set within session-start budgets), not replacing the CI runner installs. A lean image that *also* satisfies CI is a bonus convergence, not the driver.

### F5 — Cross-variant byte sharing only happens when layer boundaries are engineered for it; content-addressed base tags are the single-maintainer version of that discipline

Graham Christensen's nix layering work (2018-10-01, <https://grahamc.com/blog/nix-and-layered-docker-images/>; now `dockerTools.buildLayeredImage`/`streamLayeredImage` in nixpkgs) demonstrates the underlying mechanic: when layer boundaries follow the dependency graph instead of Dockerfile RUN order, *independent images share layers automatically* (his PHP and MySQL images shared 20 layers; push/fetch improved "by an order of magnitude", within Docker's 125-layer limit). The Dockerfile-world equivalent, per F1, is forking every variant from the **same built base stage** so the shared layers are digest-identical and each consumer pulls them once. The repo's `base-<hash16>` content-addressed registry tag + manifest-probe short-circuit (`docker-bake.hcl:104-121` — deliberately registry-as-cache, after GHA-cache SAS-TTL failures) is the same idea devcontainers/images uses (per-image `manifest.json`-driven tags, weekly dev tags) and is exactly what preserves the warm path under a two-image split: **both** `dev` and a new lean target must consume the SAME `devcontainer-base` (or an earlier, thinner shared stage) named context, so one probe/one base build serves both, and the lean image's rebuild cost is only its own thin layer.

### Synthesis — the 4 patterns most applicable to this repo (solo maintainer, 38GB image)

1. **Fork inside the one Dockerfile, publish per-stage bake targets** (F1). Delta vs today: +1 stage, +1 bake target, +1 tag family; zero new Dockerfiles; BuildKit/named-context dedup keeps one base build. This is both the Docker-docs default and the cheapest to maintain solo.
2. **Small variant count, one refresh pipeline** (F2, Uber/devcontainers). Two variants (lean + heavy) is well inside industry norms (Uber runs six); publish both from the same nightly/on-merge pipeline with the same promote/retag lifecycle rather than a second workflow.
3. **Never plan on pull-at-session-start for the heavy image** (F3). Every industry consumer of >10GB toolchains uses VM images, stored snapshots, or platform lazy-pull — none available here. The heavy image's audience is only the persistent local devcontainer; every ephemeral consumer (web, CI-in-container if ever) gets the lean variant.
4. **Keep CI on mise-action unless the lean image is free** (F4). Upstream mise guidance endorses runner installs with lockfile-keyed cache on GHA; switch ci.yml jobs to `container:` only if the lean image exists anyway for web and measurably beats the cached mise-action setup time.

## Uncertainties / gaps

- **No citable exact size for `devcontainers/universal`**: docs say only "largest image in this set" and x86-64-only; searches surfaced no authoritative GB figure (commonly reported ~10GB+ uncompressed, unverified). Comparison "38GB is ~3-4x the biggest industry one-image" is directionally right but not precisely sourced.
- **Uber Devpod details predate the 12-month window** (2022-12-13) and describe a platform team, not a solo maintainer; used here for the shape (flavors atop shared base, release channels), not for cost numbers. No equally detailed 2025-26 Meta/Google write-up surfaced in searches.
- **devcontainers/images sharing is script-level, not byte-level** (python builds FROM upstream `python`, universal FROM `ubuntu:noble`) — so it validates the *family* pattern but is weak evidence for the *shared-base-stage byte reuse* claim; that claim rests on Docker/Depot bake docs (F1) instead.
- **Claude-Code-web pull behavior** (what image sizes/session-start budgets it tolerates) is Run A's domain; F3's "web can't pull 38GB" premise is taken from the domain brief and industry analogy, not measured here.
- The mise-cookbook fetch showed no multi-stage/purpose-split guidance — mise upstream is silent on lean-vs-heavy image splits; the split rationale must come from the bake/devcontainers evidence, not mise docs.
