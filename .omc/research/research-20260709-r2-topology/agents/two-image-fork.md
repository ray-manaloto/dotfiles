## Findings

### F1. The documented "natural fork seam" (runtime tier) is the WRONG seam for a lean/heavy split — the true seam cuts through the BASE tier

The runtime tier's header sells itself as the thin-stage seam ("editing THIS
file rebuilds only the thin runtime stage, not the ~30-min base",
`.devcontainer/mise-runtime.toml:10-12`), and the domain brief calls it "the
documented natural fork seam". But the runtime tier holds only thin CLIs
(gh, fnox, bats, sccache, pipx C++ *linters*, AI CLIs — `mise-runtime.toml:35-65`).
The heavy payload and the lean toolchain live TOGETHER in the base tier:

- One `mise install --system --locked` RUN in stage 1 (`.devcontainer/Dockerfile:171-188`)
  installs BOTH the lean web/CI toolchain (the 20 exact-pinned shared tools —
  hk 1.50.0, pkl, python 3.14.6, uv, chezmoi, gitleaks + linters,
  `.config/mise/conf.d/shared.toml:20-40`, merged via `conf.d/`,
  Dockerfile:134-139) AND the heavy payload: 8 language runtimes at `latest`
  (node, bun, go, rust, zig, java, deno, ruby — `mise-system.toml:20-29`) plus
  ~25 `conda:` C++ toolchain packages (llvm, clang, cmake, gdb, lldb,
  valgrind, … — `mise-system.toml:38-76`).
- The other heavy bytes (gcc-latest trunk .deb → `/opt/gcc-latest`, clang-p2996
  COPY → `/opt/clang-p2996`) land in stage 4 (`Dockerfile:336-355`), *after*
  the base stage.

**Consequence:** forking `dev` vs `ci` leaves at the existing
`devcontainer-runtime` boundary is useless (the lean leaf would still contain
the ~30+ GB base). A two-image topology requires a NEW tier split *inside*
today's BASE tier: a `core` tier (shared 20 + python/uv, the ci.yml
contract/test toolchain) and a `cpp` tier (runtimes + conda toolchain).

**mise natively supports this split with zero custom machinery**
(tool-currency rule satisfied):

- Config environments: `config.<env>.toml` is discovered beside `config.toml`
  in `$MISE_CONFIG_DIR` and merged additively — probe-verified in-repo for the
  runtime tier (`mise-runtime.toml:3-8`; Dockerfile:386-409).
- `MISE_ENV` accepts a comma-separated list (`MISE_ENV=ci,test mise install`) —
  mise docs, Config Environments
  (<https://www.mintlify.com/jdx/mise/configuration/environments.md>; local
  cache `docs/research/mintlify-cache/jdx/mise/llms-full.txt:1036-1044`). So
  the heavy leaf can set `ENV MISE_ENV=cpp,runtime` and the lean leaf no env
  (or `MISE_ENV=ci`), each pulling exactly its tier stack.
- Per-env lockfiles are native: mise writes `mise.<env>.lock` beside
  `mise.lock` — already exercised by `mise.runtime.lock`
  (`Dockerfile:389-392`), regenerated by the daily `lock-refresh` job. A
  `mise.cpp.lock` is the same mechanism, one more file in the lock-refresh
  composite.

### F2. Proposed stage/tag graph — as a delta against today's bake targets

Today (current-graph F1/F2): 5 stages, published targets `dev`
(= `devcontainer-runtime`), `base` (= `devcontainer-base`, `:base-<hash16>`),
`p2996-cache` (= `p2996-export`, `:p2996-<hash16>`).

**Delta (additive; nothing existing is renamed except the base stage's FROM):**

```
ubuntu:26.04 (digest-pinned)
  └─ devcontainer-core        [NEW] apt bootstrap + mise + shared.toml
     │                              + mise-core.toml (python/uv + 20 shared)
     │                              → NEW tag family :core-<hash16>
     ├─ devcontainer-ci       [NEW LEAN LEAF] (+ gh cli, little else)
     │                              → NEW tags :ci, :ci-<sha>, :ci-pr-NNN,
     │                                marker :ci-<hash16>
     └─ devcontainer-base     [CHANGED: FROM devcontainer-core]
        │                            installs config.cpp.toml under MISE_ENV=cpp
        │                            (runtimes + conda toolchain) → :base-<hash16>
        └─ devcontainer       [unchanged] + gcc-latest + COPY p2996-export
           └─ devcontainer-runtime [unchanged, MISE_ENV=cpp,runtime] → :dev …

clang-builder-cold / p2996-export   [unchanged, decoupled since #160 T11]
```

bake delta (`docker-bake.hcl`): add `target "core"` (stage
`devcontainer-core`) and `target "ci"` (stage `devcontainer-ci`, own tags,
`cache-from/to type=gha,scope=dotfiles-ci`), plus
`group "leaves" { targets = ["dev", "ci"] }`. Separate gha cache scope is the
documented pattern for multiple images — "each build would otherwise overwrite
the previous cache … specify this scope attribute with a specific name"
(<https://docs.docker.com/build/cache/backends/gha/>). The `dev` target keeps
`scope=dotfiles-dev` (`docker-bake.hcl:89-94`).

**How the leaves share layers/caches — two mechanisms, both verified:**

1. **Single-invocation dedup.** When one `docker buildx bake` invocation
   builds multiple targets that share a stage, "BuildKit builds each target
   concurrently and deduplicates common work across targets. In practice, one
   target will compute the common work, and the others will just reuse that
   result" (Depot, "Buildx bake deep dive",
   <https://depot.dev/blog/buildx-bake-deep-dive>; general mechanism also in
   <https://docs.docker.com/build/bake/targets/> — groups build targets in one
   graph; attribution of shared stages to a target in the output is arbitrary,
   docker/buildx#3312). So `bake leaves` builds `devcontainer-core` ONCE and
   both leaves reuse it — free, no plumbing.
2. **Cross-job/registry sharing via the existing probe-cache pattern.** This
   repo's warm path is NOT BuildKit layer cache for heavy tiers — it is
   registry-manifest probing + digest-pinned named build contexts
   (`build-publish.yml:543-550`; current-graph F3). The fork extends it with a
   4th tier: a `core-prep` job probes `:core-<hash16>`, and BOTH `base` (heavy
   chain) and `ci` (lean leaf) consume the core image as
   `*.contexts.devcontainer-core=docker-image://…@sha256:…`. For split
   Dockerfiles (not needed here), bake also supports `target:` contexts —
   "To use a result of one target as a build context of another, specify the
   target name with `target:` prefix"
   (<https://docs.docker.com/build/bake/contexts/>) — but Docker docs
   recommend that mainly for "multiple Dockerfiles that can't be easily
   merged into one"; this repo's single multi-stage Dockerfile + named-context
   override is the already-proven equivalent (#160 T11 retired exactly that
   kind of ARG indirection, `Dockerfile:25-30`).

Recommended composition: `core-prep` job (probe, <30s warm) → its digest feeds
(a) `base-prep`'s miss-path build as a named context, and (b) a `ci` build
that is cheap enough (~minutes: 20 pinned tools + python/uv on top of core) to
run inside the existing `build` job as `targets: dev ci` in ONE bake
invocation — dedup then makes the ci leaf nearly free on warm paths.

### F3. Content-hash warm path and migration cost — preserved, with one bounded cold rebuild

- The sentinel design means new stages appended OUTSIDE the
  `BASE_HASH`/`P2996_HASH` sentinel regions do not bust `:base-`/`:p2996-`
  ("Only the *sentinel-delimited* Dockerfile sections feed the hashes",
  `.devcontainer/P2996-CACHE.md:75-77`). But any Dockerfile edit busts
  `:dev-<hash>` exactly once, because dev-hash deliberately folds the WHOLE
  Dockerfile ("under-hashing here is the cardinal sin",
  `python/src/dotfiles_setup/p2996_hash.py:131-135`).
- Splitting `mise-system.toml` DOES bust base-hash — its bytes are a
  base-hash input (P2996-CACHE.md:57-60; PR #140). So the migration PR costs
  exactly **one ~20-30 min cold base build** (build-publish.yml:84-86) and
  **zero compiler rebuilds** (p2996-hash is independent of base since #160
  T11, P2996-CACHE.md:41-44). The `identity-expected` merge-base logic
  handles the transition PR natively — on a branch that changes an image
  build input, the expected hash is the merge-base blob and the new base is
  validated by that PR's own CI
  (`.claude/rules/verify-before-advancing.md:54-67`;
  `tests/test_image_smoke.py:554-567`).
- New hash tiers follow the existing schema: `core-hash` = BASE_IMAGE +
  PLATFORM + new `CORE_HASH_BEGIN/END` sentinel section + bytes of
  mise-core.toml/lock + shared.toml + hk pkls; `base-hash` then folds
  `core-hash` + the cpp-section inputs (exactly how dev-hash already folds
  base+p2996, `p2996_hash.py:432-444`); `ci-hash` = core-hash + ci-section
  digest, stamped as a `:ci-<hash16>` validated marker only after the lean
  leaf's (fast) smoke — the same "built AND smoke-validated" marker semantics
  as `:dev-<hash>` (`build-publish.yml:707-779`).
- Retention: `PRUNABLE_FAMILIES = ("base-", "p2996-", "dev-")`
  (`python/src/dotfiles_setup/ghcr_cleanup.py:29`) must gain `"core-"` and
  `"ci-"` in the same change, or the new families accrete forever.

### F4. Tag/promotion scheme that keeps both leaves in lockstep

- **One package, prefixed tag families** (recommended): keep everything under
  `ghcr.io/ray-manaloto/dotfiles-devcontainer` so `IMAGE_REF` consolidation
  (`docker-bake.hcl:11-13`), ghcr-cleanup, and the GHCR permission set stay
  single-target. The lean leaf gets `:ci` (rolling), `:ci-<sha>`,
  `:ci-pr-NNN`, `:ci-<hash16>` (marker) — mirroring `:dev`'s families.
- **Lockstep = same commit, same run, single promote transaction.** Both
  leaves are built/published by the same `build-publish` run (same
  `github.sha`); on merge, ci.yml's `promote` job — today a manifest-only
  `docker buildx imagetools create` retag of `:pr-NNN` → `:dev`/`:latest`
  (`ci.yml:326-446`) — performs BOTH retags (`:pr-NNN`→`:dev`,
  `:ci-pr-NNN`→`:ci`) in one job body, failing the job if either retag fails,
  so the two rolling tags can never point at different commits for longer
  than one failed (red, visible) promote. The `force_dev_tag` fallback
  (`ci.yml:36-37,481`) extends the same way.
- **Industry analog:** devcontainers/images publishes a fan-out of images
  where an image built on another repo image declares `"parent"` in its
  `manifest.json` — "Specifies the parent image name within this repository …
  The build system uses this to order builds correctly" — and one release
  VERSION stamps every image/variant's tags (`${VERSION}-${VARIANT}` tag
  patterns), which is exactly the "one version, all leaves" lockstep model
  (local cache
  `docs/research/mintlify-cache/devcontainers/images/llms-full.txt:285-302,360`).
- Attestations: all published targets today carry provenance mode=max + SBOM
  (#160 T7, `docker-bake.hcl:95-102,129-133,153-159`); the `core` and `ci`
  targets must inherit the same `attest` block, and the build job's
  provenance-materials assertion (`build-publish.yml:572-588`) generalizes to
  "ci leaf's provenance contains the core digest".

### F5. Devcontainer prebuild pipelines handle exactly this shape via per-config prebuilds

The multi-config layout (`.devcontainer/devcontainer.json` heavy +
`.devcontainer/ci/devcontainer.json` lean) is first-class across the
ecosystem:

- **Codespaces prebuilds** are scoped per (repository, branch,
  devcontainer.json configuration file): "A prebuild assembles the main
  components of a codespace for a particular combination of repository,
  branch, and `devcontainer.json` configuration file" — one repo can carry
  multiple configs, each with its own prebuild, refreshed on push
  (<https://docs.github.com/en/codespaces/prebuilding-your-codespaces/about-github-codespaces-prebuilds>).
- **devcontainers/ci action** selects the config via `configFile` ("Use this
  to specify the repo-relative path to the devcontainer.json file. Defaults
  to `./.devcontainer/devcontainer.json`") with per-config `imageName`,
  `cacheFrom`, `push`
  (<https://github.com/devcontainers/ci/blob/main/docs/github-action.md>).
- **devcontainer CLI `--prebuild`**: "When `--prebuild` is passed to
  `devcontainer up`, execution stops after `updateContentCommand` … useful
  for pre-building container images"; "Combine `--prebuild` with a
  registry-push workflow so the result of `onCreateCommand` is cached in the
  image layer" (local cache
  `docs/research/mintlify-cache/devcontainers/cli/llms-full.txt:648-657,1958`).

So if the lean leaf is consumed *as a devcontainer* (Codespaces, or a web
session runtime that reads devcontainer.json — Run A's question), the
standard pattern is a second config pointing `"image":
"ghcr.io/…/dotfiles-devcontainer:ci"` — no second Dockerfile, no fork of the
lifecycle scripts.

### F6. What the lean leaf can and cannot serve (scope honesty)

- **Covers:** contract-preflight (`python`+`uv` only,
  `build-publish.yml:100-103` pattern; ci.yml per current-graph F6), pytest,
  hk/pkl lint *core* (shared 20 includes hk, pkl, shellcheck, hadolint,
  actionlint, typos, yamllint…), chezmoi — i.e. the "Claude-Code-web-
  compatible env + ci.yml lint/test toolchain" of candidate shape (ii),
  MINUS the caveat below.
- **Does not automatically cover ci.yml's `lint` job**, which installs the
  FULL root `mise.toml` toolset on the runner (setup-mise with no
  `install_args`; current-graph F6) including deliberately image-excluded
  tools — `npm:renovate` is "host-only … not needed in the ~354MB-heavier
  image" (`.config/mise/conf.d/shared.toml:17-19`). Serving lint from the
  leaf means either widening the leaf (re-importing that weight) or keeping
  lint on mise-on-runner. **Recommendation: keep CI lint on mise-on-runner**
  — jdx/mise-action caching keyed on `mise.lock` is already warm-fast and is
  the current CI-local-parity mechanism; the leaf's load-bearing consumer is
  web sessions, with CI adoption optional later (incremental, reversible).
- **Registry cost ≈ 0:** GHCR container storage and bandwidth are currently
  free for public packages, and Actions-internal bandwidth stays free
  (<https://docs.github.com/en/billing/concepts/product-billing/github-packages>).
  The real new recurring cost is CI minutes for the ci leaf build (~minutes,
  warm-path near-zero via dedup/probe) and one more lock file in
  lock-refresh.
- **Size estimate (inference, flagged):** the pre-C++-payload image measured
  1.33 GB on 2026-03-29 (current-graph F5, stale benchmark) — a core+ci leaf
  (20 pinned tools + python/uv, no runtimes, no conda toolchain) should land
  in the ~1-2.5 GB range vs ~38 GB for `:dev`. No current measurement exists;
  must be validated from the first ci-leaf CI run's dive/benchmark artifact.

### F7. Convergence path back to one image — additive and cleanly reversible

Because both leaves are stages of the SAME Dockerfile with hash-sentinel
regions, the fork is a pure superset delta:

- **Roll-forward:** migration PR = split mise-system.toml → mise-core.toml +
  mise-cpp env config (+locks), re-root `devcontainer-base` on
  `devcontainer-core`, add `core`/`ci` bake targets + `core-prep` job +
  `ci`-tag legs in metadata/promote/ghcr-cleanup/changes-filter. Cost: one
  cold base build (F3), no compiler rebuild, one dev-hash marker miss.
- **Roll-back / converge to one image:** delete the `ci` bake target, its
  tag legs, and the prep-probe; `devcontainer-core` can REMAIN as an internal
  stage indefinitely at zero cost (unpublished stages in a multi-stage file
  cost nothing; the heavy chain still builds through it, and the tier split
  of mise configs is independently valuable for cache granularity). This
  makes the two-image experiment cheap to abandon — the one-way door is only
  the mise-system.toml split, which is itself a cache-granularity improvement
  worth keeping in a one-image world.
- Full convergence to a single LEAN image is impossible while the
  devcontainer's R1/R2/R3 + C++ toolchain requirements stand (AGENTS.md
  success criteria) — the heavy leaf is not optional; only the lean leaf is.

## Uncertainties / gaps

1. **The lean leaf's load-bearing consumer is unverified from this angle.**
   Whether Claude Code web sessions can pull/use ANY custom image (and at
   what size ceiling) is Run A's domain. If web sessions cannot consume a
   registry image at all, the ci leaf's remaining value (CI lint/test in a
   container) is weak — mise-on-runner is already near-optimal there (F6) —
   and the recommendation degrades to "do only the mise tier split for cache
   granularity, skip the second published image."
2. **No measured sizes.** The ~1-2.5 GB lean-leaf estimate rests on a stale
   2026-03 benchmark (1.33 GB) plus tool-count reasoning; the ~38 GB `:dev`
   figure is doc-derived (current-graph F5). First ci-leaf build must publish
   a dive/benchmark artifact before size claims are load-bearing.
3. **Bake dedup applies only within one invocation.** The claim "core built
   once for both leaves" holds for the same-job `targets: dev ci` path; the
   cross-job path relies on the `:core-<hash16>` probe tier instead. Adding
   `core-prep` serializes one more <30s-warm job ahead of base-prep on the
   miss path (base's named-context needs core's digest); exact critical-path
   cost unmeasured.
4. **mise config-env semantics for `[settings]`/`[env]` blocks across three
   tiers (core / cpp / runtime)** are probe-verified for two tiers
   (runtime, `mise-runtime.toml:32`) but the three-tier merge order
   (`config.toml` + `config.cpp.toml` + `config.runtime.toml` under
   `MISE_ENV=cpp,runtime`) should be probed before committing — the repo's
   own use-tool-builtins rule 4 ("verify *which* native mechanism
   empirically").
5. **Per-env lock regeneration for a third lock** (`mise.cpp.lock`) in the
   lock-refresh composite is assumed mechanical (same recipe as
   mise.runtime.lock) but not verified against the composite's current
   staging steps.
6. Depot's dedup description is a vendor blog (corroborated by
   docker/buildx#3312 discussion of shared-stage attribution); Docker's own
   guide page fetched did not restate the dedup sentence — confidence high
   but the authoritative wording lives in the bake GA blog/guide not fetched
   here.
